## §A — THE FORK: the parenting/anchor model {F11, F4} — decision packet (M-2 pattern)

### A.0 The failure, stated against my own locked text
Locked §6 `parent_picker`: the conductor derives a candidate set; the agent selects within it; free-typed rejects. The live realization (`lineage.go:346-371` `ActiveLineageCandidates` = `WokenOn` + `ActiveDispatch` + same-dispatch accepted; offered at **render time**) is faithful to the locked text — and the locked text is what failed. Under concurrent traffic the global graph moves between render and submit; the seat's offered set is a stale snapshot; the honest retry re-renders into the same staleness (F11 — livelock, SEV-1 stop-the-line). The set is also too narrow for real reply semantics (F4: the semantically-correct reply target bounced `outside-active-lineage`). **Honesty note:** my S3 F-S3-M1-2 five-point *narrowing* was correct on the authority axis and is part of why F11 binds so hard — the lesson is not "re-widen" (that trades authority for liveness); it is that **any seat-supplied parent couples the seat to a snapshot of a moving graph.** Root cause (ledger): the seat supplies what the engine knows.

### A.1 Option A — conductor-computed PARENT with validated hint (RECOMMENDED)
**Mechanism.** `PARENT` moves from `parent_picker` to **`system_only`-computed**: the engine stamps the parent at **commit time** from the seat's turn context (woken-on relay → active-dispatch lineage → dispatch root, first defined), exactly as it stamps `FROM`. The seat MAY supply an optional **`parent_hint`** (an ordinary lane field, never authority): the engine honors the hint iff it can prove it server-side (the hinted id ∈ the seat's delivered/read history ∩ the accepted-graph); otherwise it stamps the computed default and records `parent_hint_honored: no` (audit, not bounce). **The parent-anchoring bounce class ceases to exist** — the engine can always compute a valid anchor, so no submit is ever rejected for parent staleness. Lineage-**class** gates (authority: "IMPL must parent an approved PLAN" etc.) are untouched and still bounce — with F3 detail parity (m-7). Anchoring = transport, always live; class-lineage = authority, still gated.
**Why recommended.**
1. **Completes my own contract's logic.** §6's principle is "the seat never supplies what the engine knows" — it is why `FROM`/`ROLE`/`relay_id`/`timestamp` are stamped. `PARENT` was left agent-picked as a concession to semantic knowledge; the dogfood priced that concession at a SEV-1 livelock. This branch closes the concession the way the contract already closes every other system field.
2. **The claim ladder strengthens.** Observer-*selected* (set chosen conductor-side, lane picks within) upgrades to observer-*computed* (value derived conductor-side, lane cannot even mis-pick; the hint is bookkeeping validated against conductor-known state). The sanctioned by-construction claim survives stronger; D4 grain improves; D5 residual unchanged.
3. **Kills the cluster at the root.** F11 dead (nothing seat-supplied can go stale); F4 dead (no candidate set to be projection-order-dependent); F2's dead-edge parent *offers* moot (m-2 stops rendering a parent field entirely — seam benefit); shrinks F5's surface (parent no longer among the render-context the digest must pin — composable with m-7's lease/tolerance fix, which is still needed for the rest).
**Costs, named honestly.** (a) Semantic precision for multi-target authoring degrades to hint-or-default — the record carries `parent_hint` + `parent_hint_honored` so a mis-anchored edge is visible, not silent; (b) locked §6 `parent_picker` text + the S3 F-S3-M1-2 five-point derivation are **superseded by amendment** (the real contract change that makes this the grilled fork); (c) Sharpening-D re-homes: the routing-relay reference becomes a hint-class reference (bookkeeping stays bookkeeping; model never a gate input — unchanged); (d) the turn-context derivation must be crisply owned: m-7's loop *maintains* per-seat turn context, m-1 *defines* what the stamp means, m-2 *drops* the parent field from forms and shapes the `parent_hint`/`parent_hint_honored`/`parent_provenance` rows.

### A.2 Option B — widened candidate set + commit-time revalidation with grace
Keep `parent_picker`; widen the set (delivered/read history + thread roots + dispatch lineage); revalidate at commit against the *current* graph, accepting picks valid at render (grace window). **Why not recommended:** the race is narrowed, not removed — the set still moves and a seat can still be pinned to staleness (livelock becomes rare, not impossible: not a fix for a stop-the-line SEV-1); widening erodes the S3 authority narrowing; render↔submit snapshot coupling — the root cause — survives. Cheapest diff; weakest fix.

### A.3 Option C — lineage lease/token
At render, issue a lease pinning candidate set + digest for a validity window; a submit inside the lease is honored against the render-time snapshot. **Why not recommended:** freezes the race instead of removing it (idle-past-expiry re-races; renewal storms on a busy store); adds a whole token/expiry/renewal machine + per-seat state to the TCB for less benefit than A; edges to superseded-but-accepted parents are authority-sound but semantically stale — tolerable, yet A gets the same tolerance without the machinery. Heaviest diff; treats the symptom.

### A.4 Packet disposition
**Recommendation: A.** Consequence map (A): supersede §6 `parent_picker` + S3 five-point by amendment; new m-2 rows (`parent_hint`, `parent_hint_honored`, `parent_provenance` — m-2 shapes); m-7 turn-context maintenance + commit-time stamp locus; anchoring-bounce class deleted; class-lineage gates unchanged. **Fixture obligations (build slice):** the F11 regression leg — the archived dogfood traffic replayed without livelock; hint-honored and hint-fallback fixtures; a concurrent-accept-during-submit fixture proving no parent-class bounce exists. **Grill questions for the operator:** (i) accept hint-fallback (never-bounce) over hint-reject? (ii) accept the semantic-precision cost on multi-target authoring? (iii) confirm Sharpening-D's re-home as hint-class. **No m-1 lock before the grill** ([VP-W3]).

## §C — F17: waiver scoping + retraction record class (lockable amendment)

**The gap:** `lineage.go:171-184` — the reviewer-visibility gate passes on ANY accepted operator record with non-empty `ORCH_REVIEW_WAIVER`, run-wide, forever; append-only store, no retraction class: one use permanently disables the check (live: waiver `relay-52552d61`).
**Amendment (store/record-class semantics — m-1; row shapes — m-2; gate consumption — m-2's gate over my semantics):**
1. **Scoped waivers.** A waiver record MUST declare scope: `{target relay_id | dispatch | record-class × dispatch | run-wide}` + optional bounded validity. Unscoped legacy waivers (the live one) read as run-wide until retracted — no retroactive reinterpretation of accepted records.
2. **`waiver_retraction` record class.** A new `record_kind: waiver_retraction` carrying a `retracts` id_ref to the accepted waiver record (the `resolves_gate` id_ref idiom). Append-only preserved: retraction is a new record, never a mutation — the §13.c5 supersedes-edge discipline.
3. **Gate lookup semantics (mine):** effective waiver state = accepted waivers **minus** accepted retractions, evaluated in commit order at gate time; a retraction re-arms the gate for subsequent submits; records accepted under a then-live waiver stand (immutability; no retroactive invalidation).
4. **Record-class intent (the s5-escalations pattern):** waiver + retraction are **operator-only fill-time scope** — both toggle a gate (authority-bearing); pessimistic floor, widening later = registry amendment + m-1 route-back.
**Fixtures:** scoped waiver passes only in scope; retraction re-arms (post-retraction identical submit bounces); pre-retraction accepts stand; non-operator waiver/retraction submit is fill-time absent + submit-path rejected.

## §D — F14: the store-lock INVARIANT (lockable amendment; the m-1 half of the [VP-W2] joint citation)

**The gap made explicit:** I1 ("sole governed writer") implicitly assumed ONE conductor per store root. F14 observed two live conductors on one root — two "sole" writers. The invariant needs the process grain stated:
1. **Invariant (I1-P):** at most one live conductor holds write authority over a store root at any time. A second conductor targeting a claimed root MUST refuse to serve — fail-closed, typed path-free refusal — never co-serve, never queue.
2. **When held:** claimed **before phase-0 recovery begins** (recovery mutates journal/projections and must be under the claim), held for the serve lifetime, released on clean shutdown.
3. **Takeover semantics:** takeover is legal ONLY when the prior holder provably cannot still write — no interleaving may ever have two writers. A claim that can be stolen from a live writer violates I1-P by construction. Crash-staleness resolution must ride a mechanism whose release is bound to holder death (kernel-bound, e.g. flock-style auto-release) or an equivalent proof-of-death; a bare pidfile heuristic alone does not satisfy the invariant.
4. **Claim honesty (D4/D5):** the lock stops *accidental* double-serve (the observed leftover-pid case) and confused ops — a malicious same-uid process can delete/bypass any lock: standard accepted D5 residual (§0.c). This is confusion-resistant ops protection, within the §C4.3 ceiling.
5. **Seam ([VP-W1] — restated so no downstream doc collapses it):** the invariant + semantics above are **m-1's**; the runtime enforcement — startup/refusal/takeover choreography, the concrete mechanism, and fixture execution — is **m-7's**. The F14 disposition cites BOTH halves ([VP-W2]).
**Fixture obligations (stated here, executed m-7):** second-conductor refusal; crash-then-restart single-writer takeover; an interleaving assertion that no two claims ever coexist live.

## §F — B-3 addendum: identity activation (the boot record closes the mint→bound→active loop) — **PAIR-APPROVED** (`DESIGN-REVIEW-implementer-20260706-202929`; the §F.1 carry-forwards are part of the approval; integration NOTE: m-7's B-1 classifier must-revise is a package hold, not an §F rewrite)

Per the operator-requested boot-stage addendum (`s6-design/DESIGN-orchestrator-planner-20260706-200259`, leg B-3). Honest premise inherited: this buys **lifecycle visibility + ordering**, not bounce-proofing (the observed boot bounces are already killed by A-1/branch-A). m-1's half is the **edge semantics**; m-7 rules the recording shape + roster + out-of-order disposition (B-1); m-2 rules the boot form (B-2).

1. **The three edges — what each asserts, and what it may NEVER assert:**
   - **`minted`** (the A-3 `seat_mint` pivot): the binding `{seat ↔ credential}` EXISTS. Asserts nothing about possession-now, liveness, or session. May never assert the seat has ever acted.
   - **`bound`** (first authenticated connect; **every reconnect re-binds**): CURRENT credential possession over a live channel — the locked DI-2/DI-3 re-attach re-verification (the CQ-6 binding clarification) made a lifecycle edge. May never assert the seat will act, nor any content claim.
   - **`active`** (the seat's **first accepted relay this mint-generation** — typically the B-2 boot form, but definitionally the first accept whatever its class): the full identity loop closed once — channel → stamp → gates → commit round-tripped as one live seat. **Liveness bookkeeping, NEVER an identity-strength upgrade**: the channel stamp already carries identity; activation grants no authority (the dispatch constraint: the boot stage sequences a seat's first actions; it grants nothing).
2. **Derivability (the m-1 store posture):** the activation edge is **DERIVED** — first accepted relay per mint-generation, computable from committed records + the binding table. m-1 adds **no new record class, no new system field, no on-disk change**; if m-7's B-1 chooses a recorded transition shape, it consumes my definition (and any new `record_kind` routes back per the standing rule).
3. **Session-restart semantics: reconnect = re-`bound`, NEVER re-boot. One activation per mint-generation.** A re-mint (A-3 pivot) starts a new generation → fresh activation required. Grounds: activation is per-identity-generation, not per-session — re-attach already re-proves possession (DI-2/DI-3); per-session re-boot would flood the store with ceremony and imply the stamp needs re-establishing (it does not). A boot form submitted by an already-active seat is an ordinary accepted record — it creates no second activation edge (first-accepted is idempotent by construction).
4. **Interlock with B-1's out-of-order ruling (either branch composes):** whether m-7 rules refuse-with-typed-bounce or allow-and-mark for a not-yet-active seat's non-boot submit, the m-1 edge definition holds — if the record is accepted, it IS the activation edge. My one constraint on B-1: the refusal branch, if chosen, must not recreate a bounce-retry channel on the boot path (the F10/F11 lesson); allow-and-mark is the liveness-safe default from my side.
5. **D4/D5 honesty:** activation is confusion-resistant liveness bookkeeping derived from governed-write facts; the D5 same-uid direct-write residual is unchanged (§0.c); no claim-ladder change, no by-construction creep (§C4.3 ceiling).
6. **Fixtures (build slice):** first-accept flips `active` exactly once per generation; reconnect-after-conductor-restart preserves `active` (no re-activation, no boot demanded); re-mint resets the lifecycle and requires fresh activation; an already-active seat's boot form accepts as an ordinary record with no second edge.
