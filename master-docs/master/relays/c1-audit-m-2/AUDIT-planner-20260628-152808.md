## 0. Thesis under audit (restated)

The relay stops being hand-authored markdown and becomes **a form the courier renders from typed input** — "fill the form, don't write the prose." Every field has an **owner** (system-filled / seat-scoped-enum / agent-enum-pick / free-text), a type, an enum-set, and a required-when condition. Authority is enforced **at FILL** (a forbidden option is simply absent from your seat's form) rather than post-hoc by a linter. A field is enum/required **iff a mechanical consumer reads it** ("canonical-iff-consumed"). The form is **dynamic** — the required-set is a function of PHASE × CEREMONY_TIER. This dissolves most of relay-lint.py's prose machinery; the linter refactors into intra-relay **form-validation** + a cross-relay **lineage engine**. (Design intent: pillar ¶41–45, ¶47.)

## 1. AC1 — 4-bucket verdict: the frank form schema + field-ownership vs what the upstream protocol already encodes

**PRIMARY_BUCKET: still-open** — the *deliverable artifact* (a single declarative field·owner·type·required-when·enum-set schema with fill-time authority) does not exist; it must be designed. But it sits on a **large promote-and-formalize substrate**: the field set, enums, and required-when conditionals already exist implicitly in the upstream protocol, scattered across protocol prose + linter code. The honest read is "design a thin net-new layer over a big already-built base," recorded below so bookkeeping does not contradict the recommendation.

still-open: (net-new design, no existing artifact) — (a) the explicit **field-ownership model** (who/how each field is filled: system / seat-scoped-enum / agent-pick / free-text). the upstream protocol has **no concept of field ownership** — it lints *values* post-hoc (`enum_field` relay-lint.py:455-462; `report_field_error` :355-371) but never constrains *who or how* a field is filled. (d) **Dynamic required-set as a declared function** of PHASE × CEREMONY_TIER — today this is scattered across imperative linter branches (read-only→FINAL_GIT_STATUS_SHORT :927-934; downgrade→ESCALATION_SCAN ordering :893-925). (E1)

## 3. AC3 — Design recommendation: schema representation + render/validate

### 3a. Representation — one declarative schema, one row per field

```
field · owner · type · required-when · enum-set · consumer
```

- **owner ∈ {system, seat-scoped-enum, agent-enum-pick, free-text}** — the three locked field-ownership decisions (pillar ¶43): system = courier-filled (FROM, ROLE, DISPATCH_ID, PARENT, timestamps, computed `*_RESULT`s, the HUMAN_GATE floor, observed evidence); seat-scoped-enum = the form offers only options this seat may pick; agent-enum-pick = the judgment enums (verdicts, PRIMARY_BUCKET, CEREMONY_TIER, scan yes/no/unknown); free-text = bodies, reasons, justifications.
- **type ∈ {enum, address-list, id-ref, evidence-ref, bool, int, free-text, row-block}**.
- **required-when** = a declarative predicate over (PHASE, CEREMONY_TIER, other-field-values). Precedent: JSON-Schema `if/then/else` + `dependentRequired` and Camunda form-js conditional "required-if" FEEL expressions (web sweep, SUPPORTS). **Bound it** — keep it a fixed predicate vocabulary gates branch on, NOT Turing-complete (CodeAct finding, pillar ¶47: a required-when that executes arbitrary code regresses determinism).
- **enum-set** = the closed option set. For seat-scoped-enum the *offered* subset is a function `(seat × field) → allowed-options` (a field-level-permission matrix; precedent: Salesforce FLS, Dynamics/USPTO field-level-access patent — web sweep, SUPPORTS).
- **consumer** = which mechanical reader consumes the field — operationalizes **canonical-iff-consumed**: a field with no consumer is flagged at schema-design time (the boundary-contract no-consumer rule).

**Carrier recommendation:** JSON Schema core (it natively expresses enum, required, if/then/else, dependentRequired — web sweep SUPPORTS) **+ a thin frank extension vocabulary** (`x-owner`, `x-seat-scope`, `x-consumer`) for the two things JSON Schema does not carry: field ownership / seat-scoping, and the consumer annotation. **One file**; the tool renders the form from it, the courier validates against it, and the linter's surviving form-validation (§2b) *is* schema-conformance against it. "Tool / courier / linter all read one source" becomes literally true — the schema file is the source. (Open question Q1 weighs JSON-Schema+extensions vs a bespoke DSL.)

### 3b. Render — where fill-time authority lives

Given (seat, PHASE, CEREMONY_TIER) the tool computes the active field-set (required-when evaluated) and, per field, the owner-determined affordance:
- **system** fields: not shown — the courier fills them (FROM stamped from the channel; PARENT from the woken-on relay; evidence from the observe probe).
- **seat-scoped-enum** fields: shown as a pick-list of **only this seat's allowed options** — this is where "forbidden option absent" lives (`direct-override` / merge-grant simply not on a pair seat's form).
- **agent-enum-pick** fields: full enum.
- **free-text** fields: text.

Strongest concrete precedents that constrained generation beats post-hoc validation: **OpenAI Structured Outputs** (schema compiled to a grammar, invalid tokens masked at sample time → conformance *by construction*) and **Swarm/Agents-SDK handoffs** (the legal next-seats are exactly the tools present; a forbidden handoff is *absent from the tool list the model sees*). Both web-sweep SUPPORTS. The upstream protocol's post-hoc detection (token machinery, role/from tripwire) is the weaker pattern this replaces.

### 3c. Validate — the send-time gate (composes with m-3 observe-as-send-gate)

`send` runs two pre-flights and bounces naming which failed (pillar ¶45):
1. **form-conformance (structure):** courier system-fills system fields, then checks the submitted typed input conforms — required-set complete, enums in range, **seat-scope respected** (a submitted option outside the seat's allowed set is a *fill-time-authority violation*, not a lint warning).
2. **observe-gate (observable done-predicate):** m-3's probe fills the evidence fields from outside the lane; the passing observation binds atomically to the emitted, stamped relay.
Then the cross-relay lineage engine (§2c) runs over the store. This is the frank replacement for "lint the finished prose."

### 3d. Decouple reasoning from formatting (counter-evidence-driven constraint)

Named risk from the web sweep: the **"Format Tax" / "Let Me Speak Freely"** results show forcing a model to *reason inside* a rigid format degrades quality. Mitigation, and it is exactly what canonical-iff-consumed already prescribes: keep enums/required strictly on **consumed control-plane** fields; leave the judgment body a **genuinely free** free-text channel — the seat reasons in prose, then fills the form. Hold this line or the form re-grows the prose problem it dissolved.

## 4. AC4 — Boundary contract: the schema MUST express m-3 / m-4 / m-6 fields

Unifying principle: **m-2 owns the field SCHEMA SLOT (its owner / type / required-when / enum-set declaration); the sibling domain owns the MECHANISM that fills or consumes the slot.** The schema is the contract m-1 stores and m-3/m-4/m-6 consume (dispatch boundary contract).

| Consumer | Fields the schema must express | m-2 declares | Sibling owns |
|---|---|---|---|
| **m-3 observe/evidence** | ACTIONS_GIT_REF, FINAL_GIT_STATUS_SHORT (type evidence-ref, **owner=system**, bind: filled-by observe-gate); EVIDENCE_TARGET (agent-enum-pick E1–E4, intent); achieved-evidence (system, observe-fact); per-phase done-predicate hook (a required-when input) | the slot + system-ownership + the target>achieved auto-flag rule | the probe MECHANISM that fills them from outside the lane |
| **m-4 routing-record** | role+model-per-dispatch (planner-emitted, altitude-B); capability-priors (system/config); justified-deviation (free-text reason + a record-kind enum **reusing the DESIGN_RECORD_KIND shape**) | the routing-record fields + owners + the record-kind enum pattern | the routing POLICY that picks values + a later release's feedback loop |
| **m-6 human-gate/email** | HUMAN_GATE_REQUIRED (**owner=system, monotonic floor — agent may only RAISE**, lock-2); gate→email bucket (system-derived from TO/CC + verdict); Owner Decision Brief 7-field content sub-schema (agent-pick recommendation + enumerated choices) | the HUMAN_GATE field + monotonic-raise semantics + the email-projection fields + the ODB sub-schema slots | the email surface + scheduler park/wake that consume them |

The Owner Decision Brief sub-schema is real prior art worth porting (agent-scripts maintainer-orchestrator/SKILL.md:61-67 — 7 fields incl. recommendation + exact enumerated choices; the enumerated choices map cleanly to agent-enum-pick and cut operator load). (E1)

No-consumer action: any field with no mechanical consumer is flagged at schema-design time (canonical-iff-consumed). None of the above is writer-with-no-reader or reader-with-no-writer; all four consumer edges are named.

## 7. Risks / reject-or-narrow gates

- **Lineage engine is not form-preservable (GATE-1 §2d-1)** — survives as a separate cross-relay engine; routed, not a blocker. Strengthened to forgery-robust via system-filled PARENT (m-1 dependency).
- **Dispatch authority must not be lost in the token dissolve (GATE-1 §2d-2)** — preserve as seat-scoped + phase-scoped form field.
- **Format Tax** — over-constraining reasoning-bearing fields degrades quality; mitigate by holding canonical-iff-consumed strictly (free-text stays free).
- **Schema evolution/versioning** — the standing tax on any typed envelope; a parked lane resuming on an older form needs a compat contract (touches m-1 store + m-6 scheduler). Likely a record-kind-style version field. (Q2.)
- **Overflow channel** — every typed-message system relies on a free-text/metadata escape hatch; without a *designed, bounded, never-gate-input* one, "fill the form" either blocks legitimate unanticipated messages or the free-text body quietly re-becomes prose (re-growing the dissolved machinery). (Q3.)
- **Scope discipline** — m-2 must NOT design the observe MECHANISM (m-3), the FROM-stamp MECHANISM (m-1), the routing POLICY (m-4), or the email surface (m-6); only the schema slots + ownership.
