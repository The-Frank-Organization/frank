## 1. Four-bucket verdict

**still-open (the core build).** The frank routing/policy **primitive** — a routing decision that is *first-class, recorded, attributable, justifiable, and human-overridable* — is genuinely still-open. No surveyed system (internal or external) records a routing **governance decision**; all deliver at most observability (which/what model ran), never a governed *why* a human can inspect and override before it takes effect (§2). The build = (a) the **routing record** (record-kind `routing_decision`, a consumer of the locked m-2 FieldSpec), (b) the **declared capability-prior table** (the floor), (c) the **3-staged policy** (prior → justified deviation → outcome feedback in a later release), and (d) the thin **router API** that renders/validates/stamps the record and admits it to m-1's `parent_picker`.

**already-closed (do not rebuild).** Three load-bearing pieces already exist:
- *The carrier* — the record + forgery-robust stamp + lineage gate + `parent_picker` admission is already provided by the **locked c1 m-1/m-2 foundation**. The m-2 FieldSpec registry already reserves `router` in the `consumers` enum and `routing_ref` in `lineage_role` (form-schema design §4, :60-63), and c1 R2 already specified the separate seat-stamped routing relay + `parent_picker` admission. m-4 designs *against* this; it does not reopen it.
- *The selection/transport mechanism* — jcode's `MultiProvider` + failover and claude-code's per-task `model` enum override are working model-selection runtimes (§ jcode / claude-code below). These are **wire-at-Step-3** assets, not rebuilds.
- *The priors* — published (Fugu §4.2 learned peaks match GPT→math / Gemini→science; plus model cards / leaderboards). The prior table is **tabulated, not derived**.

**product-overlapped (record-then-drive, don't duplicate).** jcode `MultiProvider` (single-active-provider per session) and claude-code per-task model override overlap on the *selection mechanism* — but only at the runtime layer that is **Step-3** for us. The external predictive routers (RouteLLM/Hybrid-LLM/FrugalGPT/Zooter/…) and the bandit-feedback routers (C2MAB-V, PILOT) overlap on the *policy-engine* idea and even on *non-gradient outcome feedback* — but **none persists the decision or the update as an auditable artifact** (§2, honest qualification (b)). No duplication of the governance record exists to promote.

**recommended-next.** PROCEED-TO-DESIGN the routing-record schema (m-2 consumer) + capability-prior table + 3-staged policy, with: the **m-3↔m-4 evidenced-record/benchmark seam co-designed** in the `c2-*-coord` thread; the **m-5 archetype-ceiling seam dispositioned at lock** (surface, don't close); and the **Step-3 router-execution dependency routed to the orchestrator** (the record is writable on existing runtimes now; *executing* it needs our own runtime — AUDIT-FIRST GATE 1, §6). Benchmark outcome-feedback (a later release) is a **forward hook**, not Step-0 closure.

## 2. The implicit-routing gap (named) + how the routing record closes it

**Gap statement.** Across every surveyed system, a model/role is selected with **no recorded, justifiable governance decision**. The decision is either an out-of-band human act that never touches the protocol, an ephemeral runtime config mutation, or a learned-predictor scalar compared to a threshold — at most *logged* (observability: *which* model ran), never *recorded as a justified decision a human can audit and override before it takes effect* (governance).

Per surveyed system:
- **the stock protocol (ours, today):** zero model/routing/capability field anywhere in the relay schema; relay-lint enforces none; routing is an out-of-band human lane hand-assignment; the only recorded seat identity is `FROM:<owner>.<role>` (role membership, not model). The implicit gap is *total* — there is not even a logged choice. [E1 below]
- **jcode (closest prior art):** `MultiProvider` switches one active provider per session at runtime (`RwLock<ActiveProvider>`); spawned agents inherit the coordinator's model; cost metadata is display-only; failover is reactive; **no RoutingDecisionRecord / reason / justification** — only a usage ledger + debug logs. The gap = the governance record, not the selector.
- **claude-code:** a real per-task `model: z.enum(['sonnet','opus','haiku'])` override exists, but the persisted `.meta.json` records `agentType` (role) **only** — the resolved model lives solely in ephemeral telemetry, and **no "why" field exists** at any layer.
- **agent-scripts:** model choice is prompt-level policy (speed criterion); decisions are dated **prose** logs, not a machine-readable per-decision deviation artifact.
- **external prior art:** nine predictive routers route on a learned scalar over a global threshold (implicit); four commercial products (Martian/OpenRouter/NotDiamond/Unify) deliver dashboards/response-fields/session-ids (observability, post-hoc or caller-side); MoA aggregates rather than selects.

**How the routing record + justified deviation closes it.** Routing becomes a **first-class, seat-stamped, lineage-gated relay** (record-kind `routing_decision`) carrying the per-dispatch role+model assignments (altitude B), the **capability-prior snapshot consulted** (the floor), and a **`justified_deviation`** reason **required-when the planner declares a deviation**. Because it rides m-1's `submit()`, its `FROM` is the forgery-robust stamped router seat → the decision is **attributable**; because it lands in the append-only, lineage-walkable store → **auditable**; because `routing` is a `gate_category` (§J) that escalates to a human on `human_decision_required` → **overridable**. Model stays **payload** — never a gate input (R2 preserved, §3 below).

**This is a PORT, not an invention — and two honest qualifications (resolve toward evidence).** The "default-from-a-floor + justified override + recorded reason + human approval" discipline is a **mature governance primitive outside LLM routing**: federal **SR 11-7 → SR 26-2** model-risk override registers (reason code + narrative + approver + timestamp; the near-exact structural match), ISO 27001 / NIST POA&M exception registers, ADRs, ITIL CAB, MLOps approval gates. **None has been ported to per-task LLM model routing.** m-4's contribution is precisely that port. Two qualifications the DESIGN write-up must concede rather than overclaim:
- **(a) Nearest prior art exists — Routesplain (2511.09373) and Arch-Router (2506.16655), 2025** — concept-bottleneck / user-authored-policy routing that make the routing rationale interpretable and even human-intervenable. **Differentiator is not "we make routing interpretable"** (they partly do) — it is the *seat-stamped, persisted **deviation-against-a-declared-floor** audit artifact*, which neither has.
- **(b) Non-gradient outcome feedback already exists** — contextual/combinatorial-bandit routers (C2MAB-V 2405.16587; PILOT/LinUCB 2508.21141) update a routing policy online via closed-form statistical estimators, no backprop. **So the later-release outcome-feedback loop's novelty is NOT the non-gradient mechanism** (Fugu-reward-analog framing must be hedged) — it is that **every bandit router keeps its statistics as throwaway in-memory state; none persists decisions or updates as durable, replayable, auditable artifacts.** The later-release differentiator is auditability/persistence of the update, fed by m-3 observed evidence.

Net: each ingredient has partial prior art; the **assembled, governance-first whole — benchmark/model-card-seeded prior floor + planner override + recorded justified human-auditable deviation, fed by a non-gradient outcome loop whose decisions and updates are themselves durable audit artifacts — is unfilled.**

## 3. Design recommendation

### 3a. Router API surface (conductor function (4) "router") — three thin pieces
1. **Policy engine** — a pure, fill-time function `policy.suggest(task_tags) -> { role: model, prior_basis }` that reads the capability-prior table and supplies the **floor** the planner-seat form renders as a default.
2. **`routing_decision` record** — a seat-stamped relay the **planner / orchestrator-planner** submits (altitude B: planner emits role+model per dispatch). The conductor runs form-validation + the lineage gate, stamps `FROM` from the channel, accepts it, and **admits the accepted record into m-1's `parent_picker` candidate set** for the dispatch it routes (exactly the locked R2 seam).
3. **Dispatch reference** — the work/dispatch relay carries a `routing_ref` (the locked `lineage_role: routing_ref`) pointing at the accepted routing record — **provenance/bookkeeping only**. No `model_*` field enters the dispatch's authority/gate set.

**Step-1 vs Step-3 (rides existing runtimes now; executes later — no re-cut).** Step-1: the record is *written* for runtimes we do not drive — the human still launches the lane, but the decision + justification is now a stamped, auditable artifact ("automated operator-relay" increment). Step-3: the *same* record becomes *executable* — the conductor's own runtime reads the accepted `routing_decision` and spawns the seat with the chosen model. The schema does not change between steps; only the executor appears (§6, GATE 1).

### 3b. Capability-prior representation — a declared, versioned, snapshotted table
`capability_prior : map< (task_tag | domain), ranked_model_list + basis >`. Seeded from Fugu's published priors (GPT→math, Gemini→science/GPQA, Opus→SWE/debug) + model cards / leaderboards + ours. Design constraints:
- **Declared, not learned** — this is itself part of the contribution (no surveyed router ingests benchmarks/model-cards as an *overridable floor*). The per-row **`basis`** field (benchmark name / model-card claim / observed-outcome in a later release) is what makes it a *justifiable* floor rather than a magic constant.
- **Snapshotted into the record** (`capability_prior_snapshot`, system-filled, replay-complete) — **not** a live config ref. An immutable record cannot be backfilled; a live ref silently breaks later-release replay/feedback attribution. (Carry-forward of the c1 consumer-review sharpening.)
- **Config-sourced + operator-configurable** (like `gate_category` §J), versioned so the later-release loop attributes each outcome to the prior version in force.

### 3c. Routing-record schema (consumer of the locked m-2 FieldSpec §4)
Record-kind **`routing_decision`** — its **own** enum value-set, reusing the `DESIGN_RECORD_KIND` *shape*, **not** its values (`design-doc|audit-record|direct-override` is a design-review lineage field — confirmed at relay-lint.py:42; reusing its literals would mis-own the field). Fields, each a FieldSpec:
- `routing_record_kind` — enum (own set: `routing_decision`; reserved `routing_deviation` / `routing_update` for a later release) — agent_enum_pick within routing's set.
- `routing_assignments` — `row_array` of `{ role, model, prior_basis_ref, deviated:bool }`, **seat_scoped_enum** to planner / orchestrator-planner (altitude B; only those seats may emit).
- `capability_prior_snapshot` — `object`, `fill_constraints: computed_result` (system snapshot at decision time).
- `justified_deviation` — `free_text`, **`required_when: any(routing_assignments.deviated == true)`**.
- `outcome_feedback_ref` — `id_ref`, **null-reserved** (a later-release forward hook → links to the m-3 observed-outcome evidence the benchmark consumes). Shaped now, null until then.
- `consumers: [ router, lineage_engine, human_surface, observe_gate ]`; `lineage_role: routing_ref` on the referencing dispatch.

**R2-CRITICAL construction (the single sharpest design point — preserves "model is never a gate input").** The `required_when` predicate atom is the **plain agent-declared boolean `deviated`**, *not* a comparison of the model value against the snapshot. No `model_*` predicate ever enters the schema gate. The planner **declares** `deviated`; the conductor **observes** declared-vs-snapshot as m-3 evidence (`evidence_integrity`), flagging a mismatch — mirroring the monotonic `HUMAN_GATE` declare/observe pattern. The model value lives in `routing_assignments` purely as payload/provenance. This is what lets the routing record *record the model decision* while keeping the model out of every gate, satisfying R2 by construction. (This declared-vs-observed check is the concrete m-3 seam — §5.)

### 3d. The 3-staged policy mechanism
- **Stage 1 — capability-prior floor.** The policy engine suggests model-per-role from the snapshot table (a system-supplied default at fill time).
- **Stage 2 — justified deviation (ships at Step-1).** The planner may pick a different model → declares `deviated=true` → the form **requires** `justified_deviation`. Recorded, attributable, auditable, human-overridable.
- **Stage 3 — outcome-feedback (a later-release forward hook only).** The benchmark consumes m-3 observed outcomes (via `outcome_feedback_ref`) to update the prior-table version. Non-gradient (bandit/tally analog) — but per §2(b), the *differentiator is the persisted, auditable decision+update artifact*, not the non-gradient mechanism. Shaped day-one via the snapshot + ref fields so it bolts on without re-cutting the record or the gate.

## 4. Boundary contract — what m-4 exposes to consumers
- **→ m-3 (Observation & Evidence).** (i) The `routing_decision` record is a **possible evidenced record**: m-3's observe hook attaches observed evidence — the `deviated`-vs-snapshot check now; the observed task outcome later. (ii) The benchmark loop (a later release) **consumes m-3 observed evidence** keyed by `outcome_feedback_ref`. Boundary: the m-3 hook is **observer-only** (positive write-allowlist, per locked R3); **m-4 declares which routing fields are observed; m-3 owns how it observes.**
- **→ m-5 (Workflows & Archetypes).** m-5 owns the tag-space + **authority-ceiling-at-spawn**. The archetype sets the seat **roster + authority ceiling**; the router fills **model-per-seat within that ceiling** ("human picks the slot; the router fills models within it"). Archetype tags **parameterize the capability-prior lookup** (e.g. a research archetype → route the lead/synthesizer model per domain = the "don't fix the aggregator" upgrade). The locked `slot_in` reserved opaque atom (m-2) is m-5's tag handle; m-4's prior table may key on archetype tags. **Surface, don't close** (VP guardrail) — see §5.
- **→ m-6 (Human Surface & Scheduler).** `routing` is a **category-B (orchestrator-absorbed)** `gate_category` (§J) — the routing decision normally does **not** escalate to the human (model = payload); it escalates to **A** only on `human_decision_required` (a deviation the orchestrator will not absorb). m-4 exposes the routing `gate_category` + the **ODB content** (recommendation + enumerated model choices — validated by the agent-scripts ODB 7-field schema) for the rare A-escalation; m-6 owns the bucket mapping + email projection.

**No-consumer check:** every proposed field has a named downstream consumer (router / lineage_engine / human_surface / observe_gate; m-3 / m-5 / m-6). No orphaned primitive.

## 6. Audit-first gates
- **GATE 0 — duplicate/already-built.** Does jcode's `MultiProvider` already provide a router to promote/wire rather than rebuild? **Partially, and only at the runtime layer.** `MultiProvider` + `pick_next_fallback_route` are a usable selection/failover mechanism, but single-session (no per-seat matrix; spawned agents inherit the coordinator's model) and — decisively — **record no justifiable decision.** Disposition: **promote/wire the mechanism at Step-3; build only the governance-record layer on top now.** The gap is the record, not the selector.
- **GATE 1 — Step-1 ride vs Step-3 execution.** The routing record **can be written riding existing runtimes in Step-1** (the planner emits it; the human still launches the lane). **Executing** the record (the conductor spawns the seat with the chosen model) needs our own runtime → **route the execution dependency to the orchestrator as a Step-3 item** (per `ROADMAP.md`). Design the record + policy now; do not design the runtime.
