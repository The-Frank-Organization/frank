## 1. 4-BUCKET AUDIT VERDICT (acceptance criterion 1)

PRIMARY_BUCKET: still-open

still-open: The frank m-1 primitive — a **sole-writer stamping courier** that owns an append-only relay
store and derives `FROM` from the connection a relay arrived on — **exists nowhere** in the agentic dev team protocol or either
reference. All three ship *self-asserted* identity. The new work is the courier + the channel-stamp +
store-write isolation. (Evidence: §2, §3.)

already-closed: none **for the primitive itself** — but three concrete assets should be **promoted /
reused, not rebuilt** (duplicate-gate detail in §4):
- the agentic dev team protocol's store **on-disk format** (`<RELAY_ROOT>/<DISPATCH_ID>/<PHASE>-<ROLE>-<ts>.md` + append-only
  `INDEX.md`) and `relay-lint.py`'s truth-agnostic structure/lineage checks — reuse as the stored shape +
  the inline form-validation/lineage engine. (relay-lint.py:398-404, 555-575, 1104-1130; protocol.md:368-386)
- claude-code's **inbox-file + lockfile + poll-and-inject** projection pattern — reuse as the read/`project()`
  side. (teammateMailbox.ts:43-66,134-192; useInboxPoller.ts:107,810-858)
- jcode's `ClientConnectionInfo` **connection→session binding** (debug.rs:46-60) — this is the *exact datum
  to stamp from*; jcode already has it and **discards** it (taken as unused `_client_connections`,
  client_comm_message.rs:120). Promote the binding; delete the discard.

product-overlapped: the **external** standards we PORT (not rebuild) — SO_PEERCRED/SCM_CREDENTIALS, mTLS,
Kerberos channel-binding, and especially **SPIFFE/SPIRE** ("calling from a specific process *is* the proof
of identity") are the established forms of channel-stamped identity; CT/Merkle is the optional
tamper-evidence layer; "Right to History"/PunkGo (arXiv 2602.20214) is an adjacent *published cousin*
(CT + seL4 for agent action logs) to track and differentiate against, not adopt. (URLs in §6.)

recommended-next: **DESIGN the minimal primitive** — the `submit / project / mint_seat` store API with
`FROM := lookup(connection)` stamping and the two store-isolation invariants (I1/I2, §5) — wrapped around
the reused agentic-dev-team-protocol format + CC projection pattern. Defer the Merkle/tamper-evidence layer (the courier is the
TCB). Route two cross-cutting dependencies to the CTO/VP before lock (Step-1 transport-isolation choice;
identity≠authority boundary) — see §7.

## 2. THE THREE SELF-ASSERTED-IDENTITY GAPS, AND HOW CHANNEL-STAMPED FROM CLOSES EACH BY CONSTRUCTION (acceptance criterion 2)

**Common root cause (all three):** the field the system *trusts* and the field the sender *controls* are
the **same value**. This is the generalized "two-FROM" trap (email's envelope-from vs header-From; DMARC
exists only to force them to align — see §6.2). Channel-stamped FROM closes the class by **removing the
sender's ability to write the trusted field at all**: `FROM` leaves the payload and becomes
`FROM := lookup(connection)`, computed by the sole-writer courier from the channel the relay physically
arrived on.

### Gap A — agentic dev team protocol: agent-authored `FROM`
- Identity source: a plain-text `FROM:` line the author types into its own relay file; `relay-lint`
  regex-scrapes it verbatim (relay-lint.py:398-404, 498-519). The only identity check,
  `role_from_consistency_error()` (relay-lint.py:555-575), compares the author's `ROLE` to the author's
  **own** `FROM` suffix.
- Forgery: any agent with write access to the relay dir writes a *self-consistent* pair
  (`ROLE: Planner` / `FROM: m-1.planner`) and the check returns clean; every downstream gate (orchestrator-
  review :1104-1130, merge anti-self-auth :764-782, lineage walks) then consumes the forged `FROM`.
  Confusion-robust **only** — stated as intent (relay-lint.py:556-562; protocol.md:137).
- Closed by construction: the author can no longer type `FROM` — it is system-filled from the connection
  (export pillar :41 "system (courier-filled: FROM, ROLE, DISPATCH_ID, PARENT, timestamps…)"). The
  self-consistency check becomes moot because the field is no longer attacker-writable.

### Gap B — jcode: `assign_role` / self-asserted `from_session`
- Identity source: `CommMessage.from_session: String` carried in the wire body (wire.rs:377-390); the
  server trusts it through delivery (client_comm_message.rs:147,150,257-259,271-272) and **discards** the
  connection→session binding it already holds (`ClientConnectionInfo`, debug.rs:46-60, taken as unused
  `_client_connections`, client_comm_message.rs:120). `assign_role` writes an arbitrary role string
  (`member.role = role.clone()`, comm_control.rs:769) with a self-promotion escape hatch
  (comm_control.rs:703-730).
- Forgery: a client emits `CommMessage` with any `from_session`, or self-promotes to `coordinator` then
  stamps any role onto any seat.
- Closed by construction: `from_session := connection.session_id` (use the datum jcode discards); the
  agent-facing role self-assignment is removed — a seat's role is a property the conductor set at spawn,
  never a value the agent writes.

### Gap C — claude-code: self-written `from` + `'team-lead'` string check
- Identity source: each agent writes the **recipient's** inbox file directly with `from: getAgentName()`
  (SendMessageTool.ts:157-171; getAgentName from a `--agent-name` CLI arg, teammate.ts:98-102). Privilege
  is gated downstream by the literal `msg.from === 'team-lead'` (useInboxPoller.ts:162, 557).
- Forgery: any process with FS access writes `from:'team-lead'` + a forged `plan_approval_response` /
  `mode_set_request`; the victim's poller matches the string and exits plan mode / widens its permission
  mode. The advisory `proper-lockfile` (teammateMailbox.ts:165) serializes writers but authenticates none.
- Closed by construction: agents never write inboxes; they `submit()` to the sole-writer courier, which
  stamps `from` from the connection and **projects** into the recipient's inbox. A non-lead cannot emit
  `from:'team-lead'` because its connection is not the lead's. The string check is replaced by channel
  identity.

## 3. CURRENT-STATE FINDINGS (E1 evidence backing §1–§2)

- **The agentic dev team protocol is a coordination *protocol*, not a runtime — there is no courier to promote.** `relay-lint` is
  a read-only structure checker (relay-lint.py:1-9) that only `read_text()`s files; it never mediates
  writes. The protocol instructs *each agent* to write its own relay file (protocol.md:368, 378-382);
  `INDEX.md` is append-only **by request only** (protocol.md:386) and lint-exempt. The only host hook
  (`relay-lint-posttooluse.sh`) is **non-blocking and bypassable** via Bash/heredoc/rename. The maintainers
  name forged-FROM defense as **"designed, deferred"**: *"Truth-agnostic relay-lint cannot prove which
  process wrote a relay"* (tools/adapters/README.md:52-54). → the frank thesis is explicitly future work, not
  shipped.
- **jcode already holds the trustworthy datum and throws it away** (debug.rs:46-60 binds session↔connection;
  client_comm_message.rs:120 takes it as `_client_connections` and ignores it). This is the single
  highest-signal finding: the channel-stamp is not exotic — it is *using the binding the bus already has*.
- **claude-code's trust boundary is the OS filesystem, not the app** — every agent is a writer of every
  other agent's mailbox (SendMessageTool.ts:161,239,284,…); the lock is mutual-exclusion only. No sole
  writer.
- **Export design intent confirms the target** (pillar :31,:33,:35): conductor = thin trusted courier
  owning 6 things; m-1 owns (1) the append-only relay store and (2) the seat-stamper (TCB core + identity,
  fused), and *places* (3) the inline lint gate (pre-delivery). "seat-trust / model-agnostic — only the
  SEAT is authorized; the model is payload." Stamp `FROM` from "the connection the relay arrived on, never a
  lane-supplied field" ⇒ "forgery-robust SEAT identity by construction." Residual = "one-time channel→model
  misconfig (operator-owned), not per-message."

## 5. DESIGN RECOMMENDATION — the seed of the Step-1 interface sketch (acceptance criterion 3)

> Seed only. The locked DESIGN (Superpowers `brainstorming` with the operator) is a later, separately
> dispatched phase; this audit produces the recommendation and the open questions, not the lock.

**Answer to the dispatch's design question — the minimal store-plus-identity primitive is forgery-robust by
construction IFF two invariants hold:**

- **I1 (sole-writer / store isolation):** the store is writable *only* through the conductor process. Agents
  have no direct write path to the store dir (filesystem perms / separate uid).
- **I2 (channel isolation):** every write rides a connection the conductor maps to exactly one seat, and a
  seat cannot obtain another seat's connection credential.

Given I1+I2, `FROM := lookup(connection)` is unforgeable: an agent cannot write the trusted field (I1) and
cannot borrow another seat's channel (I2). Everything else (Merkle/CT, etc.) is optional hardening, not
required for the by-construction property.

**Relay-store API surface (the write/read/spawn triad):**
- `submit(seat_connection, relay_body) -> relay_id` — the **only** write path. The conductor:
  (a) `seat := lookup(seat_connection)` → stamp system fields `FROM`/`ROLE`; (b) compute lineage system
  fields (`DISPATCH_ID`/`PARENT`/timestamps/`*_RESULT`s); (c) run the **inline gate** (form-validation +
  m-3 observe) *pre-append* — "no clean observation, no relay leaves" (pillar :45); (d) append the relay
  file + `INDEX` row (sole writer); (e) project into addressee inboxes.
- `project(seat_connection) -> [relays addressed to caller]` — read/inbox-poll, scoped to the caller's
  stamped identity (you read only your own TO/CC). Reuses CC's poll-and-inject.
- `read(relay_id)` / store queries — for the cross-relay lineage engine (the refactored linter).
- `mint_seat(seat_address) -> connection_credential` — conductor-only, spawn-time; binds a new seat to a
  fresh connection credential and records `seat ↔ connection`. The agent never sees another seat's
  credential.

**Identity-stamp mechanism:** `FROM`/`ROLE` are never read from the payload; they are `lookup(connection)`.
On-disk shape unchanged from the agentic dev team protocol (human-readable per-relay markdown + `INDEX`), but the system fields are
courier-filled (pillar :41), so a relay file is a *projection of a stamped record*, not a hand-authored one.

**Isolation boundary + the Step-1→standalone non-re-cut path** (directly answers "rides existing runtimes in
Step 1, extends to standalone later without re-cutting"):
- Step 1 ("automated operator-relay", pillar :35): I1 = filesystem perms on the store dir (only the
  conductor's uid writes); I2 = a per-seat connection credential minted at `mint_seat` over an
  OS-isolated process/connection (e.g. a per-seat Unix-domain-socket / stdio pipe the conductor owns, or a
  minted bearer token carried on that connection).
- Standalone (later): the conductor becomes the runtime that spawns seats as child processes/containers;
  I2's attestation upgrades from minted-token to **kernel-attested SO_PEERCRED / mTLS / SPIFFE-SVID**.
- **Why no re-cut:** because *all* writes already go through `submit()` over a per-seat connection from day
  one, strengthening I2 is a strict swap of the *attestation backend* behind the same API — the store shape,
  the `submit/project/mint_seat` surface, and the stamp semantics are unchanged. This is the
  "build B so C extends the same bones" principle (pillar :17; roadmap :49-50) applied to the store.
  [Caveat: the exact phrase "rides existing runtimes in Step 1… don't re-cut" is **not verbatim** in the
  export — it states the Step-1→standalone trajectory (pillar :35) and the same-bones principle; the non-re-cut
  mapping to the store is my synthesis, offered for the DESIGN phase to confirm.]

## 6. EXTERNAL PRIOR-ART — what we PORT vs what is novel (E1 = URLs)

- 6.1 **Connection-derived, platform-attested identity** is the established form of our stamp:
  SO_PEERCRED/SCM_CREDENTIALS (kernel attests peer uid/pid; sender cannot forge)
  (https://www.man7.org/linux/man-pages/man7/unix.7.html); polkit/D-Bus authorize on caller's attested
  identity; **SPIFFE/SPIRE** is the closest match — "identity is *attested, not a secret*; calling from a
  specific process is itself the proof" (https://spiffe.io/docs/latest/spire-about/spire-concepts/). → our
  channel-stamp is an instance, not an invention. **Well-trodden.**
- 6.2 **The DMARC two-FROM trap** (port the lesson): SPF/DKIM authenticate the envelope/`d=`, not the
  *visible* From; DMARC exists to force alignment
  (https://dmarcly.com/blog/how-to-implement-dmarc-dkim-spf-to-stop-email-spoofing-phishing-the-definitive-guide).
  Lesson: forgery-robustness holds only if the identity we trust (channel-stamp) is the identity every
  downstream consumer reads. **Keep one FROM; never reintroduce a payload-supplied display FROM.**
- 6.3 **Object-capability "no ambient authority / unforgeable reference"** is the literal "by construction"
  argument (https://blog.acolyer.org/2016/02/16/capability-myths-demolished/). **Well-trodden.**
- 6.4 **Single-writer append-only WAL** (Kafka/WAL/event-sourcing) gives ordering+durability but **not**
  content/identity authentication — which is exactly why FROM must be stamped *at ingress from the channel*,
  before the sole writer appends (https://nurkiewicz.com/2020/07/kafka-design.html). **Tamper-evidence**
  (CT/Merkle, RFC 6962) is a **separate, optional** layer needed only to verify the store *against the
  courier itself* — defer, since the courier is our TCB (https://www.rfc-editor.org/rfc/rfc6962.html).
- 6.5 **Confused-deputy** (Hardy 1988): the courier *is* a deputy; stamping at the channel is the canonical
  anti-confused-deputy move — keep all authorization keyed to the stamp, never a payload field
  (https://www.scs.stanford.edu/nyu/04fa/sched/readings/confused.pdf).
- 6.6 **Multi-agent impersonation** is the immature frontier where our contribution sits: documented
  agent-impersonation / "Prompt Infection" threats (https://arxiv.org/pdf/2410.07283), agents over-trusting
  peer-supplied metadata, 2026-nascent standards (NIST AI Agent Standards; MCP/A2A "define how agents
  communicate, not who they are"). Closest published cousin: **"Right to History"/PunkGo**, a Rust kernel
  unifying CT + seL4 for tamper-evident agent logs (https://arxiv.org/abs/2602.20214).

**Novelty verdict:** the *mechanism* is well-trodden (peer-cred/SPIFFE + single-writer WAL + ocap); the
*contribution* is applying TCB-grade channel-stamped identity at the **agent-seat relay layer**, a domain
the field has not settled. Port the principles; cite the cousins; claim the application, not the primitive.

## 7. BOUNDARY CONTRACT — what m-1 must expose to consumers (acceptance criterion 4)

Writes: the relay-store API (`submit`/`project`/`read`/`mint_seat`) + the courier-stamped identity fields
(`FROM`, `ROLE`, `DISPATCH_ID`, `PARENT`, timestamps) that ride the append-only store.
Reads: the agentic dev team protocol's relay/identity handling; jcode + claude-code identity models; export design intent.
Target entity: the frank relay store + seat-stamper primitive (a design recommendation, not code).

Per-consumer surface (each has a named consumer — **no orphaned primitive**):
- **m-2 (Forms & Determinism):** the **system-filled field set** (courier-owned, not user-fillable) +
  the sole-writer store the form-validation/lineage engine reads + the **seat-scoped enum source** (a seat's
  stamped identity decides which authority options its form may offer — pillar :41). Proof target: E2 form
  rejects a relay whose claimed FROM ≠ stamped FROM.
- **m-3 (Observation & Evidence):** the **store-isolation boundary itself** — observe-from-outside-the-lane
  needs the *same* isolation the seat-stamper needs (pillar :43), so m-1 exposes "courier probes the lane
  from outside it" as a shared primitive; plus the `submit()` **pre-send gate hook point** where observe
  runs before append.
- **m-4 (Routing & Policy):** the stamped store as the **write target for routing records** (routing
  decision = a seat-gated on-disk record, pillar :35/:14); m-1 guarantees the routing record's FROM is the
  router seat's stamped identity, so dispatch authority is forgery-robust.
- **m-6 (Human Surface & Scheduler):** the **addressing graph (TO/CC) + seat-address space** — "inbox =
  projection of the addressing graph" (pillar :37); m-6's operator inbox + gate→email buckets are
  projections of m-1's stamped store/addressing.

No-consumer action: none triggered — every surface above maps to a named consumer.
Proof: E1 source cites throughout §2–§6 backing each gap and claim; consumer-validated interface locking is

## 8. AUDIT-FIRST GATES — reject/narrow + routed dependencies

- Gate 0 (duplicate/already-built): handled in §4 — promote-not-rebuild for three named assets; the
  primitive itself is genuinely still-open.
- Gate 1 (can it ride an existing runtime in Step 1?): **YES, conditionally.** I1 (store perms) and I2
  (per-seat connection) are both achievable on existing runtimes. **But** the by-construction strength is
  exactly as strong as the Step-1 channel isolation: a minted-token-over-OS-isolated-process binding is
  strong; the most manual "automated operator-relay" form degrades to **operator-attested** (the human
  operator vouches which seat a relay came from) — fine for a trusted operator, but not yet by-construction
  against a seat that can reach the conductor directly. This is a real cross-cutting dependency → routed to
  the orchestrator (§7 operator-judgment item 1). It does **not** block DESIGN; it shapes the Step-1
  transport choice.

## 9. OPERATOR-JUDGMENT ITEMS (for CTO/VP + operator)

1. **Step-1 transport choice** determines channel-isolation strength (minted-token-over-isolated-process =
   by-construction; pure human-operator-relay = operator-attested). The orchestrator/operator should pick
   the Step-1 transport with this tradeoff explicit. (Routes AUDIT-FIRST gate 1.)
2. **Tamper-evidence (Merkle/CT) is deferred as optional** — needed only to verify the store *against the
   courier itself*. Since the conductor is the TCB, recommend deferring to a later cycle; confirm we accept
   "trust the courier" for Step-1.
3. **identity ≠ authority split** — the stamp says *who*; *what a seat may do* is m-4/m-5 policy keyed to the
   stamp. Confirm m-1 owns identity + store only, not authorization decisions (boundary arbitration).
