## A-1 (F5) — Form-digest stability: the digest covers the STABLE schema surface; volatile candidates are digest-exempt by class

**Root cause (code-verified; r2 wording per the implementer's review sharpening):** `digestRenderedForm` (`render.go:169-189`) hashes the rendered form including conductor-supplied **volatile rendered affordances/dynamic fields**, with exemption existing only as an **ad-hoc per-field flag** — `parent_picker` alone sets `DigestExempt` (`render.go:65-73`), while other volatile affordances remain digest-covered (`seat_allowed_values` recipient sets rotate on every mint — the F15-compounds-F5 edge; dynamic defaults and floor-dependent options likewise). Any projection/fleet change touching a covered affordance rotates the digest → in-flight submits bounce `re-render`. On a busy store the honest retry path churns (F5) and feeds the F11 livelock. The gap is flag-vs-class: one field got the exemption; the *class* never did.

**The amendment — what the digest MEANS (sharpens locked §8.2, changes no mechanism vocabulary):** the form digest exists to catch **stale schemas** — a seat holding a rendered form from a superseded config/registry generation or a different (seat, phase, tier) — because the *authoritative* validation already re-checks every value in the critical section (locked §2.1/§8.2: render advisory, loop authoritative). It was never the digest's job to pin projection state; pinning it is what made advisory-render "safe but not live."

1. **Digest input = the stable schema surface only:** config digest (the §7 chain head) + seat pattern + phase + tier + the field *shapes* (ids, types, constraints, static enums). **Conductor-supplied volatile candidate sets (parent candidates, recipient sets, any projection-derived options) are digest-exempt by CLASS**, not by per-field flag — the render marks them `conductor_supplied_volatile` and the digest strips them structurally.
2. **Their correctness moves wholly to the authoritative check** (where it already lives): the picked value is validated against the **current committed state** at validate-time inside the critical section. The seat is never bounced for holding yesterday's *options* — only for picking something invalid *now* (and F3's parity fix below makes that bounce actionable).
3. **The bounded re-render contract (the fixture-able property):** a submit bounces `re-render` **iff the effective schema shape changed** — config/registry change (§7 record), seat/phase/tier mismatch — and **never because unrelated traffic committed**. Explicitly: N foreign accepts between render and submit ⇒ zero digest bounces (the F11-adjacent negative fixture).
4. **Rejected alternative — digest lease/TTL:** a time- or generation-window lease keeps the volatile state *in* the digest and adds a clock/generation to reason about; it narrows the race without removing it (a submit racing an accept inside the window still churns at the boundary) and it complicates recovery (leases are runtime state). Stripping volatility from the digest removes the race class. (A lease adds nothing once the digest is stable — recorded as rejected, not deferred.)
5. **Fork composability (the three-way seam):** if m-1's fork lands **conductor-computed PARENT**, the parent field leaves the form and F5's sharpest volatile source vanishes — A-1 still governs recipient sets and any future volatile options. If it lands a **widened candidate set**, the widened set is digest-exempt and checked current-state at the gate. If a **lineage lease/token**, the token is a field *value* the loop honors in the critical section — the digest still excludes the volatile candidate display. A-1 is invariant across all three branches.

## A-2 (F9) — Intake identity: content-hash dedupe means REPLAY, and ids come from a durable counter

**Root cause (code-verified):** `journal.Append` (`journal.go:78-83`) dedupes by `ContentHash` and returns the **existing** `IntakeID` — but the submit path then **re-executes the pipeline anyway**, committing a fresh outcome record against the same id (the archive's three distinct rejected records on `intake-000012`). And new ids are minted as `len(entries)+1`, which is collision-prone across any partial view (segment rotation is live since S2 — "path-conditional" is exactly what a length-derived id under segmentation produces). Locked §2.2 promised the jcode idempotency-replay donor; the build shipped the dedupe *without the replay*.

**The amendment — completes locked §2.2's own sentence:**
1. **Same content-hash + an existing outcome ⇒ REPLAY that outcome** — the seat receives the original typed outcome (same `relay_id`, same state, same detail), **nothing re-executes, nothing new commits**. This is the idempotent-client-submit-token seed made precise: the content hash IS the client token.
2. **Same content-hash + no outcome yet (still in FIFO/in flight) ⇒ return the same `intake_id` and DON'T re-enqueue** — the in-flight execution's outcome answers both submissions (the reply path may hold both reply channels or the retry polls the outcome by intake id).
3. **Fresh content ⇒ a fresh id from a durable monotonic counter** — persisted with the journal (the segment header carries the high-water mark; recovery restores it as `max(all segments) + 1`), **never derived from `len()`** of anything. Ids never repeat across segments, rotations, or recoveries.
4. **The restored invariant, stated for the fixture:** at all times, on any store: **every `intake_id` has AT MOST ONE outcome record, and every outcome record's `intake_id` is unique** — the §C4.1 1:1 anchor (atomic clear-on-pop, zero stale re-emission) made true at the id grain, not just the effect grain.
5. **Recovery interaction (unchanged by design, now unambiguous):** `intake − outcomes` re-enqueues at most one entry per id; the F9 fixture (5 enqueued / 2 outcomes / exactly 3 re-enqueued) gains a **duplicate-retry leg**: a content-hash retry storm across a crash yields exactly one outcome, replayed to every retry.

## A-3 (F15) — Live seat enrollment: mint becomes a loop mutation; the fleet-wide bounce dies

**Root cause (code-verified):** mint is an admin-time CLI path (`main.go:403+`) — enrolling a seat requires a conductor restart, dropping every channel and re-render-bouncing every in-flight form (observed twice in the dogfood run; compounds F5).

**The amendment — realizes what locked §8.1/§8.5 already says (mint_seat is conductor-internal; operator tooling ASKS the conductor):**
1. **Mint = an operator-channel submission committed through the loop:** a `record_kind: seat_mint` record (operator-seat-scoped — the m-2 row is theirs to shape; the Q2=(i)/config-change authorship precedent applies verbatim: an authority-bearing act on a live store rides the operator channel, never a side door). The **canonical mint record is the one pivot**; the socket endpoint creation + binding-table update are **derived work** (the S2 derived-work-completion mechanism — a committed mint record with no live endpoint is completed idempotently at recovery, keyed by the record).
2. **No restart, no fleet bounce:** existing channels never drop; in-flight forms never see a digest change (A-1 makes this true structurally — a new seat is projection-state, not schema-shape).
3. **Credential custody unchanged:** the credential is minted conductor-side and delivered only to the new seat's lane exactly as today (D5 residual stated; m-1's DI-2 realization untouched — this amendment moves *when* mint runs, not *how* credentials work; m-1 fidelity eyes on the record class ride the build slice).
4. **F11 class list grows:** `seat-mint` joins the mutation classes (one canonical record, one rename, crash at every boundary ⇒ committed-or-not; derived endpoint work completed at recovery) — the applicability map + crash legs gain the class, same as `config-change` did in s4.
5. **The admin-time CLI path is retired to genesis-time only** (first-boot seeding before any channel exists); on a live store it delegates to the operator-channel path or refuses with the documented choreography — never a silent restart-required.

## D-1 (F16) — in-slice fix, no lock touched: shim reconnects on first call

The shim holds the seat credential and the socket path for the lifetime of its host session (ratified F-GATE-3 boundary unchanged). On a failed call over a previously-live connection it attempts **one transparent reconnect + re-auth with the held credential, then retries the call once**; only if that fails does it surface the typed `shim:conductor-unreachable`. Re-auth is the locked §8.5 re-attach (same credential ⇒ same seat, no re-mint) — nothing new is claimed; the two-call UX simply stops being the seat's problem. Fixture: conductor restart mid-session ⇒ the seat's next single call succeeds.

## D-2 (F3) — in-slice fix, no lock touched: bounce-detail parity for every rejection class

The locked m-2 §4 contract already says every bounce carries the failing field/edge to the author; the re-render class delivers detail in the submit response while lineage-class rejections deliver it only via `read()` of the rejected record — an under-delivery of the locked contract, not a design question. Fix: the typed outcome **reply** carries the same formatter output (`Field:Class` / `Edge:Kind`, the I-PH drop-Reason valve unchanged) for **every** rejection class — one reply-shaping path, no per-class branches to drift again. Fixture: for each rejection class, the submit response's detail equals the rejected record's recorded detail byte-for-byte. *(F3's actionability is what makes A-1's "bounce only on real invalidity" honest — a seat bounced without in-band detail is F11 fuel.)*

## B-1 (addendum leg, operator-requested via `s6-design/DESIGN-orchestrator-planner-20260706-200259.md`) — the seat lifecycle {minted → bound → active}, the roster view, and out-of-order semantics

**Premise honored as dispatched:** this leg buys lifecycle visibility + ordering, not bounce-proofing (the observed boot bounces are A-1/branch-A classes, already killed). It formalizes the lifecycle A-3's `seat_mint` edge opened.

### B-1.1 The recording shape — TWO durable edges from existing records, ONE runtime state; zero new mutation classes

- **`minted` — durable, record-derived:** the seat exists ⟺ its A-3 `seat_mint` canonical record (or genesis-time seeding record) is committed. Already a pivot; nothing new.
- **`bound` — runtime channel state, deliberately NOT a record:** a seat is `bound` ⟺ its credential has an **open authenticated channel right now**. This is liveness, not history — and making it runtime is the *honest* shape: after a conductor restart every seat is truthfully unbound until it reconnects; recovery derives `minted`/`active` from records (store-is-truth) and opens with `bound = ∅`, which is exactly the world's real state. A reconnect is a re-`bound` and nothing else (consumes m-1's B-3 rule: never a re-boot). Recording binds-as-records was considered and rejected: it would make `connect` a loop mutation (a pivot per channel event — load + an F11 class bought for state that recovery would have to *distrust* anyway, since a recorded "bound" is stale the moment the process dies).
- **`active` — durable, DERIVED-ONLY by m-1's order rule (r5, per the master ruling `s6-design/RECONCILE-orchestrator-planner-20260706-211920.md`):** a seat is `active` ⟺ an **accepted governed submit stamped `FROM=<seat>` exists within its current mint-generation** (generation boundary = the committed `seat_mint` pivot in commit order; m-1 §F/§F.1 verbatim). No persisted marker, no new system field. The r4 registry-drift concern is **moot by construction**: m-1's rule is an ORDER fact over the append-only store, not a shape fact — no form predicate is ever re-run over history, so registry evolution cannot touch the derivation. Under B-1.2a's ordering, the first accepted submit IS the boot record by construction, and first-accepted-per-generation is **idempotent and exactly-once by construction** (better than a stamped-once discipline — there is nothing to stamp wrongly). The roster's activation record ref = that first accepted record's relay id. Same edge m-1's B-3 names; **one activation per mint-generation**; a re-mint starts a new generation requiring fresh activation.
- **The operator seat is always-active by construction** — its channel predates any boot choreography (genesis-grade; the same bootstrap exception as system-stamped genesis), stated so no fixture ever demands an operator boot record.
- **Recovery:** phase-3 runtime tables gain the lifecycle derivation (a records scan for `seat_mint` + accepted-boot per seat); the binding-table restore is unchanged; `bound` starts empty at phase 4. No new recovery machinery.

### B-1.2 Out-of-order semantics — RULED: the render mirror makes in-order the only visible path; the authoritative check refuses the rest, typed

A `minted`-but-not-`active` seat:
- **Render side (the affordance coup):** the ONLY form its `submit` schema renders is the **B-2 boot form** — in-order isn't enforced by punishment, it's the only thing the tool surface offers (fill-time authority applied to sequencing; §8.2's grain). Post-A-1 + B-2, that form is un-bounceable for a seat that fills what it sees.
- **B-1.2a — the pre-active ADMISSION predicate (r4, the review blocker closed):** the authoritative check accepts a pre-active candidate **iff it is exactly the rendered boot form**: the candidate's header set ⊆ {the ordinary system envelope} ∪ {the m-2 B-2 boot field set}, all boot-required fields present and valid, and **zero other fields — registered or not**. *(Integration allowlist, literal per the r4 approve's note: "system envelope" means exactly the conductor-stamped envelope fields — FROM/ROLE/relay_id/DISPATCH_ID/intake_id/timestamp/schema_version/delivery_state — plus SUBJECT and the m-2 boot set; NO authority-bearing or gate header — `gate_category`, `grant`, `HUMAN_GATE_REQUIRED`, or any standard-looking extra — is in the pre-active admission set; the build plan carries this list verbatim through the m-2 B-2 boot form and the m-7 admission check.)* *(carriage corrected by master per the VP review `…-215052` — the r4 marker row was withdrawn at r5; m-7 revert-window one relay.)* "Carries the boot fields" is NOT the predicate — the live validator iterates registry fields only (`validate.go:31-65`, review-verified), so mere-presence classification would let a boot-shaped SITREP smuggle extra non-boot or authority-bearing headers into activation. Exact-form match is the render mirror made authoritative: pre-active, what the form shows is *all* that admission accepts.
- **B-1.2b — TRANSIENT runtime classification (r5, restated per the master ruling; the r4 persisted marker is WITHDRAWN):** when B-1.2a passes, the conductor's accept-time classification of "this is the activating record" is a **transient in-process fact** (m-1 §F.1 sanctions exactly this: "a transient conductor classifier may compose") — it drives the immediate roster/lifecycle table update and nothing else. **Nothing is persisted beyond the ordinary accepted record**; recovery re-derives lifecycle by m-1's order rule during the existing phase-3 records scan (B-1.1). A persisted marker was withdrawn on the master ruling because it would duplicate derivable truth — a persisted copy that can disagree with its derivation is the "one envelope, many judges" defect class this cycle exists to kill. **GC probe (invited by the ruling, answered):** the derivation reads canonical records only (`seat_mint` pivots + accepted submits), and locked §10 (`…conductor-core-design.md:137`) never GC's canonical records in v3.0 — the derivation's inputs cannot be collected; **no failure case exists under the locked posture.** Boundary condition recorded: any future retention change that could touch accepted canonical records routes to m-1 by their own verbatim trigger ("persistence of activation in any store shape" / store-retention semantics) before the derivation would need a GC-boundary rule.
- **Authoritative refusal, typed at two grains:** any pre-active submit failing B-1.2a ⇒ **one terminal `rejected` record, class `boot-required`**, with D-2 parity detail enumerating each offending field as `<field>:non-boot-before-active` (the smuggle case gets actionable per-field detail, not a blanket bounce). Allow-and-mark is rejected: it mints "active-ish" seats with pre-activation work on the record — the exact two-truths ambiguity the lifecycle exists to kill. An **already-active** seat submitting a boot-shaped SITREP is ordinary traffic: no marker, no second activation edge.
- **Never gated:** `project`/`read` are lifecycle-independent — a minted seat MUST read its mailbox to find its boot dispatch (and reads grant nothing). And per the dispatch constraint, restated as a contract line: **activation grants no authority** — it sequences a seat's first submit; every authority question stays where it lives (fill-time seat-scope, gates, grants). The boot stage is an ordering, not a gate.

### B-1.3 The roster view — a derived projection behind a `project` parameter; never a fourth verb

- **Shape (r4 wording per review):** seat → {**`activation_state`** ∈ {minted, active} (the persisted, record-derived part) · **`bound_now`** (the separate runtime liveness bit) · role · minted-at · activation record ref · last-accepted-at} — a **derived projection** (rebuildable from records + runtime bound-set, like every projection; F10 wisdom applied: the roster is state, not traffic — no reject stream in it). The two-part naming makes the post-restart truth legible: an **active-but-disconnected** seat (`activation_state: active`, `bound_now: false`) is a normal state, not a contradiction.
- **Surface:** a parameter on the existing `project` verb (`project(view=roster)` grade), **seat-scoped to operator + orchestrator seats** through the same per-seat scoping machinery every other affordance uses. The seat surface stays exactly three verbs.
- **I-PH on the roster (named per the dispatch):** seat names, roles, states, relay ids, timestamps ONLY — no socket paths, no credential material, no store/config paths. The roster joins the P1 grep matrix as a first-class surface, and the cross-seat-metadata rule is deliberately relaxed HERE ONLY by scope (the roster is *for* the operator/orchestrator and shows all seats — that is its function, scoped to the seats whose function it is; a non-privileged seat's `project` never returns roster data).
