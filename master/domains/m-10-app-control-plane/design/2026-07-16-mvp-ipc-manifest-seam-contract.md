## §A — Topology frame (consumed, not re-decided)

Per amendment §2b (grill #1): **one app main process** hosts the **m-10 control plane as a module** — the run-manifest writer, the §C dispatch/ticket seam, the scheduler, the active-turn lease + `turn_epoch`, and the durable app-state store. **m-9 (worker)** and **m-8 (connector)** are **separate supervised child processes**. The conductor is its own isolated service; m-10 has **no conductor edge, no seat, no submit credential, no credential bytes — opaque references only** (amendment §1; packet `:28`).

**As-if-process-separated rule (binding on every seam below):** every m-10 interface in this contract is expressed as **framed messages over a byte channel + durable records** — never as shared memory, direct store access, or in-process pointer passing — so the Step-4 daemon split relocates endpoints without re-architecture. Where the MVP realizes a caller in-process (the seat broker, if m-7 places it in the app main process), the SAME message/record shapes apply over an in-process transport.

### A.1 Channel topology — m-10 is the connection BROKER, not a traffic hub
- **CTRL-W** — m-10 module ↔ m-9 worker process: lifecycle, turn admission, F59 ticket ops, wake forwarding, cancellation, health.
- **CTRL-C** — m-10 module ↔ m-8 connector process: lifecycle, epoch state supply, health. **No provider payload transits CTRL-C.**
- **DATA-P** — m-9 ↔ m-8 **direct**: `LLMRequest` + the normalized provider event stream (amendment §1 freeze→authorize→attach→send; packet `:27` "app IPC to m-10 + m-8"). **m-10 establishes this channel and is never on its path** — the control plane must not sit on the token-stream hot path, and the durable store + opaque credential references must not share a process-hop with provider payloads (mirrors the §2b/F57 accidental-disclosure posture).
- **Broker control channel (CI-1, consumes m-7 §2.10 at their final r8 @ `ab0ed428…`)** — the BROKER owns a dial-in control LISTENER (`broker-control.sock`, 0600, private runtime dir); **m-10 is the CLIENT**. Socketpair-inheritance does NOT apply to this channel — dial-in by construction so a replacement app-main can reach a surviving broker. m-10's client obligations: hold the exclusive `broker-control.lock` fcntl lock BEFORE the durable `control_generation` advance, then connect and present `{control_token, control_generation}`; the token is handed to the broker at SPAWN via ONE inherited pipe descriptor (broker reads one line, closes; rotation only at broker spawn; adoption presents the existing token). Epoch/lease state supply + the event/ack protocol ride this channel (§B.4/§B.5).

Establishment (CTRL-W, CTRL-C, DATA-P only): m-10 creates each as a `socketpair(AF_UNIX, SOCK_STREAM)` immediately before spawning the child; the child inherits **exactly its own endpoints** (CTRL + its DATA-P end), marked close-on-exec on the parent side and re-marked close-on-exec in the child before any tool subprocess is launched. Tool subprocesses inherit **no channel endpoint of any kind** (amendment §2 hardening; annex "no secret/control handle is INJECTED into bash"). All runtime sockets/files live in a **private runtime directory** (mode 0700), path supplied by the app main process.

**DATA-P lifecycle (generation-paired; the restart rule):** a DATA-P socketpair is bound to the **(worker generation, connector incarnation) PAIR** that inherited it. On the death/replacement of **either** owner, m-10 replaces **BOTH** under the new epoch with a fresh socketpair (co-restart); the prior in-flight attempt parks per §B.3 (never auto-resend, so nothing of value survives the dead pair anyway). Named cost, accepted for the MVP: a healthy peer is restarted on its partner's failure — rare, and connector re-spawn is cheap (credential reload from the secret store under m-8's contract). No descriptor-passing/rendezvous mechanism exists in the MVP; a private-listener DATA-P rendezvous is the named Step-4 split-time evolution (§I). m-10 never holds a DATA-P endpoint after spawn in any variant.

### A.2 Frame format (all channels; version-pinned)
```
frame := uint32_be(length) || payload_bytes        # length = len(payload_bytes); max = FRAME_MAX (compiled constant, MVP 4 MiB)
payload := canonical-JSON object:
  { "v": 1, "chan": "ctrl-w"|"ctrl-c"|"data-p"|"broker", "type": <message-type>,
    "seq": <canonical-decimal-uint64 STRING, sender-monotonic per channel>,
    "re": <canonical-decimal-uint64 STRING | absent — the seq of the request this frame replies to; REQUIRED on every reply-class message>,
    "run_id": <string|absent>, "turn_epoch": <canonical-decimal-uint64 STRING | absent>, "body": { … } }
# canonical-decimal-uint64 STRING = the §A.2 counter rule below: grammar ^(0|[1-9][0-9]*)$, value < 2^64, numeric decoded comparison.
# NO trust-bearing counter is ever a JSON number, here or in any message-body example this contract governs.
```
- **Canonical JSON = RFC 8785 (JCS)** — the single canonical encoding for every digested or compared byte sequence in this contract (frames need not be re-canonicalized on read; digests below always are).
- **Trust-bearing counters are canonical decimal STRINGS, not JSON numbers (R4):** JCS interoperable integers cap at 2^53−1 (RFC 8785 §3.2.2.3), which cannot carry the declared `uint64` domain exactly. Every counter that gates, fences, keys, or orders — `turn_epoch`, `seq`, `re`, `state_seq`, `control_generation`, `event_seq`, `op_seq`, and every transition/operation identity component — is encoded as a string matching the pinned grammar `^(0|[1-9][0-9]*)$` (base-10, no sign, no leading zeros, value < 2^64; violation ⇒ malformed frame). Comparison is numeric over the decoded value. This rule applies wherever these counters cross JSON: frames, the broker feed, store-adjacent exports.
- Unknown `type` ⇒ reject-and-record (`FAULT_UNKNOWN_MESSAGE`), never silent drop. Unknown **fields** inside a known type: the default is ignore (additive evolution), **scoped per message family** — a family declared CLOSED by its owner is rejected on unknown fields. The broker event/ack family is CLOSED (m-7 r6 §2.11: "unknown fields ⇒ m-10 rejects the frame"); CTRL-W/CTRL-C families default additive unless a consumer confirmation pins otherwise.
- `seq` is per-sender, per-channel, strictly monotonic — gaps are diagnostic evidence, not protocol errors. `re` correlates replies to requests (`ticket_granted.re = authorize_tool_call.seq`); a reply-class frame without `re` is malformed (`FAULT_UNKNOWN_MESSAGE` disposition).
- Oversized frame ⇒ channel fault ⇒ supervision disposition (§B.3). DATA-P chunking bounds are m-8/m-9's to design within `FRAME_MAX`.

### A.3 Backpressure (owned here; honest and minimal)
- Every channel has a **bounded send queue** (compiled constant depth). Writers **block up to `SEND_DEADLINE`**; a full-past-deadline CTRL channel is a **channel fault** → supervision disposition (§B.3). No unbounded buffering, no silent drop on CTRL/DATA channels.
- The **single exception**: wake/advisory messages (§E) are droppable at pressure — push is best-effort + advisory by ratified contract (amendment §6/F61); a dropped wake is recovered by durable rediscovery, never by queue growth.
- DATA-P flow control between m-9 and m-8 (stream chunk pacing) is designed by those owners **within** this frame + bounded-queue envelope; my contract pins only: bounded, blocking, fault-on-deadline, no drop.

### B.2 The two lease invariants (distinct; both m-10-owned; durable in `leases`)
1. **One-active-worker lease (per run):** at most one worker **generation** holds the run's lease at any instant. A replacement generation acquires the lease only after the prior generation is **proven terminal** (reaped) or the operator disposes of it explicitly — the packet §3 fail-closed rule preserved; **never automatic provider resend**.
2. **Active-turn lease (per run):** at most one turn is admitted/in-flight per run at any instant (MVP: one run, one worker, one turn). Turn admission (`turn_open`) is granted only to the current lease-holding generation at the current epoch.
- **The attach-acquisition gate (D-2, R16-F1 — observed capability acquisition, not verifier readiness):** the worker reports its broker-attach outcome on CTRL-W as **`attach_result{generation_id, turn_epoch, result}`** — `result` carries **m-7's producer tokens BYTE-EXACT** (their current D-3 set: `attach-ok` · `broker:attach-suspended` · `broker:attach-tuple-mismatch`; no m-10 wrapper renaming). **First-turn admission gates on m-10's RECEIPT of the `attach-ok` report** (emitted by the worker ONLY after it has received the broker's attach-ok and holds its connection-scoped capability) — never on the broker feed merely being installed (installed state proves the verifier is ready; only the worker's report proves acquisition). **`attach_result.result` is CLOSED over exactly the three pair-approved m-7 r11 tokens (R18-F2; bound @ `9331ea88…`, approve `…-195335` — PREPARING is a cause of the suspended result, not a new token):** `attach-ok` ⇒ acquired (admission unblocks) · `broker:attach-suspended` ⇒ bounded hold/retry inside `ATTACH_DEADLINE` · `broker:attach-tuple-mismatch` ⇒ **immediate FAILED disposition for the generation, no retry**; missing/wedged (no report) ⇒ the `ATTACH_DEADLINE` supervision disposition; **an unknown or malformed `result` value is a protocol/channel fault ⇒ the existing fail-closed supervision disposition** (never guessed into a class). **Any future producer-result addition is an interface AMENDMENT with fresh consumer review — never an automatically classified member.** Fixtures at rebind: the three result legs + missing-result deadline + unknown-result fault. Reachability: emission = the worker's attach path; consumption = this admission gate.

rejection = **`turn_reject{run_id, turn_id, reason ∈ {stale_epoch, unknown_turn, conflicting_report}}`** (the ONE closed set — `conflicting_report` is a member, R19-F2; stale epoch per the high-water rule). **`turn_cancel_ack` durably records the cancellation/partial fact and does NOT terminalize the turn or release the lease**; ### B.4 `turn_epoch` — issue, increment, distribution, rejection (F64-integrated)
- **Scope + storage:** per `run_id`; a strictly monotonic `uint64` in `epochs`, persisted **before** any use of the new value (durable-then-visible). **Durable representation (R3-F2):** SQLite INTEGER is signed-64 and coerces values above 2^63−1 to REAL (distinct upper-domain identities collapse) — so every persisted trust-bearing counter (`turn_epoch`, `state_seq`, `control_generation`, `event_seq`, `op_seq`, transition/operation identity components) is stored as **fixed-width 20-digit zero-padded decimal TEXT** with schema constraint `CHECK(length(col)=20 AND col NOT GLOB '*[^0-9]*' AND col <= '18446744073709551615')` — the upper bound is valid lexicographically because equal-width decimal ordering equals numeric ordering (R4-F2: length+digits alone admits out-of-domain values), and the same full-domain bound is validated in code on **every insert and update**, not only local increments. `ORDER BY`/`MAX` recovery scans stay exact. **Increment ownership, exact:** the transition applier (§F chokepoint) is the sole increment site **for the m-10-OWNED counters** (`turn_epoch`, `state_seq`, `control_generation`): parse → bound-check → add one → re-pad; **increment at 2^64−1 fails closed** (park, operator disposition — never wrap, never truncate). **Broker-owned inbound counters** (`event_seq`, `op_seq`, and transition/operation identity components) are **validate-and-store-only** at m-10 — their increment and exhaustion behavior is m-7's contract. Wire form (§A.2 unpadded string) ↔ store form (padded) convert only at the store boundary; counters cross JSON **only** as the §A.2 canonical decimal string.
- **Issue/increment rule (R3-F1: ONE trigger, revocation-first):** the epoch becomes current in **exactly one durable transaction, of exactly two kinds**: (i) **run admission** mints the run's first epoch (E=1, no predecessor); (ii) **generation RETIREMENT** — the decision that the active generation is failed/replaced — mints E+1. **Lease grant BINDS a generation to the already-current epoch and never advances it.** A replacement candidate that washes out pre-lease does not re-mint (revocation already happened; the candidate never had authority); each retirement mints exactly once. Epochs never decrease, never reuse, never skip persistence. **The invariant is "RETIREMENT ⇒ new epoch"** (plus run admission for E=1) — a new generation does not per se imply a mint (wash-out retries share the epoch), and never "new turn ⇒ new epoch".

### B.5 m-10's half of the epoch-transition handshake + the broker recording protocol (consumes m-7 §2.5/§2.10/§2.11 at their final r8 @ `ab0ed428…`; the CI-3 deltas)

4. **CROSSERS_DURABLE:** commit one `crossing-pending` row per frozen operation, keyed `{epoch_transition_id, operation_id}`, in ONE transaction that also advances the ledger row to `CROSSERS_DURABLE`; then **ack** — only that ack lets the broker INSTALL E+1 and lift the barrier.
5. **Completions:** apply `cross_epoch_completion` updates to the keyed rows (`completed | completed-before-install | rejected`); commit durably **before** the broker releases a response-coupled payload.
6. **Recovery (by transition ID, never inference):** on control (re)establishment, answer the broker's ledger query for the named `epoch_transition_id` — **committed** (crossing rows exist) ⇒ resume the SAME transition (re-ack the exact committed set); **not committed** ⇒ durably ABORT: one transaction resolving EVERY row of that ID (`completed-before-install` / terminal `aborted-attempt`), and only after the old ID is terminal propose a **fresh** ID for the still-current E+1. **Broker loss** ⇒ resolve that transition's rows `unknown-outcome` + durable abort (the §B.3 park discipline; never silent replay). An aborted attempt never re-authorizes E — epoch authority and transition-attempt fate are separate.
7. **Event recording (CI-3):** the broker keeps no durable state; m-10's store is the writer for the CLOSED broker event family (§A.2) — rows keyed `UNIQUE(broker_instance_nonce, event_seq)`, ack `broker_event_ack{broker_instance_nonce, event_seq}` **after** durable commit, duplicate delivery of a committed key returns the SAME ack. The event-type census, required fields, and delivery classes are m-7 r6 §2.11's (consumed, not restated); counters cross as canonical decimal strings (§A.2).
7a. **`INSTALLED` classification (R9-F1 — the durable fact, named):** m-10's ledger row advances to `INSTALLED` only upon **durably committing the broker's `epoch_installed{epoch_transition_id, …}` event row** (CI-3 keyed, dedup-idempotent). Because m-7 permits bounded loss of uncoupled events, a lost `epoch_installed` leaves the ledger legitimately at `CROSSERS_DURABLE` — and that is safe by construction: recovery resumes the SAME transition, re-delivers the ack for the exact committed frozen set, and the broker's install is idempotent (m-7 §2.5). The ledger therefore never claims `INSTALLED` from an unrecorded event, and never needs to.
8. **Replacement sequencing hook:** the frozen crossing set names the exact in-flight operations; whether to drain them before granting the new generation its capability is m-10 lifecycle policy (MVP default: do not wait — the fence + park discipline already covers them).

### D.1 The ticket (durable, in `tool_authorizations`)

`canonical_args_digest` is computed by m-9 over the **complete, assembled, validated, thereafter-immutable** args object (streamed fragments stay INERT until assembly — amendment §4) and re-derived/verified by m-9 at execution; m-10 stores and matches it, never interprets args.

### D.2 Issue (m-9 → m-10 `authorize_tool_call` on CTRL-W)
**One total, ordered decision procedure (R30, superseding the r29 single-clause form; F80's family retained): first match selects exactly ONE typed result; every rejection reply is reply-class + `re`-correlated; commit-before-reply on every row-writing path.** The rejection family for the lifecycle checks is **`authorize_reject{tool_call_id, reason}`** with the CLOSED reason set **`{run_not_admitted, turn_inactive, lease_invalid, turn_budget_exhausted}`**; `STALE_EPOCH`, `DENIED_ABOVE_SET`, `DUPLICATE_REQUEST`, and `IDENTITY_MISMATCH` remain their own established typed rejections.

**(0) Replay governs FIRST (R30-F2)** — precedence over every mutable-state check, *including stale-epoch* (the same equivalent-duplicate-over-stale precedence the §B.2 D-5 table pins at branch (3)). If a row exists at `(run_id, turn_id, tool_call_id)`: the **replay-identity predicate** compares the request's `{canonical_tool_name, canonical_args_digest, turn_epoch}` to the STORED triple — the same invocation identity §D.3 matches at consume. **Identity match ⇒ the reply is derived SOLELY from the stored row** by this closed mapping, with **no write, no state change, no supervision effect** — deterministic after any turn/lease/epoch change and after the commit-then-crash-before-reply window: `ISSUED` ⇒ the same `ticket_granted{ticket_id}` (lost-reply re-send) · `VOID` with `void_reason ∈ {run_not_admitted, turn_inactive, lease_invalid}` ⇒ the same `authorize_reject{reason}` · `VOID/denied_above_set` ⇒ `DENIED_ABOVE_SET` · `VOID/expired` ⇒ `authorize_reject{turn_inactive}` (no `VOID/stale` mapping exists — stale requests never write, §D.2 (2), so the mapping is total over the five-member domain) (total because expiry commits only at turn end, epoch mint, or crash recovery — in every case the named turn is durably non-active, and turn ids are never reused) · `CONSUMED | OUTCOME_RECORDED | UNKNOWN_TOOL_OUTCOME` ⇒ `DUPLICATE_REQUEST`. **Identity mismatch ⇒ `IDENTITY_MISMATCH`** — the issue-side twin of §D.3's: a same-key, different-invocation ask; no write, no row mutation, no supervision.

Fresh key ⇒ the ordered checks, all fail-closed, each failure selecting exactly one classification (overlapping predicate failures are resolved by ORDER — R30-F3):
1. **The named run exists durably in `runs` (R31-F1 — the existence cut precedes the fence because there is no fence to consult)** — unknown `run_id` ⇒ `authorize_reject{run_not_admitted}`, **row-less and counter-neutral**: no `epochs` row exists for an unknown run, so "current vs stale" has no comparator input and **no epoch is ever invented to compare**; fence-first behavior for KNOWN runs is unweakened — this branch fires only when the fence itself is undefined.
2. **`turn_epoch` current for the run** — stale ⇒ `STALE_EPOCH`, **row-less and counter-neutral (R31-F2)**: ZERO durable mutation, matching the contract's uniform stale posture (§B.1 `attempt_open_reject{stale_epoch}` no-row/no-charge · the D-5 stale-sender zero-mutation branch · §B.4's reject-stale-on-every-CTRL-W-operation rule · the §G stale-workers-fenced assertion). A stale/superseded sender can never create, mutate, or charge authorization state — historical or current — and because every row-writing classification sits BELOW this fence, **every committed row is current-epoch by construction** (the "turn exists" predicate alone was insufficient; this ordering is what closes it).
3. **Run admitted + non-terminal** — else ⇒ `authorize_reject{run_not_admitted}` (reachable: operator cancel/run-terminal racing an in-flight call).
4. **The named turn IS the currently admitted active turn** — else ⇒ `authorize_reject{turn_inactive}`; *inactive* is defined totally: terminal, `INTERRUPTED`, cancelled, **or an unknown turn id** (reachable: a call straggling past its own `turn_terminal`, or a confused peer naming a turn m-10 never admitted).
5. **The sender's generation holds the run's valid worker + active-turn lease** — else ⇒ `authorize_reject{lease_invalid}` **+ the §B.1 internal-invariant-fault disposition, ATOMICALLY (R30-F3 + R31-F3): ONE §F chokepoint transaction commits BOTH the VOID row (`void_reason = lease_invalid`) AND the complete retirement-transaction effects** (generation FAILED→retirement, lease released by retirement, E+1 minted, turn `INTERRUPTED`, the §B.4 state-sensitive row parking) — **the reply is sent only after that single commit; the row and the retirement effects cannot exist separately.** **At-ceiling form (R32-F1 — the invariant fault is never masked by the row bound):** when the turn's counter is at the §2a ceiling, the SAME atomic transaction commits the complete retirement effects and **omits only the VOID row insert**; the reply is still `authorize_reject{lease_invalid}` after the commit. Retirement occurs **exactly once** on either form — the retirement transaction is keyed by `(run_id, retiring generation_id)` with the committed-once guard (§B.3 matrix (b)), and a post-retirement re-ask never reaches (5): the sender is stale at (2) (E+1 minted) ⇒ row-less `STALE_EPOCH` — deterministic without any replay row. Crash cuts, both covered on both forms: crash BEFORE the transaction ⇒ nothing durable, and the re-ask deterministically reclassifies over unchanged state (reaching (5) again ⇒ the transaction runs); crash AFTER commit, before the reply ⇒ the below-ceiling form replays (0) the stored `authorize_reject{lease_invalid}`, the at-ceiling form reclassifies to row-less `STALE_EPOCH` at (2), and recovery proceeds via the §B.3 matrix branch (b) — **replay's no-supervision rule is SAFE by the atomicity invariant: a `VOID/lease_invalid` row existing at all proves retirement committed with it.** Rationale: with (2)–(4) established, an invalid lease is **invariant-impossible** under §B.2 — both lease releases travel only inside the epoch-mint or turn-terminal transactions, which respectively make the sender stale at (2) or the turn inactive at (4) — so reaching this branch is evidence of store/lifecycle divergence (the current-generation-conflict class of the D-5 table), never an ordinary race.

### D.3 Consume (m-9 → m-10 `consume_ticket`; exactly-once, atomic)

The comparison is therefore the CURRENT invocation, presented by an AUTHENTICATED CURRENT sender, against the STORED ticket — the ratified mutated-args negative AND the ratified stale-worker-consume negative are both decided by construction. One store transaction — **the success predicate requires ALL of:** stored-ticket epoch = presented epoch = durable current epoch · the channel's authenticated generation is the run's current lease-holder · `state=ISSUED` · name/digest match:
```
UPDATE tool_authorizations SET state=CONSUMED, consumed_at=now
 WHERE ticket_id=<wire> AND state=ISSUED
   AND turn_epoch=<wire presented> AND turn_epoch=<m-10 durable current epoch>
   AND <channel-authenticated generation holds the run's current lease>
```

- **(b) `state ≠ ISSUED` ⇒ `DUPLICATE_CONSUME`** (the one-shot is spent — the primary durable fact once the sender is proven current; **the stale-TICKET case lands here by construction**: an old-epoch ticket was transitioned `VOID/expired` atomically at the mint (§D.4), so a current sender naming it finds `state ≠ ISSUED` — the ticket-row epoch conjunct is belt-and-suspenders, never the classifier).
- **(c) name/args-digest mismatch ⇒ `IDENTITY_MISMATCH`** (the row REMAINS ISSUED — a mismatched ask consumes nothing and mutates nothing; the still-live ticket may yet be consumed with the true identity).

Overlaps by the order: stale-sender + spent ⇒ `STALE_EPOCH`; stale-sender + mismatch ⇒ `STALE_EPOCH`; all three ⇒ `STALE_EPOCH`; spent + mismatch (current sender) ⇒ `DUPLICATE_CONSUME`. **No partial path: consume without full identity match does not exist.** **The post-consume mutation guard is SPLIT, honestly (R33-F82):** mutation after authorize but before consume is MINE — the wire-vs-row match above rejects `IDENTITY_MISMATCH`; mutation after `consume_ok` but before invocation is **m-9's executor re-derivation half** (their §3.2 re-check against the same stored identity semantics) — my contract's half of that cut is the stored comparand plus honest §D.4 outcome recording of whatever their re-check reports. Fixtures (each asserting **reply-or-fault** + row state + execution count + supervision disposition): identity match at consume (one row, `consume_ok`, one execution) · identity mismatch at consume (row stays ISSUED, zero execution) · **a stale sender consuming its own historical ticket (zero executions, zero row mutations, `STALE_EPOCH`)** · **a stale sender naming a CURRENT ticket with matching identity (zero executions, zero row mutations, `STALE_EPOCH` — the R34-F1 negative)** · stale+spent overlap · stale+mismatch overlap · the all-three overlap · a current sender naming an expired old-epoch ticket (⇒ `DUPLICATE_CONSUME` via the VOID-at-mint construction) · mutation after authorize before consume · mutation after consume before invocation (the split cut — jointly asserted, each seat owning its half) · unknown `ticket_id` (**NO reply frame** + the exact §B.3 fault/supervision effects, zero row mutation) · presented-epoch-above-current (**NO reply frame** + the same fault effects, authority never advanced).

### D.4 Crash windows (§7 UNKNOWN/PARTIAL rule)
- **ISSUED, never consumed:** the ticket **dies with its turn/epoch** — on turn end, epoch increment, or crash recovery it transitions VOID **with `void_reason = expired` (R30-F1)**. A new attempt requires a **new ticket** (new authorization, same checks); a re-ask at the dead key replays per §D.2 (0) as `authorize_reject{turn_inactive}`.
- **CONSUMED, no recorded outcome** (crash between consume and `record_tool_outcome`): the ticket parks **`UNKNOWN_TOOL_OUTCOME`**; the tool call row parks likewise; **never silent replay** — a fresh attempt is a new ticket under the new epoch, and the parked row remains as the honest record (annex "crash outcomes stay honest": the two windows — pre-consume, post-consume/pre-outcome — are the tested negatives).
- **The outcome record (R35+R36 — the closed wire contract; m-9's R16-F1 requirement, the shape authored here as owner):** `record_tool_outcome{ticket_id, turn_epoch, outcome, <the outcome-discriminated member>}` (m-9 → m-10, **one-way** — no reply frame exists on any branch, the §B.1 one-way-consumer discipline) closes the loop ⇒ the ticket state `OUTCOME_RECORDED`. **The `outcome` WIRE domain is CLOSED at exactly two members** — `OUTCOME_RECORDED` is a ticket STATE and `UNKNOWN_TOOL_OUTCOME` is a crash-window STATE reached only by m-10's own recovery/parking; neither is ever a wire value:
  - **`executed`** — the invocation occurred and returned (the tool's own success/failure is result content in m-9's turn state, not lifecycle state). Carries **`invocation_identity`** = the ACTUAL invoked triple `{canonical_tool_name, canonical_args_digest, turn_epoch}`; **validity condition:** it must equal the consumed ticket's stored identity — a mismatched `executed` claims an effect under an identity never authorized, which is peer-state divergence ⇒ the record is REFUSED (no state change) + the §A.2/§B.3 protocol/channel-fault disposition. `tool_calls` terminal: **`EXECUTED`**.
  - **`not_invoked_integrity_fault`** — the split-guard's m-9 half (§D.3): the executor's independent recompute caught a post-consume mutation BEFORE invocation — the ticket is CONSUMED, **zero invocation occurred, and no-effect is DEFINITE** (honestly DISTINCT from `UNKNOWN_TOOL_OUTCOME`, where a crash left the effect unknowable; conflating them would park a certainty as indeterminacy — the accounting-lie class `rejected_local` exists to prevent). **`invocation_identity` is ABSENT — a zero-invocation record never fabricates an invocation**; the frame instead carries the distinctly-labeled evidence pair **`integrity_evidence{expected_identity, observed_identity}`** (expected = the consumed ticket's stored triple; observed = the executor's recomputed triple; ids + digests only, never payload) — **the mismatch stays visible in the durable record, not erased**. `tool_calls` terminal: **`NOT_INVOKED_INTEGRITY_FAULT`** — a DEFINITE-no-effect terminal, never parked UNKNOWN; the evidence pair persists on the row.
  **The frame + carriage (R36-F1 — the §B.4 F59 rule holds here exactly as at consume):** `record_tool_outcome{ticket_id, turn_epoch, outcome, <the outcome-discriminated member>}` — presented `turn_epoch` from the authenticated CTRL-W request · the sender's generation/run association from the private channel's `assign`-bound identity · the durable current epoch from m-10's own state: the same three non-substitutable authorities as §D.3. **The two frame shapes are CLOSED and discriminated (R36-F2):** `executed` REQUIRES `invocation_identity` and FORBIDS `integrity_evidence`; `not_invoked_integrity_fault` FORBIDS `invocation_identity` and REQUIRES the complete labeled pair — any missing, forbidden, or malformed conditional member is a shape violation at (0) below. **Validation predicates, checked BEFORE the atomic commit (R36-F2 — the owner checks the evidence it persists; a row must never claim a mismatch nobody verified):** for `executed`: `invocation_identity` == the consumed ticket's stored triple; for `not_invoked_integrity_fault`: `expected_identity` == the consumed ticket's stored triple AND `observed_identity` schema-valid AND `observed_identity` ≠ `expected_identity` — a false expected, an equal pair, or an invalid observed takes the ONE no-reply fault disposition with zero ticket/`tool_calls` mutation.
  **The ordered, one-way, TOTAL transition table (R36-F1 — no branch emits a reply frame; every sender status × ticket state classified):**
  (0) malformed frame — grammar or discriminated-shape violation ⇒ channel fault (§A.2), zero mutation;
  (1) unknown `ticket_id` ⇒ channel fault, zero mutation (a never-minted reference is peer divergence);
  (2) presented epoch ABOVE durable current ⇒ channel fault (m-10 is the sole mint — the §D.3 pre-2 rule verbatim);
  (3) **committed-equivalent duplicate — PRECEDENCE OVER STALE (the D-5 branch-(3)/§B.1 durable-fact replay discipline):** `state=OUTCOME_RECORDED` and the outcome-specific equivalence key matches — `executed`: `{outcome, invocation_identity, presented epoch == the persisted commit epoch}`; `not_invoked_integrity_fault`: `{outcome, the full labeled pair, presented epoch == persisted}` (historical-epoch equality is what makes a delayed re-delivery idempotent, never epoch-blindness) ⇒ idempotent no-op;
  (4) **stale sender** — the channel's generation is not the current lease-holder OR presented epoch below current ⇒ **consume-and-drop, ZERO mutation**: a stale/superseded sender never moves `CONSUMED`, `UNKNOWN_TOOL_OUTCOME`, `VOID`, or any terminal row (§B.4 fencing; the delayed stale record against a retirement-parked `UNKNOWN_TOOL_OUTCOME` row lands HERE — the park is preserved, honestly: that generation's outcome claim died unverifiable with it);
  (5) current sender · `state=CONSUMED` · predicates valid ⇒ **the atomic §F chokepoint commit** (ticket `OUTCOME_RECORDED` + the `tool_calls` terminal + the validated evidence, one transaction); predicate failure ⇒ the fault disposition, zero mutation;
  (6) current sender · `state=OUTCOME_RECORDED` · NOT equivalent ⇒ no-op, the committed terminal PRESERVED, protocol-violation diagnostic — never downgraded or rewritten;
  (7) current sender · `state=ISSUED` or `VOID` ⇒ channel fault, zero mutation (a record for a never-consumed ticket — VOID is reachable only from ISSUED expiry or denial creation, never from CONSUMED, so both states mean no consume happened);
  (8) current sender · `state=UNKNOWN_TOOL_OUTCOME` ⇒ **invariant-impossible** (the UNKNOWN park commits only inside the retirement transaction that retires the consuming generation and mints E+1 — a still-current sender cannot coexist with its own parked ticket) ⇒ the fail-closed store-divergence fault, zero mutation, park preserved.
  **The record-vs-retirement race is total on both sides of the chokepoint (R36-F1):** record commits FIRST ⇒ the later retirement finds `OUTCOME_RECORDED`, and its state-sensitive parking (keyed consumed-no-outcome) correctly does not touch it; retirement commits FIRST ⇒ the delayed record arrives stale and drops at (4), the park preserved. **Supervision: NONE automatic on my side for either member** — the record IS the evidence; m-9's own disposition (their constraint: the integrity fault ends their turn `turn_failed`, reported via their normal turn machinery) arrives through D-5, never through this frame. **Fixtures (each asserting NO reply · ticket state · `tool_calls` state · epoch/generation effects · execution count · terminal non-downgrade):** the positive path end-to-end (consume → invoke → `record{executed, actual}` ⇒ `OUTCOME_RECORDED` · `EXECUTED` · one execution · no supervision) · the valid no-invocation fault path end-to-end (consume → recompute-mismatch → zero invocation → the validated pair ⇒ `OUTCOME_RECORDED` · `NOT_INVOKED_INTEGRITY_FAULT` · zero executions · the mismatch readable durably · m-9's `turn_failed` via D-5) · `executed` with mismatched identity (fault, zero mutation) · **false expected** (≠ stored ⇒ fault, zero mutation) · **the equal pair** (⇒ fault — never persisted as a mismatch) · **forbidden/missing conditional members** (⇒ shape fault) · the record-vs-retirement race, both commit orders · the delayed stale record against `UNKNOWN_TOOL_OUTCOME` AND against `VOID` (drop, rows preserved) · the equivalent duplicate after epoch advance (historical-epoch match ⇒ no-op) · the conflicting duplicate after epoch advance (terminal preserved) · the current-sender×UNKNOWN invariant fault.

## §E — Wake contract (amendment §6; non-gating stretch)

- **Flow:** conductor pushes to the connected m-9 seat channel (m-10 cannot receive it — no seat, no credential) → m-9 forwards `wake_forward{relay_id}` on CTRL-W → m-10 executes `INSERT OR IGNORE INTO wake_schedule(relay_id, …)` with **durable `UNIQUE(relay_id)`** → duplicate deliveries are **no-op acks**. Scheduling **effect = at-most-once**; a schedule row leads to at most one turn admission per `relay_id`.
- **Push is best-effort + advisory** (F61): it creates no authoritative state, replaces no `project`/`read`; a wake lost while the connection stays up is **accepted** and recovered only by **m-9's durable rediscovery** at startup/reconnect/poll (the record is truth). m-10's only obligations: the idempotent schedule table + turning an accepted schedule row into a worker-turn admission (§B.2) when the scheduler runs. **m-10 never touches the conductor** — no verb, no credential, no push receipt.
- Wake frames ride the droppable/advisory queue class (§A.3); loss ⇒ rediscovery, never queue growth, never a failed MVP (non-gating stretch).

## §F — Durable app-state store (amendment §7 ext-review #6)

**Realization: a single local SQLite database** (WAL mode, `synchronous=FULL` — durable-then-visible requires commit-time durability), in the private runtime directory, **separate file, separate writer, zero schema overlap with the conductor store** — the m-10 module is the **sole writer** (single-writer discipline mirrors the conductor's own m-7 rule without touching it). **The database file is private to the m-10 module: every other consumer — the broker feed, m-9, m-8, diagnostics — receives state through frames/the feed interface, never by opening the file** (the conductor's verbs-not-raw-store-paths guardrail, applied app-side; also what keeps the Step-4 split honest). **Schema versioning from day one:** `PRAGMA user_version` carries the store schema version; migrations are forward-only and ship with the binary that bumps the version (the v3 public-release rule — version schemas + migration procedures before the first external database exists). All §B–§E durability claims ("durable-then-visible", atomic consume, `UNIQUE(relay_id)`) are realized as transactions here. (Go driver choice — cgo vs pure-Go — is a named T4 build decision; either satisfies this contract.)

**The single-transition-chokepoint rule (binding on the build):** every state transition in §B–§E — ticket, worker, turn, lease/epoch, attempt, wake — is applied through **one transition-applier path**: one transaction that applies the change and bumps `state_seq`, no ad-hoc writes at call sites. This is required discipline for the fencing/recovery invariants, and it is deliberately the enabler for the **optional forensic events journal (deferred; operator 2026-07-16)**: an append-only `events` table written in the same transaction at the same chokepoint — **transitions + identities/digests only, never payload bytes (no payload column exists by schema)** — behind a config toggle, with a **named retention/GC rule** (e.g. keep-last-N-runs, GC on run-terminal) and **export/persist options** for archival. NOT built in the MVP; adding it later = one INSERT at the chokepoint + the toggle, no schema surgery or call-site audit. The journal, if enabled, is forensic only — recovery always scans the authoritative state tables, never replays events.
