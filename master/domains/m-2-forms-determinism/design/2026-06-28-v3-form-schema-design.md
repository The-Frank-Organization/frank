## 1. Thesis (proved, not assumed)

The relay stops being hand-authored markdown and becomes **a form a trusted courier renders from typed input** — "fill the form, don't write the prose." Authority is enforced **at FILL** (a forbidden option is *absent* from the seat's form), not post-hoc. A field is enum/required **iff a mechanical consumer reads it** (canonical-iff-consumed). The form is **dynamic** — required-set = f(PHASE × CEREMONY_TIER × …). This **deletes** the bulk of relay-lint.py's prose machinery (§10) and refactors the remainder into intra-relay **form-validation** + a cross-relay **lineage engine**.

Proof the thesis is sound and net-new: no surveyed system (v2.8.8, jcode, claude-code, agent-scripts) does fill-time authority over a typed multi-seat relay; the nearest precedents (OpenAI structured-outputs constrained decoding; Swarm handoff-as-available-tool) confirm constraint-at-generation beats post-hoc validation. v2.8.8 already encodes ~50 fields + enums + required-when + lineage (relay-lint.py + protocol.md) — **promote, don't rebuild**.

## 2. The model — an SMTP-inspired three-layer envelope

SMTP's enduring idea: **the envelope is separate from the message, and the envelope is stamped by the transport, not written by the author.** That is exactly our trust model. Every relay has three layers:

| Layer | SMTP analog | Owner | Contents |
|---|---|---|---|
| **Envelope** (transport) | `MAIL FROM` / `RCPT TO` (set by the submitting MTA) | **system / courier (certified)** | `FROM` (seat), `ROLE`, `TO`/`CC`, `DISPATCH_ID`, `PARENT_DISPATCH_ID`, `timestamp`, `relay_id`, `schema_version`, reserved `certification` |
| **Headers** (the form) | RFC 5322 registered header fields | per-field (§3) | `PHASE`, `AUTHORITY`, `EVIDENCE_TARGET`, verdicts, `HUMAN_GATE_REQUIRED`, routing-record, scan/scope blocks … |
| **Body + `X-` headers** | message body + `X-*` extension headers | free-text / never-consumed | judgment prose (genuinely free) + the overflow channel (§6) |

**`ROLE` is system-owned (envelope), not a header pick** (rev1, per DESIGN-REVIEW). The courier stamps `ROLE` from the *same* certified connection as `FROM`; it may be rendered as a **read-only projection** in the header view, but it is never seat-filled. This is precisely what makes the v2.8.8 `role_from_consistency_error` tripwire dissolve (§10a) — ROLE and FROM come from one channel, so a *confused* agent has **no seat-fillable ROLE field** to make disagree (confusion-resistant; **D5 residual:** a shell-bearing seat forging a store record is m-1 TCB scope). §3, §10, and §12 all use this one owner model. (`TO`/`CC` are also envelope-layer but are `recipient_picker`, not `system_only` — sender-selected, courier-validated against the minted address space; only `FROM`/`ROLE` are identity. m-1 coord B2.)

**One-FROM rule (no lane-writable display-FROM — closes the DMARC two-FROM confusion for a *confused* agent).** Email's spoofing surface is the gap between the envelope sender and the user-visible `From:`; DMARC exists only to force alignment. We collapse it: **there is no header `From:`** — FROM lives only in the system-owned envelope, so a *confused* agent has no display-FROM field to fill inconsistently (confusion-resistant; **D5 residual:** a shell-bearing seat forging a store record is out of the schema layer's scope). We get DMARC's alignment outcome with zero alignment machinery. (= m-1's "no payload display-FROM / two-FROM trap".)

## 3. Field-ownership model + fill-time authority

`owner ∈ { system | seat_scoped_enum | agent_enum_pick | free_text }`:
- **system** — courier-filled; **no lane form-affordance** (a *confused* agent has no rendered field to fill — confusion-resistant; **D5 residual:** a shell-bearing seat bypassing the form/courier is m-1 TCB scope): envelope fields (incl. `FROM` and `ROLE`, stamped from one certified channel), computed `*_RESULT`s, the `HUMAN_GATE` monotonic floor, observed evidence (m-3).
- **seat_scoped_enum** — the form offers only the options *this seat* may pick; forbidden options are absent (e.g. `AUTHORITY: direct-override` / merge-grant simply not present on a pair-seat form).
- **agent_enum_pick** — judgment enums the seat freely picks from the full set (verdicts, `PRIMARY_BUCKET`, `CEREMONY_TIER`, scan yes/no/unknown).
- **free_text** — bodies, reasons, justifications (Format-Tax line, §6).

*Hybrid fill-constraints (`parent_picker`, `recipient_picker`, `monotonic`) are not pure `owner:system`* (m-1 coord B1/B2; G1 rev2): the system supplies a **floor or candidate space** and the agent **selects within it**, the courier validating the pick. `parent_picker` — the conductor-derived parent candidate set; `recipient_picker` — the minted address space; `monotonic` (`HUMAN_GATE_REQUIRED`) — the system sets a **floor**, the agent may only pick within `[floor, MAX]` (RAISE, never lower), and the floor itself is the **MAX across all raisers** (system baseline, agent, m-5 archetype-ceiling, m-4 routing-raise) so a lower write never wins. `FROM`/`ROLE` are never hybrids — they are pure `system_only` identity.

**Fill-time-authority render semantics.** Given `(seat, PHASE, CEREMONY_TIER, slot)` the renderer computes the active field-set (required-when, §5) and, per field, the owner-determined affordance: **system** (pure `system_only`) → not shown (courier fills); **hybrid** (`parent_picker`/`recipient_picker`/`monotonic`) → a constrained pick *within* the system-supplied candidate space or floor — so a `monotonic` `HUMAN_GATE_REQUIRED` is agent-**RAISE-able**, not hidden — and the courier validates the pick (set-membership, or monotonic ≥ floor) (G1 rev2); **seat_scoped_enum** → pick-list of *only this seat's allowed options* (the authority gate); **agent_enum_pick** → full enum; **free_text** → text. The forbidden option is never rendered, so a *confused* agent has **no tool to submit it** (confusion-resistant fill-time authority, not a post-hoc rejection), and the courier **also validates the pick on submit** — an out-of-scope pick routed *through the courier* is rejected by set-membership control-flow regardless of how it was authored. **D5 residual:** a shell-bearing seat bypassing the courier/form entirely is m-1's TCB scope, not the schema layer. Precedents (E1): Swarm handoff = the legal next-seats are exactly the tools present; OpenAI structured-outputs = invalid tokens masked at sample time.

**CQ-3 mechanics confirmation (c4-cq-gateconfig; m-2 confirms, m-6 authors the A-floor table).** The pure-judgment **A-floor** (m-6's mandatory HUMAN_GATE floor by `(phase × record_kind)`, `ARCHITECTURE §J2`) composes with this model **with no schema change** — it is simply **another MAX-input raiser**: `floor = MAX(system baseline, agent RAISE, m-5 archetype-ceiling, m-4 routing-raise, **m-6 A-floor**)`, so the mandatory floor always wins and a below-floor value routed through the courier is rejected — **[c5 KEEP: structural monotonic-MAX control-flow property, holds regardless of seat behavior; D5 residual for an out-of-courier shell bypass]**. A *confused* seat attempting a **below-baseline pick** is a **ceremony downgrade** — it does not lower the gate (monotonic-MAX forbids it); it is only reachable via an explicit **`gate_category = ceremony_downgrade`** waiver, itself an A-bucket human-gated category (§17.1). So m-7 enforces the A-floor at fill/submit purely through the existing monotonic mechanics. **Confirmed against §3/G1 + AC9; no new m-2 mechanism required.**

## 4. The single canonical source — bespoke FieldSpec registry (carrier decision)

**Decision: the canonical source the tool (renderer), courier (validator + stamper), and linter all read is a bespoke `FieldSpec` registry** — a versioned data model in which ownership / seat-scope / consumer / lineage-role are **first-class**, borrowing JSON-Schema *vocabulary* only for the structural sublayer (type / enum / required-when) so mature validators cover the already-solved part.

```text
FieldSpec:
  id:            string                      # canonical field name
  layer:         envelope | header | body    # SMTP layer (§2)
  owner:         system | seat_scoped_enum | agent_enum_pick | free_text
  type:          string | enum | bool | int | address | address_list
                 | row_array | id_ref | evidence_ref | object | text
  enum_set:      named-enum | inline-list     # closed option set (header/agent_enum_pick)
  gate_referenceable: bool                    # DEFAULT false (m-2-F5). true iff a required_when/visible_when predicate may key on this field's id (§5). Model-identity fields (chosen_model, §17.3), computed labels (record_integrity/surface_intent, §17.6), and the X- namespace are false-by-declaration — this is the first-class data the R2 gate-grammar KEEP + the X- schema-consumer KEEP invariants read (a predicate naming a false-flagged field is rejected by the grammar, §5)
  seat_scope:    map<seat-pattern, allowed-options>   # the fill-time-authority matrix
  required_when: <predicate>                  # §5 bounded vocabulary
  visible_when:  <predicate>                  # §5 (seat/phase/slot gating)
  fill_constraints: monotonic | system_only | seat_allowed_values
                 | computed_result | observed_value | parent_picker | recipient_picker
  consumers:     [ courier | form_renderer | form_validator | lineage_engine
                 | observe_gate | router | human_surface | egress_gate ]
  lineage_role:  none | parent_edge | grant | verdict | lock_id
                 | action_report | merge_claim | routing_ref
```

**Rejected alternative — JSON-Schema core + `x-owner`/`x-seat-scope`/`x-consumer` extensions.** Rejected because the *novel, load-bearing* layer (ownership, seat-scope, consumer, lineage-role) would live in `x-` extensions that off-the-shelf validators **ignore** — so we'd write custom interpretation code for the part that matters anyway — and JSON Schema validates *post-hoc*, not at render/fill time, which is the opposite of our thesis. It makes the already-solved layer first-class and the novel layer an ignorable extension. Prior art favors bespoke typed records for exactly this control-plane: claude-code uses Zod (coreSchemas.ts / controlSchemas.ts), jcode uses typed Rust records (jcode-message-types). We keep JSON-Schema's `if/then/else` + `enum` *expression vocabulary* inside `required_when`/`enum_set` so the structural sublayer stays familiar and mechanically checkable.

**Render/validate flow:**
1. Courier authenticates the lane (m-1) and **system-fills** envelope fields (FROM, relay_id, dispatch_id, default PARENT, timestamp, schema_version) + any observable evidence (m-3).
2. Renderer selects visible fields + per-seat enum options from the FieldSpec registry + `(seat, phase, tier, slot, parent)`.
3. Agent fills only owned judgment/body fields (enum picks + free text).
4. **send — pre-append validation (readiness-fix-c1 seam; nothing persisted yet, the candidate is held in-courier).** `send` runs the pre-append gates, bouncing with the exact failing field/edge: **(a) form-validation** (required-set complete, enums in range, seat-scope respected — an out-of-scope option is a fill-time-authority violation) then **(b) lineage gate** — the cross-relay **lineage engine** (§10c) validates the candidate's edges against the **persisted `accepted`-graph**, with the candidate supplied **in-courier** (it walks `persisted ∪ {candidate}`; it does **not** append the candidate as `submitted` first — there is **no persisted `submitted` limbo state**). **(c) [RESERVED — lands Step-2] observe-as-send gate** (m-3 done-predicate) — an **additive** hook-point named in the ordering but **not required for Step-1**; **Step-1 = store + form + lineage only** (per `ROADMAP`/`ARCHITECTURE` Step-1/Step-2 split; m-3 builds at Step-2).
5. **Atomic commit (readiness-fix-c1 seam; m-1 owns the store transaction).** On pass, the courier stamps the record and performs **one atomic append of an `accepted` record** + INDEX row + deliver, as a **single transaction** (TOCTOU-closed) — and **ordinary recipients / work consumers act only on `accepted` records** (the c1 safety invariant). **Narrow `held` carve-out (CQ-4, per review `020503`):** a `held` record (m-7 §6 internal-fault-on-authority, or the CQ-2 fail-closed disposition; §17.1) is committed but **consumed only by the gate / escalation / scheduler / operator-resolution machinery** that re-runs, parks, or produces the next verdict record — **no downstream work authority ever executes from a `held` record.** On form/lineage fail, the write path produces a **distinct terminal `rejected` evidenced record** (auditable attempt trail) + **bounces to the author with the failing field/edge** — never a persisted `submitted` limbo, and never delivered or consumed. This preserves the v2.8.8 guarantee that lint blocks *before* handoff/dispatch (protocol.md:397/407) **and** m-1's "no un-gated deliverable state": authority cannot be acted on until form+lineage pass. The **lineage gate runs for all records but has blocking edges only for authority-bearing ones** — design-doc PLAN locks, delegated dispatch / merge grants, substantive IMPL reports, merge claims, and orchestrator-authority relays; non-authority records (SITREP, plain DESIGN, AUDIT, RECONCILE) commit as `accepted` on form pass (lineage is a no-op for them).
6. Markdown is rendered as a **view/export only**; the canonical object is the typed envelope.

## 5. Bounded required-when / visible-when predicate vocabulary (Q4)

Predicates are a **finite, inspectable boolean** — `all_of` / `any_of` / `not` over a **closed atom set** — never Turing-complete (the audit's named top risk; CodeAct/determinism rationale: gates branch on a fixed vocabulary, not arbitrary compute):

```text
atoms:  phase_in:[…]            ceremony_tier_gte:<tier>     authority_in:[…]
        seat_is:<pattern>       role_in:[…]                  slot_in:[…]        # RESERVED atom — shape only, no Step-1 values
        record_kind_in:[…]      scan_result_in:[…]           claims_action:<bool>
        field:<id> <op> <value>          # dependent-required (op ∈ ==,in,present); <id> must have `gate_referenceable: true` (the first-class FieldSpec flag, §4, m-2-F5) — every model-identity-marked field is `gate_referenceable: false` (the live routing model field is `chosen_model`, §17.3; exclusion is the field's own flag, not a `model_*` name pattern) (R2, readiness-fix-c4)
        any_row:<array>.<field> <op> <value>   # bounded existential over a row_array's rows (decidable, finite; no nesting/loops); <field> obeys the same gate-referenceable allowlist (readiness-fix-c4)
        layer_present:<layer>            # closed context atom; <layer> ∈ {store, form, lineage, observe}; courier-evaluated from which fill-layers/writers are bound at runtime (CQ-1 step-gate)
combinators: all_of | any_of | not        # bounded boolean; no loops, no calls
```

The evaluator is a pure boolean over the relay's own fields + `(phase, tier, seat, slot, present-layers)` context. This expresses every v2.8.8 conditional (read-only→`FINAL_GIT_STATUS_SHORT`; downgrade→`ESCALATION_SCAN`; `DESIGN_LOCK_ID`→`DESIGN_RECORD_KIND`) as data, decidably and auditably.

**CQ-1 step-gate — observe-owned requireds are gated on observe-layer presence (c4-cq-m1; m-2 co-sign of m-1's resolution (a)).** An **observe-owned** field's effective required predicate is `all_of(required_when(F), layer_present:observe)` — so when no observe writer is bound (**Step-1**, m-3 builds Step-2), `layer_present:observe == false` ⇒ the field is **not required**. A form gate therefore can never demand a field that nothing can fill (the fill-time-authority principle: a required field must be fillable). The step-gate is derivable from the field's typing — a field with `owner:system` + `fill_constraints: observed_value` (or a `*_RESULT`/rollup computed from observed values) is **observe-layer-filled**, so the atom makes explicit what canonical-iff-consumed already implies.
- **Observe-owned set (the m-3 write-allowlist, §12 m-3 / §17.6):** `ACTIONS_GIT_REF`, `FINAL_GIT_STATUS_SHORT`, `achieved_evidence`, the `*_RESULT` set, per-field `evidence_integrity`, `record_integrity`, `executable_claim_results`, `egress_scan_result`, `degradation_notes`, `deviated_observed`, and the per-phase done-predicate observe-gate hook.
- **Hard guardrail (m-1):** the step-gate applies **ONLY** to observe-owned fields. Every `system_only` / lineage / form-owned required field stays **fully required in Step-1** — the step-gate is not a lever to relax non-observe requireds. Note `EVIDENCE_TARGET` is `agent_enum_pick` **intent** (not observe-owned) — it stays Step-1-required; only the observed `achieved_evidence`/`*_RESULT` are step-gated. R2-safe: `layer_present` references build-layers, never model.

**R2 grammar-enforcement — model is not gate-referenceable (readiness-fix-c4).** The generic `field:<id>` atom's `<id>` is drawn from a **gate-referenceable-field allowlist that structurally excludes every model-identity-marked field** (the live routing model field is `chosen_model`, §17.3, flagged non-gate-referenceable — exclusion is by the model-identity mark, **not** a `model_*` name pattern, which `chosen_model` would not even match): model-identity fields are **not gate-referenceable**, so no `required_when`/`visible_when` predicate can key on the model — even through the generic dependent-required atom. This makes R2 (*model ≠ gate input*, m-1 coord) **structurally impossible to violate in the schema the tool reads**, not merely asserted — **[c5 KEEP: a trusted-engine gate-grammar invariant; no predicate atom references the model field, so the property holds regardless of seat behavior, not a malicious-containment claim]**: the absence of a `model_*` atom (§17.3 `:289`) was necessary but not sufficient while `<id>` could name a model-identity field (e.g. `chosen_model`); the exclusion (by model-identity mark) closes that hole. Model stays payload/bookkeeping; trust stays keyed to the stamped seat `FROM`. The R2-safe deviation trigger keys on the **planner-declared** `declared_deviated` bit (`agent_enum_pick`, §17.3), never on model identity and never on the system-computed observe-side `deviated_observed`. The aggregate routing trigger `any(routing_assignments.declared_deviated == true)` is expressed by the bounded `any_row:` existential atom above — decidable over the finite `routing_assignments` rows, so a single deviating row in an altitude-B fan-out cannot escape the required justification.

**`slot_in` is a RESERVED atom for Step 1** (rev2 #5, VP-approved): the atom *shape* exists, but **no concrete archetype/slot enum values are defined** and **no required-when predicate may branch on a concrete slot** in Step 1. m-5 (Workflows & Archetypes) owns the tag-space + concrete slot semantics in a later cycle — same reserved-seam pattern as `certification` / Merkle hash-chain. (`(…, slot)` stays in the evaluator context so m-5 extends the same bones.)

## 6. Overflow channel (Q5) + the Format-Tax line

**Overflow = `X-`-prefixed fields** (SMTP's `X-` convention): present in the relay, carried and stored, but **never read by any mechanical consumer and never a gate input** (`consumers: []`, `lineage_role: none` enforced for the `X-` namespace) — **[c5 KEEP: a schema-consumer invariant, not a malicious-containment claim — the registry declares the `X-` namespace `consumers:[]`/`lineage_role:none`, a structural property of what the tool reads, holds regardless of seat behavior]**. Unanticipated content has a sanctioned home and does not silently re-grow into gate-bearing prose, because `X-` is structurally non-consumed.

**Format-Tax line (held strictly):** enums/required apply only to **consumed** control-plane fields; the judgment body stays a genuinely free `free_text` channel — the seat reasons in prose, then fills the form. (Counter-evidence proved in audit: "The Format Tax" / "Let Me Speak Freely" — forcing reasoning inside a rigid format degrades quality; canonical-iff-consumed is the mitigation.)

## 7. Certification (Q1b) — reserve + defer

Email authentication maps cleanly onto m-1's TCB:
- **SPF** (the *connection* authorizes the sender) → m-1's **channel-stamped FROM** — active; **confusion-resistant** (a confused agent has no tool to stamp a FROM it doesn't hold; **D5 residual:** a shell-bearing seat forging a store record is out of scope — m-1's TCB, not the form layer).
- **DKIM** (the substrate *signs* the record) → an **optional courier signature** over the stamped envelope. **Deferred for v3.0** (operator decision); m-1's current locked position is courier-as-TCB. m-2 **reserves** a system-owned `certification` envelope field — **null-reserved** (m-1 coord Q-A): present in *every* v3.0 record with `default: null`, so signing turns on later with **zero schema change** (a pure behavioral change: courier populates, verifier consumes). canonical-iff-consumed keeps it dormant until a verifier exists. Crypto-hardening note (m-1 coord E): this deferred DKIM-signature and m-1's deferred Merkle/append-log hash-chain are the same deferral class (verifiability *against the courier itself*); both are reserved seams, named jointly at the lock as "crypto-hardening: reserved, courier-as-TCB for v3.0."
- **DMARC** → dissolved by the one-FROM rule (§2).

Public-release intent (operator, 2026-06-28) makes eventual activation of `certification` more likely (external verifiability) — reserving now is the cheap hedge.

## 8. Legacy strictness (Q2) — strict, form-only submit

The form/courier is the only **governed/sanctioned** path to create a relay (confusion-resistant; **D5 residual:** a same-uid shell-bearing seat can write a store record directly — m-1 TCB scope, out of the schema layer). Legacy v2.8.8 hand-authored markdown is **read-only history** (importable/projectable), **never submittable**. Any hand-authored-markdown submission path would reopen every prose hole the typed envelope dissolves (fences, bare tokens, ambiguous rows); strictness is what *permits the deletion* of the ~33 prose checks (§10a) rather than retaining them for a compat window.

## 9. Schema versioning + migration framework (Q3) — ship the seam, zero migrators

Public-release intent makes the schema a **public interface**, so versioning is first-class even though there is nothing to migrate yet:
- `schema_version` — system-owned envelope field, stamped immutably on every record.
- **Published compatibility contract:** *additive* (new optional header / new `agent_enum_pick` value / new `X-` field) = backward-compatible → **minor** bump, old readers ignore-unknown; *breaking* (remove/rename a field, narrow an enum, **widen a system-owned closed enum whose mechanical consumers switch exhaustively on it — e.g. `delivery_state` `{accepted, rejected, held}`, byte-exact-locked at three**, change ownership or required-when) = **major** bump → requires a registered migrator. (Widening an *open* `agent_enum_pick` judgment enum stays additive/minor above — the ignore-unknown rule holds only where no consumer switches exhaustively.)
- **Migration mechanism:** records are immutable (m-1 append-only store), so migration is applied at **read/projection time** by a registry of version→version migrators (a chain upgrading an old record to the current view). v3.0 ships the registry + chain-application + version-negotiation **with zero migrators registered**; the first breaking change registers the first migrator into an existing seam.
- **Submission is always current-version** (strict form-submit; courier renders the current form), so version skew only appears on **read** of historical records. Parked lanes wake to the current form.
- Cross-cutting: m-1 persists `schema_version` per record + serves records for read-time migration; m-6 scheduler wakes lanes to the current form.
