## §1 — The connector secret-boundary delta (F57-NARROW strength; m-1-owned)

### 1.1 The secret classes (exactly two; and what is NOT secret)
- **S-A — provider credentials** (API keys): runtime holder = **m-8 only** (the charter's m-1 boundary); provisioning/custody source = the operator config path.
- **S-B — seat credentials** (the logical m-9 seat's conductor credential): runtime holder = **the m-7 broker only** (under §2 of this contract); mint/custody **source** = the existing operator mint path (c1 §5 `mint_seat`; s6 re-mint — new credential appears ONLY in the operator submit reply / the 0600 binding-table admin path, F-S6-M1-1 verbatim); **authorized runtime custody SINK = exactly one broker-private, permission-checked 0600 credential file, operator-authored from that source** (pinned §2.4 — the F2 disambiguation; it does not weaken F-S6-M1-1: the conductor-side floor is unchanged, this names the app-side sink the "only" previously left ambiguous).
- **NOT secret (must be safe to expose app-side):** config/integrity stamps and digests · run manifests · `turn_epoch` values · F59 tickets (they bind *digests of args*, never secret bytes) · **opaque credential references** (§1.4).

### 1.2 The claim, exact (the ratified F57 narrowing — this contract claims NO MORE)
**Non-injection:** S-A and S-B bytes are **not injected into** the enumerated surfaces — the **model context · local-tool arguments · the `bash` environment/files/argv · inherited FDs · logs** — and (m-1 extension, continuous with I-PH + F-S6-M1-1) **not into** conductor records/projections/INDEX/typed errors, the m-10 app-state store (incl. tickets/crash states), E0 app-event bodies, or run manifests.
**Placement:** separate-process placement of the holders (m-8; the broker outside the worker generation, F66) is **accidental-disclosure reduction**.
**Explicitly NOT claimed:** hard unreadability. **A same-user unsandboxed process (incl. `bash`) may inspect peer-process state** (`/proc`, debug interfaces, handles, dumps) on some platforms — the named **unsandboxed MVP residual**, for BOTH secret classes. This is the confusion-not-malice line: a *confused* agent has no tool that is *handed* the secret; deliberate peer-memory spelunking is out of MVP scope. The real OS boundary is **Step-4 H-12**. *(Continuous with §0.c D4/D5: non-injection is the D4 claim; same-user inspection is this vertical's D5-analog residual — stated, not closed.)*

### 1.3 The §2 minimum hardening list — design REQUIREMENTS (owner-assigned)
1. `bash` launches with a **sanitized environment** (m-9 executor half).
2. **No secrets in process argv or ordinary env** — any process, any launch (m-8 · broker · m-9 · m-10 launch paths).
3. **Close-on-exec on every internal IPC descriptor** (broker/m-8/m-10 channels).
4. **Tool subprocesses inherit NO m-8 / m-10 / seat-broker channel** (m-9 executor; §10 annex row 8 is the fixture grain).
5. **No secret-bearing crash dumps** (m-8 + broker: scrub-or-disable on the secret-holding processes).
6. Runtime sockets/files in a **private runtime directory** (app main + m-8).
7. **The operator's ambient provider credentials are NOT inherited by m-9** (m-10 launch path: explicit env allow-list, not a deny-list).

### 1.4 Two DISTINCT app-side objects — a credential REFERENCE is not a USE capability (F1: never conflate; each carries its own authority + leak claim)
- **1.4a — The opaque credential locator/REFERENCE (custody orchestration; held by m-10):** carries **no secret bytes and no credential-derived verifier** (no key digest/fingerprint an offline check could confirm against; an arbitrary handle resolvable ONLY inside the holding process — m-8 for S-A, the broker for S-B). **Possession alone neither authorizes resolution nor selects/attaches a credential**: resolution occurs only inside the holder within an **independently authenticated + authorized** operation — and the real authorization paths are distinct per class (MR1): **S-A** — resolution + attachment occur ONLY after the **m-3-owned provider-request policy authorizes the frozen core at m-8** (the `freeze→authorize→attach→send` order; the F59 ticket authorizes the app-side TOOL CALL, never the provider request or credential resolution); **S-B** — resolution occurs ONLY inside the **broker's operator-provisioned startup/re-auth path** (reading the §2.4 sink); **the F64 epoch gate fences worker USE of the already-bound channel — it never authorizes credential resolution.** Leaking a reference is therefore **secret-inert AND authority-inert**. **m-7/m-8 may NOT satisfy this requirement by pointing at a bearer capability token** — that is the other object below.
- **1.4b — The epoch-bound worker USE capability (channel delegation; held by a worker generation) is a DIFFERENT security object**, defined in identity terms at §2.5. It is **intentionally AUTHORIZING**: while its epoch is current, it moves exactly the three broker verbs (`relay.submit`/`relay.project`/`relay.read`) **+ typed transport-metadata `Describe`** + push receipt/rediscovery, on its **private broker IPC connection**, all behind the same per-invocation epoch gate. **`Describe` is transport metadata (MR3): NOT a fourth relay verb, NOT one of the fixed eight dispatch tool names; it creates no principal, has no identity consequence, and carries no relay-acceptance authority — it is fenced identically** (stale-epoch `Describe` refused; negative carried to §5). It carries no secret bytes, creates no principal, and has **no offline credential meaning** — but it is **NOT leak-inert**: presented on an accessible current-epoch broker channel it authorizes. Its honest containment claim = the private-IPC surface discipline (§1.3 items 3/4/6: close-on-exec, no tool-subprocess inheritance, private runtime dir) + the epoch gate + revocation-by-epoch-advance — **never the 1.4a claim.**
- **Consumer negatives (carried to §5):** (i) **reference-without-authority**: a credential reference presented outside an independently authorized operation resolves nothing; (ii) **capability replay**: a USE capability replayed after an epoch advance OR across a broker restart is refused.

### 1.5 Verification grain
The **§10 sentinel-secret test proves accidental-disclosure ABSENCE ONLY** — never same-user-inspection resistance (its wording is part of this contract). The denied-path "secret resolver never invoked" and "credentials attach only after authorize" proofs are m-8's contract, cited here as the S-A enforcement fixtures; annex row 8 (no secret/control handle injected into `bash`) is the S-B/handle fixture.

## §2 — Seat identity + credential-lifecycle semantics (F60; m-1-owned — m-7's broker realizes custody UNDER these semantics)

### 2.1 What a LOGICAL seat IS
A logical seat is a **conductor-side identity**, never a process: **`(minted seat address, current mint-generation)`**, where the mint-generation is the seat's **latest accepted `seat_mint` pivot in commit order** (the s6 §F.1 definition, unchanged). Its identity facts live in committed records + the binding table; the channel-stamped `FROM` derives from the binding of the credential presented on the connection — **unchanged** (the Identity-Seam Rail). **The logical m-9 seat is the sole app seat/principal (F66)**; it holds exactly one live stamped credential (S-B), **broker-held**.

### 2.2 The two-counter law (the load-bearing separation)
There are exactly **two generation counters, deliberately distinct, never coupled**:
- **mint-generation** — m-1, conductor-side, = the committed `seat_mint` pivot chain. **Identity epochs.** Advances ONLY by an operator act (mint-before-serve; re-mint). Genesis-anchored, monotonic, never reused (the pivot chain IS the counter — no new store state).
- **`turn_epoch` / worker generation** — m-10, app-side state store. **Supervision epochs.** Advances automatically on worker replacement.
**F60 stated exactly: worker replacement increments `turn_epoch` and NEVER the mint-generation.** No app-side event may cause, require, or imply a `seat_mint`. This is why worker-per-seat is rejected without exception: per-generation minting would couple the counters and place mint authority in m-10's hands — **m-10 must never hold mint authority** — and identity churn would sever lineage accountability from the durable seat.

### 2.3 Identity persistence across restart/replacement (the s6 §F lifecycle, mapped — extended, not forked)
- **`minted`** — unchanged (the operator's `seat_mint` pivot).
- **`bound`** — the **broker's** authenticated connection on the seat credential (the broker is the connecting party now; §F "every reconnect re-binds; empty after restart" applies to the broker's channel). A worker generation NEVER binds — it has no credential to bind with.
- **`active`** — unchanged: first accepted relay per **mint-generation** (whichever worker generation caused it, via the broker).
- **Worker replacement is conductor-INVISIBLE by design** — same credential, same binding, same mint-generation ⇒ **same identity; no re-mint, no re-bind (unless the broker's channel itself cycles), no re-boot, no new activation.** The compensating control for conductor-invisibility is the **F64 broker generation fence**: the broker checks the current `turn_epoch` on EVERY request operation — **each of the three canonical relay verbs AND typed transport-metadata `Describe`** — and on **every push delivery/forwarding** (the complete §1.4b surface; m-7's contract realizes; m-10 supplies epoch state, receives no credential bytes, gains no conductor verb).

### 2.4 Mint/rotate under the broker (the s6 machinery, custodian swapped)
Re-mint semantics are **byte-unchanged** from the s6 ruling: one operator `seat_mint` submit ⇒ binding-row replacement (`realized_mint_ref` completion provenance; crash window closed per `…-102208`) ⇒ **old credential dies at auth `Resolve`; channels authenticated on it force-close** — which now means: **the broker's channel force-closes; the broker re-authenticates with the new credential.**
**The provisioning handoff, PINNED (F2):** the **source** is the operator submit reply / 0600 binding-table admin path (F-S6-M1-1 unchanged); the operator authors the credential into **exactly ONE broker-private, permission-checked (0600) credential file** — the **only authorized persistent app-side custody sink** for S-B — and the broker (re-)reads that file at start/rotation (m-7's realization, `2026-07-16-step3-mvp-transport-broker.md`). **That file joins the S-B census with full obligations:** rotation **OVERWRITES** it (no stale copy survives), it appears in no log/typed-error/crash-dump (§1.3 item 5 extends to it) and no backup/telemetry path, and it is deleted on seat decommission. **Preserved negatives:** the broker never reads the conductor's binding table directly; no m-10 store/frame/path ever carries the bytes; no worker or m-8 surface sees S-B; no app-side relay/IPC carries credential bytes. Any different sink shape routes back to m-1 before either pair approves.
Worker generations are untouched by rotation (their capability targets the broker, not the credential); orthogonally, an epoch increment never touches the credential. **Rotation = identity-epoch event; replacement = supervision-epoch event; neither implies the other** — the full event cross-product is pinned in §2.7.

### 2.5 The epoch-bound USE capability, in identity terms
The capability a worker generation holds is **a revocable delegation of the seat's channel — never a second identity**:
- It **appears nowhere in identity space**: not a mintable address, not a principal, no conductor-visible existence, no stamp consequence — every record produced through it is stamped `FROM = the seat`.
- It carries **no credential bytes** (S-B never copies into a worker generation) and confers use **only through the broker's per-operation epoch gate** (F64) — possession alone moves nothing once the epoch advances. **While the epoch is current it DOES authorize exactly the complete §1.4b surface** — the three canonical relay verbs + typed transport-metadata `Describe` (request operations) + push receipt/rediscovery (fenced at forward time), on the private broker IPC — its authority + leak claim is **§1.4b's, never §1.4a's leak-inertness**.
- **Revocation (epoch increment) is a supervision act with zero identity consequence** — the seat's identity, binding, and lineage continuity are untouched.
- **Honest accountability note (labeled, not claimed away):** the conductor **cannot distinguish which worker generation authored a relay** — lineage accountability attaches to the durable SEAT (that is the point of F60); *which generation acted* is app-side bookkeeping (m-10's epoch-bound state + m-3's E0 events), evidence-graded E0, never identity.

### 2.6 The rail, applied (consistency clause)
The broker is **custody plumbing, not identity machinery**: it adds no stamp, no identity transform, no new principal class; `FROM` derivation is untouched; the epoch fence is a monotonic comparison, **not a home-grown crypto primitive**; the identity stays **structured-so-it-could-later-carry-attestation** (the §8 null-reserved `certification` seam untouched). Any future strengthening (signed capabilities, attested workers) routes through the amendment path with the no-home-grown-primitives bar explicit.

### 2.7 The event/effect matrix (F3 — m-1 owns the identity-semantic EXPECTED RESULT; m-7/m-10 own the mechanisms)

| event | mint-generation | `turn_epoch` | `bound` (s6 §F) | capability disposition | in-flight disposition (owner) |
|---|---|---|---|---|---|
| **worker replacement** | unchanged | **+1 exactly** (m-10) | unchanged (the broker's channel persists) | old-epoch capabilities dead at the broker gate; the new generation is issued fresh | broker completes-or-rejects, recorded (m-7 F64 linearization) |
| **broker restart** | unchanged | unchanged (m-10's durable state; **no implicit advance, no reset/reuse**) | **re-`bound`** — the broker re-authenticates from the §2.4 sink | **every old connection-scoped capability/token DIES with the broker's connections** (replay refused — §1.4 negative ii); the logical delegation of an eligible current-generation worker is reattached **at the unchanged epoch, only through the authenticated restart protocol, with FRESH capability material** (MR2) | app-layer fail-with-retry; nothing silently resumed (m-7/m-10) |
| **conductor restart** | unchanged | unchanged | **re-`bound`** on reconnect (s6 §F.1: `bound` starts empty after restart) | unchanged (epoch untouched) | conductor recovery rules (m-7/store); broker reconnect + durable rediscovery (§6 wake) |
| **re-mint (rotation)** | **+1 exactly** (the operator pivot) | unchanged | force-close → re-`bound` with the new credential from the **overwritten** sink | unchanged — capabilities target the broker, not the credential | old credential dies at `Resolve` (s6); broker in-flight verb calls complete-or-reject, recorded (m-7) |
| **re-mint ∥ replacement (overlap, either order)** | **exactly +1** | **exactly +1** | force-close → re-`bound` once | old-epoch dead; the new generation usable **only after BOTH** the current-credential channel is up **AND** its capability epoch is current | broker linearizes the epoch change against in-flight calls (m-7 F64); **no implicit `seat_mint`, no epoch reset/reuse, each counter advances exactly once** |

The matrix is normative at the identity grain: any build outcome contradicting a cell routes back to m-1.
