### 1.4 The durable-rediscovery loop (the record is truth; consumes m-7 §2.6 + §1.5.4)
Push is **best-effort + advisory** (amendment §6/F61) — it signals a projectable record *may* exist; it is never authoritative state and never replaces `project`/`read`. The receiver's delivery guarantee is therefore **durable rediscovery, not push**:
- **On startup and on every reconnect** (broker restart, capability re-acquisition, connection replacement), the receiver runs a **catch-up `project`/`read`** against its durable mailbox to recover any records a lost push would have signalled. A wake lost while the connection stayed up is accepted and recovered at the next rediscovery pass.
- **`relay.read`'s conditionally-mutating disposition (m-7 §1.5.4) is consumed as-is:** a lost first response is healed by re-read — any later read returns the authoritative current disposition (`checksum-mismatch` pending / `record-quarantined` with incident identity); the receiver keeps **no dedup or repair bookkeeping** (duplication is impossible by m-7's landed mechanism).
- **Retry posture (consumes m-7 §1.5):** the receiver's default `RetryGate` is always-allow, but a served application rejection is terminal (never re-sent by transport); `broker:unknown-outcome` on a fenced submit retry is a **rediscovery trigger**, not a resend (the record is truth).

### 1.5 Wake forwarding (consumes m-10 §E; duplicate-safe by m-10's `UNIQUE(relay_id)`)
When the conductor pushes to the connected seat channel, the broker forwards the nudge to the current-epoch capability connection; the receiver forwards `wake_forward{relay_id}` to m-10 on CTRL-W. m-10's durable `UNIQUE(relay_id)` makes scheduling **at-most-once** — duplicate deliveries are no-op acks. The receiver adds **no scheduling state of its own** and never touches the conductor to schedule; a lost wake is a rediscovery event, never a failure (non-gating stretch).

### 2.3 Turn terminals (m-9-owned turn semantics — five-layer agenda layer 4; PROPOSED, pair-review + grill at stage-4)
*(r2/F3 — the two denial classes are separated, each terminal states provider-wire and tool-effect facts INDEPENDENTLY, and the self-contradictory "partial-zero wire" is struck.)* Exactly one per logical turn:
```text
turn_completed    finish_reason=stop; output observed; all tool rounds folded
turn_refused      finish_reason maps to a typed refusal (content-filter); honest, never empty
turn_denied       a PROVIDER-SEND egress denial (m-8 egress_denied token) on an attempt, OR an
                  absent/invalid routing before any attempt existed, ended the turn. The DENIED
                  attempt sent zero provider wire (m-8 refuses pre-wire); any EARLIER attempt in
                  the same turn is recorded with its OWN per-attempt wire facts — the terminal
                  never asserts a turn-level "zero wire".
turn_cancelled    operator/steer cancel; partials committed labeled-partial; interrupted ≠ failed
turn_failed       wire/adapter/machinery failure after the bounded (no-auto-retry) attempt(s)
turn_exhausted    a §2.4 bound tripped: max attempts, max tool calls, max wall-clock, doom-loop —
                  INCLUDING a model that loops on above-ceiling (DENIED_ABOVE_SET) tool asks
```
**A tool-authorization denial is NOT a turn terminal (r2/F3).** `DENIED_ABOVE_SET` (§3.3) occurs AFTER a provider attempt has already returned a complete `tool_call_end` (provider wire for that attempt already happened); it returns a typed tool-error result to the model and **counts toward the max-tool-calls bound (§2.4)** — the turn **CONTINUES**. It terminates the turn only transitively, as `turn_exhausted`, when a §2.4 bound trips. So `turn_denied` is reserved for the **pre-wire provider-send egress class + absent-routing**; within-turn tool denials never reach it.

**Per-terminal fact rule (r2/F3):** every terminal record states (a) the provider-wire disposition **per attempt** (an attempt sent-completed / sent-failed / denied-pre-wire / cancelled / lost — never a turn-level roll-up that hides an earlier attempt's wire), and (b) the tool-effect disposition per tool call (completed / interrupted / unknown_effect / denied-no-execution). No terminal conflates the two axes.

**Separation law (preserves CQ-4 / amendment §3 "no fourth `delivery_state`"):** turn terminals are m-9-layer semantics carried INSIDE records + m-3 E0 app-events; the records themselves still reach exactly one existing relay delivery-state `{accepted, rejected, held}` at the conductor, and the app-events floor at E0. **No turn terminal is a fourth delivery_state and none is a gate token.** (This is the stage-3 shape; the byte-exact set + the mapping to m-3 `phase` values pins at stage-4 with m-3, and is a grill item there.)
