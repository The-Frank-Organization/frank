*(realizes lifecycle-half §3 — consume-then-execute; the THREE identities / TWO derivation points (F84).)*

**5.2 The three identities / two derivation points (F84, lifecycle §3.2).** #1 the FROZEN authority (`{canonical_tool_name, canonical_args_digest}`, derived once at request construction over the complete validated immutable args via SHA-256/JCS — m-10 §D.2:193 — sent in `authorize_tool_call`, stored at mint, never unfrozen); #2 the CURRENT pre-consume comparand (derived FRESH immediately before `consume_ticket`, and carried on the four-field consume wire — so m-10's #2-vs-#1 match fires `IDENTITY_MISMATCH`/ticket-`ISSUED` on a mutation before derivation point A); #3 the CURRENT pre-invocation comparand (recomputed after `consume_ok`, compared against #1 — a mutation before derivation point B ⇒ zero invocation). ## §6 — E0 population
*(the `m3.app_event.v1` rows the worker populates + carries, per m-3 r4; the worker is the E0 populator+carrier, m-8 emits none.)*

**6.1 What the worker emits, and when.** Per attempt outcome the worker MAY report an E0 event (m-3 §1.4 — non-guaranteed; a crash emits none, and a live worker losing the retirement/reap race may leave no surviving E0, in which case m-10's durable `UNKNOWN_PROVIDER_OUTCOME` row is the surviving truth). The event carries `phase ∈ {denied, sent, completed, failed, cancelled, unknown}` mapped **total** over m-8's `attempt_result.disposition` (m-8 §6): `sent`/`completed`/`failed` per stream terminal; `cancelled` (the determinate non-failure terminal — never report a cancellation as `failed`); `denied` (with `deny_reason`, present **iff** `phase=denied`); `unknown` mirroring `UNKNOWN_PROVIDER_OUTCOME`. `phase=cancelled` is realized **post-token per the m-3 F73 ladder** (non-gating — §11 flag 5).

**6.2 Carriage + encoding.** The worker delivers the event as an `app_event{…}` frame on **CTRL-W** → m-10's `pending_app_events` rows (**the worker seat carries it to the conductor; m-10 never does** — m-10 §B.1). `turn_epoch` is the canonical-decimal-uint64 STRING (the m-10 §A.2 encoding — one encoding across the frame, the row, and the SITREP copy). `event_evidence`/`event_integrity` are the fixed literals `E0`/`self_reported`; `reported_by = "m-9-worker/g<generation>"` is a claim, not a proof.

**6.3 Redaction (m-3 §2.3, hard).** An E0 event carries **identifiers, digests, enum outcomes, timestamps only** — never prompt bytes, provider response content, headers, wire frames, or credential references. Raw `LLMRequest`/provider frames/transport envelopes/raw tool envelopes are never valid conductor payload and never appear. (E3 is the external observer's record — never the worker's, m-3 §3.1.)

## §7 — Session/context management + compaction posture (the simplest honest thing)
*(the MVP context/session state + compaction — "pick the simplest honest thing and say why", dispatch §1. A GRILL topic.)*

**7.1 The MVP posture (why the simplest subset).** The worker holds the durable turn transcript (the `input[]` source) and reloads it each turn iteration. For compaction the MVP takes opencode's **V2-core minimal subset** (~15 lines of real logic; `references/opencode` `packages/core/src/session/compaction.ts:225-236,128-159,161-168` @ `cd46f22d5`): **one token estimate** against a budget (`context − max(max_output, buffer)`, buffer ≈ 20k); if under budget, do nothing; else **keep the newest N tokens (≈8k) of the transcript verbatim** as `recent` and **summarize the rest** (`head`) with **one provider call** against a fixed structured template (Objective / Important Details / Work State {Completed, Active, Blocked} / Next Move / Relevant Files — `packages/opencode/src/agent/prompt/compaction.txt` @ `cd46f22d5`), then replace the model history with `[summary, ...recent]`. On repeated compaction the prior summary is passed as `<previous-summary>` and updated, not regenerated. The heavier V1 machinery (turn-splitting, per-turn budgeting, media-stripping, independent tool-output prune) is deferred refinement — the barely-enough posture.

**7.2 The two invariants that MUST hold even in the MVP.** (a) **Provider-native reasoning/tool blocks NEVER survive the compaction boundary** — only lowered text crosses; this avoids signature/encrypted-reasoning breakage when the prefix changes (`specs/v2/session.md:115` @ `cd46f22d5`) and is consistent with frank's `replay_envelope` custody (reasoning replay is turn-scoped on its originating lane — m-8 §1.1:46, lifecycle §2.8 — so cross-turn native reasoning is out of scope by construction). (b) **"Compaction itself overflowed" is TERMINAL, not a loop** (`compaction.ts:404-413` @ `cd46f22d5`) — a turn that cannot be compacted even after summarizing ends honestly (`turn_failed`), never an infinite compaction loop.

**7.3 Accounting.** Compaction's token estimate uses the authoritative terminal `completed.usage` (m-8 §1.2:70 — interim `usage{}` is progress-only), so the budget decision is made on real accounting, not a progress guess (lifecycle C-2).

## §8 — The two carried OWNER-BYTES pins
### §8.1 — L5: shared-client build-digest coverage
**The question (owner-bytes):** is the shared conductor-client INSIDE `m9_worker_build_digest`, or separately built and transitively covered by `release_digest`? (The stage-6 lock VERIFIES; m-9 DECIDES here.)
**Decision (lean, defended — a GRILL topic):** **SEPARATELY built, transitively covered by `release_digest` — NOT folded into `m9_worker_build_digest`.** Rationale: the shared conductor-client is a **shared artifact** (§4.1 — it backs both the native relay tool AND the retained MCP frontend), and the kimi `klient` precedent (`references/kimi-code` @ `df68995`) is exactly a client SDK shared across frontends/transports. Folding a shared dependency into one consumer's build digest would either double-count it (if the MCP frontend is separately digested) or falsely bind a shared artifact to a single consumer. Keeping `m9_worker_build_digest` scoped to the worker's OWN code, and letting `release_digest` transitively cover the shared client, keeps each digest honest about what it attests. **The tension** (for the grill): single-digest simplicity (one digest covers everything the worker loads) vs. shared-artifact honesty (a shared client is not the worker's to attest).
