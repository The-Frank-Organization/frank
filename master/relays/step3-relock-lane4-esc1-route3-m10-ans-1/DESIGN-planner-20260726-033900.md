## The load-bearing finding: the frozen AND-invariant already makes this total
Resume-trust in my design is a **conjunction**, not a lookup (rev16 §2:30 evidence property #1 + m-9 r17 §3 the two temporal properties):
- **Conjunct A (frozen evidence):** the manifest entry is `settled_with_content` — it records only that content **WAS durable at settlement**, nothing about now.
- **Conjunct B (current presence):** at resume, the content is found in the **currently recovered valid prefix, matched IDENTITY-EXACT** on `{run_id, source turn_id, tool_call_id|attempt_id}` (+ `args_digest` for tool entries).

An edit changes the recovered prefix's bytes, so its **identity no longer matches** the frozen receipt/snapshot identity ⇒ **Conjunct B fails** ⇒ the entry maps to **`content_lost` → `DEGRADED`** (m-9 r17 §3:336), and edited content is **never trusted, never reconstructed, never treated as reconstructed content**. **An edited byte therefore CANNOT inherit the original's trust status** — the trust verdict requires B, and the edit is precisely what breaks B. This is *label, never gate* by construction: m-10 does **not** hard-fail the resume (the run proceeds), but the edited content is **labelled untrusted/degraded**, never promoted as the provider's or tool's actual output (the deepagents fabrication class is structurally excluded).

## Items 1–6, m-10 half

**1. Detection (my part).** I do not detect "an edit" qua edit; I detect the **identity mismatch** an edit produces — the frozen receipt/snapshot identity (`{run_id, turn_id, attempt_id}` + the stored round-identity operand) vs the recovered content's identity, at the resume-reconciliation phase (post-`turn_open`, m-9's stage-2). This is honest: I need only identity-mismatch detection, which the frozen contract already performs; no new edit-detector is owed on my side. *(Emergency hand-repair and sanctioned `bivpak`-class rewrite are indistinguishable to me by design — both surface as identity mismatch — which is correct: the MVP does not privilege one edit source over another.)*

**2. Labelling (my part).** The mismatch surfaces via my **§4 disposition path** as `resume_disposition = DEGRADED` (the `content_lost` result reported through the receipt-gated report/receipt frames), rendered on the operator surface from durable state. The manifest entry **stays `settled_with_content`** (it truthfully records past durability); the **resume result is DEGRADED** because Conjunct B failed. The two are different records with different jobs — evidence-of-past vs trust-now — and keeping the manifest honest while degrading the resume is exactly what prevents silent promotion.

**3. Trust classification (my part), TOTAL over content kinds.** Edited provider/tool content is **untrusted → degraded**, never `settled_with_content`-trusted at resume. Total: *any* provider_output or tool_result whose recovered identity no longer matches its frozen entry ⇒ `content_lost` → `DEGRADED` → re-derived, never promoted. There is **no default-trust branch**: absent-or-mismatched positive evidence is never trusted (m-9 r17 §3). The classification is binary at my seam (identity-exact-match ⇒ trusted; else ⇒ degraded), with no "edited-but-trusted" state.

**4. Reconciliation with the immutable snapshot + prior receipt identity (my core).** My `resume_snapshot` (immutable §1 manifest bytes, rev16 §4, **no UPDATE path**) and my `content_ready_receipts` rows are **m-10-store state — an edit to m-9's D1 log does NOT rewrite them.** So after an edit they remain the **frozen record of what was settled**, describing "a prefix that no longer exists byte-for-byte" — and that is correct, because they are **evidence of past durability, not a claim about current bytes.** Reconciliation = my frozen evidence vs m-9's recovered (possibly edited) prefix, under the AND-invariant: match ⇒ trusted; mismatch ⇒ `content_lost`/DEGRADED. The snapshot/receipt are never mutated to "agree" with the edit — that would be the silent promotion the constraint forbids.

**5. Disposition + first action (my part).** `resume_disposition = DEGRADED`, `resume_action = re_derive` (the only wire value, rev16 §4 / m-9 r17 §3:360). First action: the worker **re-reasons from the durable recovered prefix**; nothing reconstructed, edited content never trusted. If no valid resume path exists even degraded ⇒ **fail-closed run-terminal** (m-9's honest floor). No silent resume, no auto-trust.

**6. Rebase-or-supersede — the MVP SUPERSEDES-BY-DEGRADE; it does NOT rebase.** My settlement snapshot + receipts are **immutable**; **no authorized-rebase path exists in the MVP.** So a **sanctioned** edit (a deliberate tool rewrite) is handled **identically** to an emergency repair: the edited content fails Conjunct B ⇒ `content_lost`/DEGRADED ⇒ re-reason. The successor does **not** rebase my durable evidence onto the edited bytes. An **authorized rebase-across-both-stores** (re-anchoring the receipt/snapshot identity to sanctioned new bytes) is exactly the **named Step-4 carry** (`ROADMAP.md`: path-independent canonicalisation or an explicit authorised rebase; git-like session versioning) — an **authority ingress the MVP defers wholesale** (the same class as the parked-clearing path and H-21). ## `receipt_conflict` is NOT implicated — the derivation (per master's ask, not analogy)
`receipt_conflict` fires **only** when m-10 receives a **second same-key live `content_ready` frame** whose evidence tuple differs from the first committed one (rev16 §2, the complement of duplicate-equivalence, first-committed-stands). **An edited historical log emits NO second `content_ready` frame at all** — an edit mutates the **recovered prefix** that stage-2 matching reads at *resume*, on a **different seam** (post-`turn_open` reconciliation), never the **live receipt-ingress** seam. The two seams do not meet: receipt-ingress is a live worker sending a fresh receipt; edit-handling is a resume reading stale bytes. Therefore relaxing `receipt_conflict` would **not** make an edited session resumable (there is no second receipt to conflict), and it **stays frozen** — confirmed by derivation, matching your VP-blocked-prescription correction exactly.
