## Item 1 — the controlled stale/wrong epoch-or-lease input (deterministic; two sub-faults)
The gate opens only on install-proof evidence — a tuple-matching `epoch_installed` event OR `state_proposal_result{installed}` — keyed by `{run_id, generation_id, turn_epoch, state_seq}`. The scenario induces, via the build-tagged test seam (the same limits/injection seam the frame fixtures use — no production injection point), a run whose **durable trusted tuple has advanced past a captured generation's tuple**, then replays that stale generation's admission evidence. Two deterministic sub-faults, each fenced:
- **(1a) STALE_EPOCH / STALE_STATE_SEQ:** install-proof evidence carrying a `turn_epoch` **and/or** `state_seq` **below the current durable tuple** (a superseded generation's install proof, presented while a newer transition has committed). rev16 §6:130 is exact: "an OLD `epoch_installed` event can never match the current tuple while a newer transition is pending."
- **(1b) WRONG_LEASE (disposed-but-live predecessor):** a generation whose lease was **released at its retirement** (rev16 §B.4 retire+release-lease+mint-E+1) attempts to bind/admit a successor turn. The lease is not held by that generation; single-writer forbids re-acquisition. *(This is exactly m-9's "disposed-but-live predecessor" hazard, observed at my admission seam rather than the log-writer seam.)*

## Item 2 — the admitted-current positive control (proves discrimination, not mere refusal)
Install-proof evidence whose tuple **exactly matches the current durable `{run_id, generation_id, turn_epoch, state_seq}`** ⇒ the two-form assign gate **opens exactly once** ⇒ the successor turn admits at the current epoch under a **fresh lease** (rev16 §4:55, atomic) ⇒ proceeds to the normal governed loop. The leg passes **only if the same harness both refuses (1a/1b) and admits (2)** — discrimination, not a gate that refuses everything.

## Item 3 — the exact fail-closed durable/wire outcome (my terms)
On the fenced (stale/wrong) input:
- **Durable:** NO successor `turns` row; NO active-turn lease bound to the stale generation; NO `resume_snapshot` written for a stale successor; the current durable trusted tuple **UNCHANGED** (stale evidence neither advances nor regresses it); the rejection is **recorded** per the §6 disposition table (`installed`-tuple-mismatch ⇒ fail-closed, recorded, no gate open; `rejected-stale` ⇒ **invariant fault**, recorded, **no re-proposal**, operator disposition — rev16 §6:123/§6:126).
- **Wire:** NO `assign` frame and NO `turn_open` emitted to the stale successor — the gate sits **before** lease-bind-before-assign-before-admission (rev16 §6:130 order), so no successor-facing frame is sent on a mismatch. The operator-visible surface is the §10 loud render + operator disposition (no silent swallow, no retry loop that could converge a divergent authority).

## Item 4 — zero-successor-work/effect (OBSERVED, per the xit-dur-4 reachability lesson)
A fenced successor performs **no provider attempt, no tool effect, no conductor verb, no durable write beyond the recorded rejection**. Reachability is insufficient (a worker that exposes a runnable transition but never executes it must not pass); the fixture asserts it **observably**:
- **ZERO rows** written to `provider_attempts` / `tool_calls` / `tool_authorizations` for the stale successor between the stale-admission attempt and the fail-closed rejection;
- **ZERO** CTRL-W `assign` / `turn_open` and **ZERO** DATA-P frames emitted on its behalf;
- the run **does not advance** (no new turn, epoch unchanged).
This is **structurally** guaranteed (the gate precedes all work) **and** asserted by observation (no rows, no frames) — the fixture proves the absence, not just the ordering.
