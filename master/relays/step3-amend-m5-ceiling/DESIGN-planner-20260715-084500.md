## F2 fold — freshness = section digest AND a monotonic trusted-config generation (rollback-closed)
**Accepted:** `policy_digest`-equality alone doesn't close rollback — an older policy section reintroduced could make a stale digest re-appear "current" and loosen a binding outside the typed respawn gate, violating the locked under-authorize-on-old-records principle (§5:86-95) and the §8c ceiling-raise-only-via-typed-contract rule.

**Freshness rule (m-10 load path), rev2:** a `bound_ceiling` is **fresh iff**
1. `policy_digest` == the **current active Layer-1 section stamp**, **AND**
2. `config_generation` == the **current active trusted-config generation**, where `config_generation` is a **monotonic, never-reused epoch** on the trusted-config (increases on every fold; a value is never reused).

**Any** of: absent · `policy_digest` mismatch · `config_generation` mismatch (higher = superseded policy; **lower/rollback = regression**) · unknown or **reused** generation · partial/unresolvable resolution ⇒ **stale ⇒ fail-closed** (deny all tool dispatch = zero execution) — **unless** the change is itself the product of the governed **typed reconfiguration/respawn path** (§4), which produces a **new binding at the new generation** and retires the old worker. A rollback therefore can never loosen (or even silently change) a running worker's ceiling: it fails closed and forces a governed respawn. The monotonic generation distinguishes **"same bytes still current"** (generation matches) from **"old bytes reintroduced"** (older-or-reused generation ⇒ stale).

**Cross-domain dependency (flagged, m-5 requires it — CC m-7.planner, m-1.planner):** the **monotonic, never-reused `config_generation`** is a required property of the CQ-4b trusted-config (one top-level digest + per-section stamps, loaded at genesis). The trusted-config **integrity/load owner is m-7** (conductor-core: trusted config load + integrity) and **genesis is m-1**; my freshness rule **consumes** this property, it does not author the trusted-config mechanism. If m-7/m-1 realize monotonicity via the **top-level config digest chained to a generation counter** (or an equivalent), my rule reads whichever field carries the never-reused epoch. **This is a dependency to confirm with m-7/m-1, not an m-5-owned mechanism** — I flag it so the first-stage interface names it rather than assuming bare digest equality.
