## 5. PER-ARCHETYPE INVARIANT COMPOSITION (acceptance criterion 3)

### 5.1 The composition model
A running seat's gate-set = **its `seat_archetype` (spawn-fixed) ⊗ the `slot_in` work-archetype of each record it submits (classified at acceptance).** The seat_archetype fixes {ceiling, tool-set, routing-prior, behavioral-mode, default human-mode}; each work-record's slot_in adds {observe-invariant set} on top of the phase-shaped base predicate, evaluated WITHIN the seat's ceiling. Example: an `implementer` seat (write-feature ceiling) submitting a `refactor` record gets the IMPL base predicate + test-files-unchanged, all bounded by write-feature (it cannot merge-to-protected regardless of work-archetype).

### 5.2 seat_archetype → {ceiling, routing-prior, tool-set, behavioral-mode, default human-mode} (candidate composition, surfaced)
| seat_archetype | authority-ceiling | tool-set | routing-prior (m-4 bucket) | behavioral mode | default human-mode |
|---|---|---|---|---|---|
| sensor | read-only | none | fast-cheap | answer-once | side-question surface |
| actuator | single-bounded-action | the one actuation tool | (per-action) | execute-once | interactive (gated) |
| implementer | write-feature | full | top-tier-coding | execute | interactive |
| design-lead | design/read-lean | read + design | strong-reasoning | plan/design | interactive |
| reviewer | read-only | read-only | mid/strong-general | adversarial | interactive |
| orchestrator | dispatch/route (no source write) | dispatch | strong-reasoning | decompose/route | interactive |

### 5.3 Authority-ceiling SEMANTICS (the lattice — promotes the v2.8.8 AUTHORITY enum)
A monotonic ordered lattice (least→most authority), consistent with the locked `AUTHORITY` enum:
`read-only` < `read-only+tools` < `write-scratch` < `write-feature` < `merge-feature` < `merge-protected`(A-gated).
- A `seat_archetype` pins a **MAX** ceiling at spawn (recorded per-assignment, F2).
- A template/expansion-slot may **TIGHTEN below** the archetype max (monotonic, like the c1 J1 gate-override monotonicity); it may **never loosen above** it.
- `route_dispatch()` refuses to staff a seat above its archetype ceiling (fail-closed, locked C2.2). The ceiling lattice is the concrete semantics behind the locked opaque `authority_ceiling`.

## 7. SENSOR / ACTUATOR ARCHETYPE DESIGN (acceptance criterion 5 — sensor full; actuator symmetric)

### 7.1 Sensor (the c2 sketch → full)
Direct prior art: claude-code `runSideQuestion`/`runForkedAgent` (`sideQuestion.ts:53-102`). Promote the invariant triple verbatim — `canUseTool`-deny + `maxTurns:1` + non-interrupting + separate sidechain surface.
- ceiling = read-only (hardest); `route_dispatch()` fail-closes any write/merge staffing of a sensor seat.
- tools = none (tool-blocked); turns = 1; shared read-only context fork (point-in-time); non-interrupting (lane continues); answer → separate surface, never the lane inbox.
- integrity split (locked C2.5): content = `self_reported`/advisory/never-gate-bearing; metadata (tool-blocked, no-source-actions, 1-turn) = `observed`.
- **NET-NEW over claude-code (its own gap note):** ours is a DECLARED seat_archetype with a seat-stamped FROM + an append-only routing/observation record stamping {seat, model, zero-tool ceiling} — not an anonymous self-fork.
- **OPEN (surfaced, c3): routing-prior tension.** C2.5 locked `fast-cheap`, but claude-code's sideQuestion deliberately **inherits the parent model** to keep the prompt-cache hit (`sideQuestion.ts:82-84`) — a fast-cheap model re-reads cold context. As a SEPARATE seat we do not share the lane's cache the way a self-fork does, so fast-cheap is defensible, but the **cache-hit-vs-cost** tradeoff is a real c3 routing-prior decision (m-4 boundary); flag, not blocker.

### 7.2 Actuator (the symmetric bounded-effector — surfaced)
The write-counterpart the dispatch names ("sensor/actuator"). Where the sensor reads, the actuator performs **exactly one declared bounded side-effect** then closes — the tightest WRITE ceiling (anti-confused-deputy).
- ceiling = `single-bounded-action` (one declared actuation, nothing more); tools = only the one actuation tool; turns = 1.
- Unlike the sensor, the actuator's output **IS gate-bearing** (it changed state) — observe-as-send gates the actuation's outcome (the action's evidence is `observed`, not advisory).
- candidates: an egress-send actuator (performs the external send after the egress gate clears), a formatter/codemod actuator, a comment-post actuator.
- **GATE-1 dependency (route to orchestrator):** a `single-bounded-action` ceiling generally CANNOT be enforced on a ride-existing-runtime in Step 1 (the host harness, not the conductor, bounds a seat's actions) — so v3.0 records the actuator ceiling as a governance contract + best-effort host-config; **true conductor-enforced single-action ceiling needs the standalone runtime (Step 4-5).** Not a c3 design blocker; a later-step build concern (§9).
