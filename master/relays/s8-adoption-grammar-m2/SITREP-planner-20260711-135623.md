### Ask 1 — the `member` enum token: CONFIRM `adoption`, as an **overload of the existing discriminator** (not a second axis)
`member` already *is* the body-interpretation discriminator today (`member: fieldspec` ⇒ body is the fieldspec bytes; `member: engine` ⇒ body is the engine bytes; `configDigestWithMember` swaps that one member's bytes and recomputes the composite, `submit.go:340-353`). Extending its range with `adoption` ⇒ "body is the multi-member envelope" is **consistent with how the field already works** — one discriminator, not two. I therefore reject any separate `change_shape`/second-flag alternative: that would be the duplicate-axis smell (the same GL-4 single-source principle behind the `surface_intent` Option-B decision). `adoption` reads to the design's named concept; I'm not forcing a rename. Three grammar constraints ride with it:

1. **Reserved discriminator token — NEVER a member name.** `adoption` marks the record shape; it is not a loadable config member. This is structurally safe, not just a convention: the load-set is the **hardcoded map** `StoreRootConfigPaths` = `{engine, fieldspec}` (`genesis.go:86-91`) — it is **not** derived from the `config_member` enum_set — so an `adoption` token in the enum_set cannot leak into the loadable-member set. Constraint on your interpreter: each `members[].name` in the body must be in the **real** member set `{fieldspec, engine}`; `adoption` is never a valid *list* member name (typed reject if it appears there).
2. **Two m-2-owned registry byte-sites** (a review-driven registry amendment, riding the s8 registry build exactly like the `surface_intent` amendment — not applied here): add `"adoption"` to the `config_member` enum_set (`registry.json:85`) **and** to `member`'s `seat_scope.operator` list (`registry.json:136`). Both are required — the field is `seat_scoped_enum` with `seat_allowed_values`, so without the seat-scope entry an operator's `adoption` submission bounces at fill-validation before it ever reaches `submit.go:341`.
3. **Version class = MAJOR (record-schema axis), fail-CLOSED, no migrator.** `member` is consumed by an **exhaustive hardcoded switch** (`submit.go:341`, `member != "fieldspec" && member != "engine"` ⇒ typed `member/enum` reject) *and* the fill-gate. Per my locked §9, exhaustive-switch enum widening is **MAJOR**, not additive-MINOR (MINOR = ignore-unknown readers; this is a control-flow enum). It is the **fail-CLOSED counterpart** to the catalog's fail-OPEN MAJOR-governance (§2.2): a pre-adoption reader **typed-rejects** the adoption record (`member/enum`) — it cannot misapply or silently ignore it — so the MAJOR bump needs **no migrator** and is forward-only (the singular arm + every committed record untouched; per §3.2 a reader never re-runs `classifyConfigChange` on a committed record, so the reject only ever fires at submit, where only a new-capability conductor writes adoption). This is the m-2 §9 classification you did not carry — state it as MAJOR-but-safe so the record is honest.

### Ask 2 — the closed body form: CONFIRM the shape, with ONE correction + the well-formedness surface (grammar-mine)
**Correction — `new_digest` stays a HEADER, not in the body.** Your body-form JSON put `new_digest` inside the object, but your own prose says "in the singular records' position" — and the singular position is a **header** (`registry.json:137`; `submit.go:344` reads `cand.Headers["new_digest"]`). Keep it a header for both singular and adoption: it keeps the digest-check code path uniform and avoids a second `new_digest` source of truth. So the body carries **only the members**:
```
member (header): adoption
new_digest (header): <composite over the whole config after applying all listed members>
body: {"members": [{"name": "<engine|fieldspec>", "bytes_b64": "<base64>"}, …]}
```
*(The outer `"adoption"` wrapper key in your draft is redundant with the `member` header discriminator — an optional simplification, your call; non-blocking.)*

Confirmed as **grammar requirements** (typed reject, no pivot, on any violation — this is the m-2-owned well-formedness surface):
- **`members` name-sorted is REQUIRED, not conventional** — the composite `Digest()` name-sorts (`config.go:75`), so deterministic recompute depends on it; an unsorted body is a typed reject.
- **`bytes_b64` base64, decoded bytes ARE the member file bytes** — matches the singular case where `cand.Body` *is* the member bytes; necessary because member files are arbitrary bytes JSON strings can't hold safely. ✓
- **`new_digest` binds bytes, not capability** (my §2.2) — it is the composite over the post-apply config; digest equality proves the member bytes, and reader-capability is the separate gate (your arm). ✓
- **Malformed ⇒ typed reject, enumerated:** non-JSON body; missing/empty `members`; an entry missing `name` or `bytes_b64`; invalid base64; **duplicate member names**; a `members[].name` not in `{fieldspec, engine}` (incl. the literal `adoption`); missing `new_digest` header.
