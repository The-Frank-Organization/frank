## What this proposal contains, and what it deliberately does not

**Contains:** the ten fixture-input artifacts (one per record, to the enumerated ten — no more, no fewer) and the two baseline artifacts the top-level `baseline_artifact_digest` / `baseline_config_digest` will name.

**Does not contain:** `STEP-3-EXIT-FIXTURES.json`. Per plan §7 step 3 the manifest is emitted as its own envelope only after every input digest is materialized and equality-confirmed. It rides proposal 2 (= M).

**Batching, and why.** All twelve ride ONE proposal rather than twelve. The lineage table pairs one `…-l4-materialize-<n>` receipt and one `…-l4-equality-<n>` confirmation to one `…-l4-propose-<n>`, so a per-artifact split would cost twelve hand-relayed round trips for no additional gate. If master prefers per-artifact receipts, say so and I will re-cut — the envelopes are already independent.

## Encoding decision (stated, because every downstream digest depends on it)

Every artifact is **RFC 8785 (JCS) canonical JSON, UTF-8, with NO terminal newline** — sorted keys, minimal separators, no floats anywhere. This matches the canonical-encoding rule already governing hashed JSON in this design (m-3 r4 R2-F1 "stored-bytes = exact JCS output, no terminal LF"; m-10's manifest encoding). It matters here because `input_artifact_sha256` is a hash over these exact bytes: a trailing newline or a key reorder silently changes every one of them. Master's materialization must write the bytes verbatim — no formatter, no newline-at-EOF convention.

## Carried obligation 3 — the r7-mirror check, DISCHARGED: NO

The brief makes this a mandatory check at E3-predicate authoring with a STOP-and-escalate branch. I ran it against the artifacts, not against my recollection of them.

**The trigger, exactly as ruled** (`master/RECONCILE.md:582`): re-open only if authoring the E3 exit-test predicates surfaces an **`xit-gov-1`-gating** predicate that demonstrably needs the m-10 leg to resolve 2a/2b **independently of the DATA-P reply** — independence becoming *correctness*, not *coverage*.

**Result: it does not.** Grounds:

1. `xit-gov-1`'s gating set is exactly predicates 2.1, 2.3 and 2.4. Master's ratified D2 fold makes 2.2 and 2.5 **recorded-only / non-gating**, so no verdict of theirs passes or fails a leg — and those are the two predicates that sit nearest the provider-refusal surface.
2. Predicate 2.1 takes the carried `frozen_core_digest` and the observer's **independent derivation over its captured wire request**. m-3 states the separation in its own bytes: *"P2b keys on the provider **request** m-8 sent, never on this m-8→m-9 **reply**"* (`2026-07-22-stage6-lane2-e0-e3-delta.md:186`). The 2a/2b split is a property of that **reply**.
3. None of the three gating predicates takes the §B sink record, `presence_class`, or `m10_row_state` as an input at all. The sink is an m-3 **record** that "enforces nothing" (§3.4); the composite exit proof stays Master+VP's.

So independence remains **coverage, not correctness**, which is the exact condition under which the v3 deferral stands. **Disposition recorded: non-gating deferred. No route-now escalation is raised on this obligation.**

**The contingency I am binding rather than burying.** This answer depends on a scenario choice that is mine: `xit-gov-1` is authored on m-8's **row 5** (sent, terminal `completed` — freeze reached, P2a=1), the only outcome class where predicate 2.1 is ELIGIBLE and DECIDABLE. On any refusal or loss class the predicate lands on an `unknown` branch and **HOLDS** the leg rather than passing — so a 2a/2b-dependent `xit-gov-1` is not constructible in the first place. If a later revision re-authors `xit-gov-1` onto a refusal cut, **this check must be re-run**; it is recorded inside the artifact itself so the dependency travels with the bytes.

## Two authoring decisions that need owner-fidelity attention

**1. `xit-op-1` is structurally a failure-surface test, and only one construction satisfies it.** The ratified predicate needs `{last_event, stop_reason, unknown_effects[], resume_action}` all present and non-null. But m-10 makes `runs.stop_reason` non-null **only** via `resume_frame_overflow` or `parked_unknown_capacity_exceeded`, NULL "in every other state and on every other failure path" — and the cap terminal explicitly carries **no** `resume_action`. Therefore `resume_frame_overflow` is the only construction putting both members on one record at one grain. I compose it with the N910 provider loss, which is causally natural rather than contrived: the accumulated `uncertain` entries are exactly what inflate the continuation frame past the bound. **m-10 owns this surface and must confirm the reading at owner-fidelity** — if m-10 reads `resume_action` at turn grain (the `DEGRADED`/`re_derive` pair) instead of run grain, this record changes.

**2. `xit-ho-1` deliberately does not invent m-2's member name.** §7 requires the second record to carry "a parent/reference to record (1)'s `relay_id`". The exact spelling of that member is m-2's owned schema. The artifact fixes the **semantic** requirement (a resolvable reference to record 1's `relay_id`) and names **m-2** as the owner-fidelity boundary that supplies the member name. Inventing another domain's field spelling is exactly the failure this project has caught before, so I did not.

**Two fixtures require the build-tagged TEST-ONLY reduced limits table** — `xit-dur-5` and `xit-op-1`. Under the production limits table m-10's compile-time assertion makes `resume_frame_overflow` **statically unreachable**, so the one-byte-over leg is not constructible in production and must not be faked there. This is recorded in both artifacts' `build_requirements`.

## Determinism — the precondition every digest-valued expectation rests on

This holds under either resolution of the esc1 question, which is why I authored it now rather than waiting.
