## Q-C RESOLUTION (m-2 §15 Q-C — my call as routing owner)

**Question:** does `model-per-dispatch` belong in the routing-record HEADER (per-relay field) or a separate
routing RELAY (per-dispatch record)?

**Resolution: HEADER field — carried on the dispatch-INITIATING relay (the PLAN / IMPL-dispatch-class relay
that routes a unit of work to a seat). NOT a separate routing relay. NOT a field on every relay.**

Precisely: a `model` header field (plus the deviation fields below), `owner: seat_scoped_enum` scoped to
planner / orchestrator-planner, `visible_when` = dispatch-initiating relays only (see encoding note). It is
semantically per-DISPATCH but physically carried as a header on the one relay that initiates the dispatch.

**Reasoning (decides the FieldSpec shape):**
1. **Altitude-B has one seat emit role+model AT dispatch.** The dispatch (line 22) + CLAUDE.md lock the
   "router seat" as the planner/orchestrator-planner that emits the work dispatch. Routing and dispatching
   are one act by one seat at one moment — the natural carrier is the dispatch relay itself, not a second
   record describing it.
2. **Forgery-robustness for free (Q3).** A header on the dispatch relay inherits that relay's stamped
   `FROM` (m-1 I2). No separate stamping path, no correlation between a routing record and the dispatch it
   routes — the routing decision IS the dispatch relay's content, stamped once.
3. **Outcome-correlation for free (Q5).** The v3.1 feedback loop must join (routing decision) → (outcome).
   The outcome lives in the dispatch's downstream relays (implementer report, review verdict, observed
   evidence) which already share the dispatch's lineage/DISPATCH_ID. Header-on-dispatch means the join is
   the EXISTING lineage graph (walk DISPATCH_ID → outcomes). A separate routing relay adds a third node and
   an extra join for no benefit.
4. **Per-dispatch, not per-relay.** The decision is made ONCE when work is routed, not on every SITREP in
   the thread. `visible_when` gates the field to dispatch-initiating relays, so it does not bloat ordinary
   relays — it collapses Q-C's apparent dichotomy (it is a header field, but effectively per-dispatch).
5. **A separate relay would only win** if a different seat routed after the planner, if a single dispatch
   were re-routed multiple times, or if the routing record had to exist before any work relay. None hold in
   altitude-B. So header is strictly simpler with strictly more reuse of the foundation's primitives.

Encoding note for m-2: `visible_when` should select dispatch-initiating relays. This is expressible with
existing atoms (`phase_in:[PLAN]` / IMPL-dispatch class + `role_in:[planner, orchestrator-planner]` +
`seat_scope`). If a clean single predicate is wanted, a trivial `dispatch_initiating:<bool>` atom can be
added to the §5 closed atom set — additive, no Turing-completeness risk. Flag, not a blocker.

## ANSWERS TO THE FIVE REVIEW QUESTIONS

**Q1 — Are altitude-B (role+model/dispatch) + capability priors + justified deviation + the v3.1
benchmark/feedback handle all expressible as typed FieldSpec fields?**
YES, all four are expressible (m-2 §12 m-4 bullet names them; FieldSpec §4 has the machinery):
- `role` — already `owner: system` (envelope, stamped). Routing emits the role TARGET of the dispatch; the
  emitter's own ROLE is stamped. Expressible. (E1: m-1 §6, m-2 §3.)
- `model` — header, `owner: seat_scoped_enum` (planner/orch-planner), `type: enum` (closed set of model
  ids), `consumers: [router]`. Expressible. (E1: m-2 §4 owner/seat_scope/enum_set/consumers fields; `router`
  is in the consumers enum, line 61.)
- `capability_prior` — `owner: system`, `type: object`/map, `consumers: [router]`. Expressible — BUT see
  Sharpening A on fill-semantics (snapshot vs reference). (E1: m-2 §12 "capability_prior (system/config)".)
- `justified_deviation` — `owner: free_text` (reason) + a `record_kind` `enum_set`, `consumers: [router]`.
  Expressible — see Sharpening B (own enum values). (E1: m-2 §12, §4 lineage_role/enum_set.)
- benchmark/outcome-feedback handle — `owner: system`, null-reserved, `consumers: [router]` (reserved),
  `lineage_role: none`. Expressible via the same null-reserved pattern as `certification`. (E1: m-2 §7/§12.)

**Q2 — header vs separate relay?** RESOLVED above: header on the dispatch-initiating relay.

**Q3 — does "stamped store as write target + routing-record FROM = router seat's stamped identity" give
forgery-robust dispatch authority (no lane can forge a routing decision)?**
PARTLY — necessary and delivered for the IDENTITY layer; the full claim needs two more pieces that the
foundation also supports:
- IDENTITY (delivered by m-1, by construction): a routing header rides `submit()`; `FROM` is stamped from
  the connection (m-1 I2 a–d all closed). A malicious lane cannot emit a routing decision attributed to the
  planner. ✓ (E1: m-1 §4 I2 proof, lines 59–68.)
- AUTHORITY (the rest of "no lane can forge a routing decision"): a lane could emit a `model` header under
  its OWN correctly-stamped FROM and have the router honor it. That is forging AUTHORITY, not identity.
  Closed by (b) `model` as `seat_scoped_enum` — absent from non-planner forms, so a pair/implementer form
  cannot render or submit it (m-2 fill-time authority, §3/§11.2), and (c) the m-4 router honoring a routing
  header only from an authorized emitting seat, keyed to the forgery-robust stamp (anti-confused-deputy).
- CONCLUSION: the foundation is SUFFICIENT to BUILD forgery-robust dispatch authority, but the stamp ALONE
  is the identity half. The authority half = m-2's seat_scope (must be ENCODED on the model field —
  Sharpening C) + m-4's router check (my domain, later cycle). This is precisely m-1's identity≠authority
  routing — accepted below.

**Q4 — record_kind reuses DESIGN_RECORD_KIND shape — right pattern, or own enum?**
Reuse the SHAPE (a closed enum classifying the justification + a free-text reason — the same FieldSpec
pattern), but routing needs its OWN enum VALUES. DESIGN_RECORD_KIND's values (`design-doc | audit-record |
direct-override`) are design-review-lineage concepts, semantically disjoint from routing rationale. The
routing-rationale enum maps to the locked 3-staged policy (CLAUDE.md): e.g.
`prior` (followed the capability-prior default) | `justified-deviation` (deviated, reason given) |
`operator-override` (pinned by operator/orchestrator) | `benchmark-derived` (v3.1-reserved). Overloading one
enum across two unrelated gates couples them (a future edit to design-review kinds would wrongly touch
routing) and violates canonical-iff-consumed (distinct consumers: `[router]` vs `[lineage_engine]`).
FieldSpec already supports a separate named-enum, so a distinct `ROUTING_RECORD_KIND` is expressible with no
foundation change — just don't literally share the DESIGN one. (E1: m-2 §4 enum_set named-enum, lines 54/60;
protocol DESIGN_RECORD_KIND values.)

**Q5 — is the benchmark/outcome-feedback handle shaped so the v3.1 loop bolts on WITHOUT re-cutting the
record or the gate?**
YES, conditional on three shaping requirements, all of which use patterns m-1/m-2 ALREADY ship:
(i) **Replay-completeness:** the routing header must denormalize the model-pick + the capability_prior IN
   EFFECT + the deviation flag + record_kind AT fill time, so the immutable record is self-describing. If
   capability_prior is only a live config reference and config drifts, you cannot later ask "did deviating
   from the prior pay off?" → Sharpening A.
(ii) **Reserved outcome handle:** a null-reserved system field (the `certification` pattern, m-2 §7) —
   `consumers: [router]` reserved for v3.1, `lineage_role: none`, default null in every routing record →
   activates by behavior change, zero schema change.
(iii) **Correlation by lineage, not mutation:** outcome arrives AFTER the dispatch; the store is immutable
   append-only (m-1), so you CANNOT fill the outcome back into the routing record. The v3.1 loop instead
   JOINS via the lineage graph (DISPATCH_ID → outcome relays) — which the Q-C header resolution makes free —
   and feeds results into the capability_prior CONFIG (a router INPUT), NOT into the gate. So no gate re-cut:
   feedback is read-side analytics adjusting future defaults, not a re-gating of past records.
If (i)–(iii) hold, the v3.1 outcome-feedback loop (the open, non-gradient analog of Fugu's reward) bolts on
cleanly. Only (i) needs sharpening with m-2. (E1: m-1 §6 immutable/append-only line 86; m-2 §7 null-reserved
certification lines 96–103; m-2 §9 read-time migration/append-only.)
