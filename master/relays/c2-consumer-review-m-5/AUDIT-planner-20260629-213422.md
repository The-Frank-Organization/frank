## DELIVERABLE 1 — Seam-fit verdict + interface findings

The opaque archetype-tag is consumed at THREE points, each correctly reserving semantics to m-5:
- m-3: the done-predicate hook takes the opaque `slot_in` atom and SELECTS an invariant-set; m-3 owns the predicate-execution mechanism + result shape, m-5 owns the tag→invariant-set map (m-3 §5; m-2 `slot_in` = "reserved opaque archetype-tag atom (m-5 owns the tag-space)").
- m-4 (recommendation): archetype tags parameterize the Layer-2 `(role, task_tag)→ranked-bucket` lookup (m-4 §10).
- m-4 (ceiling): the archetype authority-ceiling-at-spawn caps what the router may staff; `route_dispatch()` fail-closes to `routing_unavailable` rather than silently down-grade (m-4 §8/§3).

The clean factoring I CONFIRM fits: `slot_in` (and the m-4 archetype-tag vector) is ONE opaque key; each consumer keeps its OWN map from that key to its projection (m-3: key→invariant-set; m-4: key→bucket-ranking and key→ceiling). m-5 in c3 owns the key-space and all projection tables. The consumers need only the key. No re-cut. **But three findings make the difference between "fills in c3" and "needs a c2 re-cut":**

### F3 (the headline) — the tag-space is TWO orthogonal axes, not one conflated atom
There are two distinct, orthogonal archetype dimensions, consumed at different times by different domains:
- **work-archetype** (PER-RECORD): selects the m-3 done-predicate invariant-set. The m-3 §5 candidate set lives here — extension / refactor / cleanup / bugfix / migration. This is the `slot_in` atom on the WORK record being gated.
- **seat-archetype** (PER-SEAT, fixed at spawn): selects the m-4 authority-ceiling (§8) + the capability recommendation (§10). The sensor (Deliverable 3) lives here — e.g. sensor(read-only) / implementer(write) / reviewer(read-only).

A single seat carries BOTH at once (e.g. an `implementer` seat-archetype, ceiling = write-not-merge, doing a `refactor` work-archetype record whose invariant = suite-green + no-test-edits). Conflating them into one `slot_in` atom is an interface mis-cut. **Good news: the interface already accommodates the split** — m-4 §3 says "archetype tag **vector**" (plural-ready), and m-2's single `slot_in` is correctly just the work-archetype axis that m-3 reads. RECOMMENDATION (surface for the lock, lock in c3): record both axes as DISTINCT opaque tags — `slot_in` = work-archetype (m-3, per-record); a separate `seat_archetype` tag (m-4, per-seat-at-spawn) for ceiling + recommendation. m-5 owns BOTH spaces. Flagging now prevents a c2 re-cut where a consumer assumes one tag.

### F1 (threading REQUIREMENT, tamper-resistance) — `slot_in` must be CONDUCTOR-stamped from the spawn-time binding, never lane-writable
m-3's two load-bearing invariants (refactor = no-test-edits; bugfix = red→green) are the defense against the reward-hacking evidence m-3 cites (m-3 §5, audit §A). But they are only tamper-resistant if the lane CANNOT choose its own work-archetype tag — otherwise the lane re-tags `refactor`→`extension` to escape the no-test-edit invariant. By the same logic as observe-as-send ("you can't lie in a field you don't fill," m-3 §2), `slot_in` must be **conductor-stamped from the seat's spawn-time archetype binding** onto each work record, not agent-filled. m-2 currently declares `slot_in` opaque but does not pin its FILLER. RECOMMENDATION: at the lock, record that the archetype tag is conductor-filled-from-spawn (observer-class provenance), not lane-writable. This strengthens the whole tamper-resistance story and is the kind of cross-domain thread (m-4 spawn-binding → m-1 store → m-3 observe) the consumer lens exists to catch.

### F2 (threading, replay-completeness) — the archetype tag + resolved ceiling need a recorded PER-ASSIGNMENT home for the non-template path
m-4 §3 takes the archetype tag vector as a `route_dispatch()` INPUT, but the `routing_assignments` row (m-4 §5: `{seat, role, task_tag, declared_bucket, chosen_model, declared_deviated, pin_mode}`) has NO archetype/ceiling column. For template-spawned teams this is fine — the per-seat archetype lives in the m-5 template structure, referenced by `template_ref`. But for HAND-AUTHORED staffing (a planner directly staffing a sensor seat, no template), the ceiling must still be enforced AND recorded for replay/audit ("why was this seat capped read-only?"). RECOMMENDATION (m-4-owned record internals; I only surface the consumer need): add an opaque `seat_archetype` (and/or resolved `authority_ceiling`) column to the `routing_assignments` row, OR confirm that in v3.0 every archetype-bearing spawn goes through a template (so `template_ref` is the sole carrier). Either resolves it; I flag the gap, m-4 picks the fix.

NET: the opaque-atom interface FITS and reserves all semantics to m-5. F1+F2 are additive record-provenance threads; F3 is an axis clarification the "vector" language already anticipates. None forces a c2 re-cut if folded at the lock.

## DELIVERABLE 3 — the side-question sensor archetype (proposed; ceiling shape surfaced, full invariants c3)

The `/btw` analog (ROADMAP §interjection lines 37-39; jcode-ux-notes §3; Claude Code `runForkedAgent` prior-art). m-5 owns the archetype; m-4 routes it; m-6 owns the surface; the runtime owns boundary-injection/soft-cancel.

Proposed `sensor` archetype (a SEAT-archetype, F3 axis):
- **authority-ceiling-at-spawn = read-only.** The hardest ceiling. m-4's `route_dispatch()` REFUSES to staff a sensor seat into any write / edit / merge / dispatch / send-to-lane authority — fail-closed to `routing_unavailable`, never a silent downgrade (m-4 §8/§3). Permits only: read the shared lane-context snapshot + write to its own separate answer surface. This is the load-bearing anti-confused-deputy proof of the whole authority-ceiling mechanism.
- **tool ceiling = none (tool-blocked).** Even read-only tools (file-read/grep) are blocked in v3.0 (ROADMAP "tool-blocked"; jcode v1 + Claude Code `runForkedAgent` both block all tools). It reasons purely over the forked context snapshot. (SURFACE: a "read-only-tools sensor" variant is a c3 question, not v3.0.)
- **turn ceiling = 1 (single-turn).** Answers once, then the seat closes. No multi-turn loop.
- **context = shared, read-only fork.** A point-in-time snapshot of the lane's context + prompt cache at fork (Claude Code `runForkedAgent`). It does NOT see future lane state and is NOT in the lane's worker lineage — a parallel side-branch.
- **topology = non-interrupting parallel.** The lane CONTINUES (ROADMAP "without interrupting the lane"); the sensor's answer goes to a SEPARATE surface (m-6), never injected into the lane's inbox. (Contrast jcode `/btw` deferral; we adopt Claude Code's concurrent non-interrupting fork.)
- **routing (m-4) = `fast-cheap` bucket.** Lightweight by design (single-turn, read-only, no tools) ⇒ rank-1 recommended bucket is `fast-cheap`; the spawn `routing_decision` is trivially on-floor, no deviation expected.
- **observe profile (m-3) = read-only-report predicate.** The sensor's answer record uses the read-only/report base done-predicate (allowed artifact present + no source actions — trivially satisfied, tool-blocked). Its answer is agent-asserted judgment over a context snapshot ⇒ `record_integrity: self_reported` (no outside-vantage observation to make; advisory, never gate-bearing). The sensor record never gates the lane's deliverable path. This is honest and correct, not a gap.
- **egress (m-3) = dormant v3.0 / gated on first external send.** If a sensor answer ever leaves to an external surface (m-6 away-mode), it passes the fail-closed egress scan like any send.

Why it is an ARCHETYPE, not a one-off: it is the cleanest instance of the seat-archetype axis (F3) — a pure read-only ceiling + tool-block + turn-cap — and it is exactly template T3 made of one sensor seat. It validates the entire authority-ceiling-at-spawn mechanism end-to-end.
