## 1. The extraction boundary — what "the valid prefix" is, and how its end is fixed
Under the trimmed floor (one file per run · completeness-gated · settled-tool-round checkpoints; no chaining/rotation/boundary-equation):
> **The valid prefix = the ordered records from the file start up to and including the `round_marker` whose `round_index` == the fixture's pinned `resumed_round_index`.** Its end is fixed by that **pinned round checkpoint**, not by where the file ends. A round is in the prefix only if it is **complete** (all its records present and each record complete — the completeness test, Route 1 Ask 3) and closed by its `round_marker`; an incomplete final record (torn write) or an in-flight partial round is **not** in the prefix.

No chain/boundary-equation is needed to define the boundary under the floor: **completeness + the pinned round checkpoint** determine it totally.

## 2. The canonical representation — the exact form compared
> **The ordered sequence of the valid-prefix records, each in its §1.3 canonical JSON form** (keys sorted lexically, no insignificant whitespace, UTF-8, one record per line). The comparison is over the record **contents** (the authored bytes) — which the harness holds on both sides (condition (iv): the harness authors the record contents) — **not** over per-record digests. Members:
- **Included:** all authored content members (envelope + payload) — `seq`, `kind`, `turn_id?`, `round_index?`, `ts_monotonic`, and the per-kind payload.
- **`ts_monotonic` is safe to include** for the same reason I gave earlier: the valid prefix is **read and replayed verbatim on resume, never re-stamped**, so the actual prefix reproduces the frozen `ts_monotonic` byte-for-byte. (If any future scenario had the build re-author a prefix record, its `ts_monotonic` would be non-deterministic and would have to be harness-supplied under a stated rule — not the case for `xit-dur-1`.)
- **Excluded:** the per-record content checksum (`record_digest`), which drops to **advisory** under Route 1 Ask 3 (a bit-rot diagnostic / edit-label, not part of the compared content) — so it is **not** a member of the compared representation. `prev_digest` is gone entirely (no chaining). `segment_id`/`marker_digest`/`seq_hwm`/`generation_id` are the S-1 **receipt** members (Route 5), not journal-record members, and are not part of this comparison.

So the compared object is a **closed, ordered, canonical record-content sequence** — a bounded artifact, both sides in hand.

## 3–4. Expected artifact + actual locator (m-3's, with the m-9 constraint)

## 5. The mismatch diagnostic

## THE FROZEN-INTERVAL PROOF (the load-bearing part — VP4-F1)
**frank keeps appending after it resumes**, so an unbounded "compare the log" would compare a legitimately-grown file. The comparison must bind the **frozen interval**, and it does, by construction:
> **The compared interval's upper bound is the `round_marker` for the fixture-pinned `resumed_round_index`** — a value **frozen in the fixture input**, not read from the file's current end. Records after that round_marker (rounds with `round_index` > `resumed_round_index` — the post-resume appends) are **outside the compared interval by definition of the boundary (§1)**. The extractor walks from the start and **stops at the pinned round_marker**; it does not read "to end of file." So the interval is `[start, round_marker(resumed_round_index)]`, derived entirely from frozen fixture material (`predecessor_turn_id` + `resumed_round_index`), and the append tail is excluded **before it is ever read** — not re-scoped after the fact. This removes the circularity VP4-F1 identified: the bound is a frozen input, so a legitimately-grown file cannot spuriously fail or be silently re-scoped.

## This is NOT the ordered digest list in another costume
The compared object is **record CONTENTS**, not per-record digests. The operator rejected the ordered `{seq, record_digest}` list; this comparison uses **no per-record digest as the comparison term** (the checksum is advisory, excluded from the compared representation, per Route 1 Ask 3). The whole-prefix content comparison is the operator's chosen form, and it is **soundly specifiable** — I do **not** conclude it needs per-record structure, so this is not a blocker.
