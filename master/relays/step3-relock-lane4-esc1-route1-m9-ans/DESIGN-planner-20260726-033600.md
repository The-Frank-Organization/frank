## Ask 2 — can per-record checksums become advisory rather than gating? YES, with a trust-downgrade, not a silent pass
A checksum **mismatch on a well-formed historical record** is an **edit**, and it should be surfaced as a **label + trust re-classification**, never a resume refusal and never a silent promotion:
- The mismatch **triggers** re-labeling: the record is marked **edited-since-write**, and its content is **re-classified out of trusted-provider/tool-truth** — it becomes **untrusted-but-model-visible or degraded** (the exact class is Route 3's trust machinery), so an edited `provider_output`/`tool_result` is **never presented as the provider's/tool's actual output** (the deepagents fabrication class my §9 faults). That honours the VP's constraint verbatim: *"'label, never gate' cannot silently promote edited bytes as prior provider/tool truth."*
- With that trust-downgrade in place, the mismatch **does not gate resume** — resume proceeds with the edited content honestly labelled. So the checksum is **advisory** (it fires a label + downgrade), not a bar.
- **What must still gate is NOT a checksum case — it is torn-write (Ask 3).** So "advisory" here means "advisory as a *content-integrity gate*"; it retains a real job (fire the edit-label + trust-downgrade). It is not ignored.

**Answer: yes — advisory, meaning it triggers an honest edit-label + trust-downgrade rather than a refusal; no mismatch class needs to gate resume, because the only thing that must gate (a torn final record) is caught by completeness, not by the content checksum.** The full trust-classification is Route 3 (joint m-9+m-10), which I do not author here.

## Ask 3 — does last-record completeness cover torn writes on its own? CONFIRM
Torn write = an **incomplete final record**; edit = **well-formed records, different content** (your distinction, exactly). In a line-oriented journal (one record per line, `\n`-terminated, per §1.3), a torn final write manifests as **a final line lacking its terminating `\n` and/or not parsing as a complete record** — detectable **nearly free** by completeness, without any content checksum.
- **So completeness covers torn-write on its own** for the single-turn confusion-not-malice MVP. The per-record **content** checksum is therefore **NOT the torn-write/durability mechanism** — completeness is.
- **What completeness misses that a checksum catches (the honest refutation you asked for):** a **complete-but-corrupted** record — same length, valid JSON, terminating `\n`, silently flipped bytes (**bit-rot**). A content checksum catches that; completeness does not.
- **Is bit-rot load-bearing for the MVP?** Under **confusion-not-malice + single-turn + local filesystem**, bit-rot is a rare **hardware** event, not an admitted adversary — and a real harness on a plain file has the identical residual (a harness on SQLite gets per-page checksums from the engine for free). So the checksum's residual role is a **bit-rot diagnostic**, which is exactly the **advisory** posture of Ask 2. It is not a durability mechanism the MVP torn-write requirement needs.

**Consequence — the gating floor shrinks:** the **gating** durability elements reduce to **{completeness of the final record · the settled-tool-round checkpoint marker · the per-run writer fence}**. The per-record content checksum drops to **advisory** (bit-rot diagnostic + the Ask-2 edit-label). This composes cleanly with Ask 2 and with the Route-5 member trim.
