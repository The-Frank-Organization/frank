## Blocking finding

### 1. `Scan` has no value to scan after the Renderer contract is introduced

The r2 design defines `RenderedField` as `{ Name, Value string; Origin Origin }` and `Renderer func(meta gate.OutboxItem, source record.Record) (Rendered, error)` (`docs/sprints/2026-07-06-s5-slice-5/designs/s5-b-mechanisms-design.md:123-127`). That is the right producer shape: the egress renderer owns the outbound value, including conductor-generated ODB slots.

But the `Scan` input type remains `Item struct { Meta gate.OutboxItem; Source record.Record; Dest, Field string; Origin Origin }`, with no `Value` field (`.../s5-b-mechanisms-design.md:105-111`). `Drain` is required to call `render()` and scan every rendered field pre-send (`.../s5-b-mechanisms-design.md:111-116`, `:138-147`), and the pass leg specifically depends on a conductor-shaped renderer generating a `model_name` field (`:129-131`, `:140-146`). As specified, there is nowhere for `Drain` to pass that generated field's `Value` into `Scan`.

This is not cosmetic. Confidentiality and safety rules classify content: model-name tokens, secrets, PII, and auth URLs. For fields generated by the renderer, especially the ODB `model_name` slot, the value may not exist in `source.Headers` or `source.Body` at all. If `Scan` only receives `Source`, `Dest`, field name, and `Origin`, it cannot prove the r2 acceptance legs through the real `Drain` contract.

Required revision: make the scanned item carry the rendered value, or make the scan signature accept `RenderedField` directly. For example:

```go
type Item struct {
    Meta gate.OutboxItem
    Source record.Record
    Dest string
    Field RenderedField
}
```

or equivalently add `Value string` beside `Field string`. Then state that `Drain` scans each `RenderedField.Value` with its paired `Name` and `Origin`, while findings still render only `Field:Class` for I-PH. This keeps the r2 provenance fix intact and makes the pass/(a)/(b)/(c)/fail-closed legs implementable through `Drain`.
