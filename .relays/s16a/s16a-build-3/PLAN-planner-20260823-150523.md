## 3. Test-design laws (each is a charter/plan/PM obligation, not style)
1. **Contracts, never code.** Every assertion derives from the pinned bases (as amended) and the row's CT cell. Reading current module source to learn "what it does" is legitimate only for locating exported surfaces to probe; an expectation sourced from current behavior instead of the contract is the defect class this battery exists to kill.
2. **Compile-clean, RED-by-assertion.** The whole package MUST compile and run at the launch base. A gate row's nonconformance must surface as a test FAILURE (assertion/`t.Fatal`), NEVER a compile error — a compile break silences the other 63 rows. Concretely: probe missing struct members via wire-bytes/JSON round-trips or reflection (field lookup fails → `t.Fatalf` → RED); probe never-built pieces via behavior (C09: dial through the EXISTING `internal/appctl/brokerclient` — no listener answers → RED; A12/C07: drive the existing entry points and assert the contract-required effect, absent → RED). Never reference an identifier that does not exist at base.
3. **RED means FAIL, never skip.** No `t.Skip` in any gate row — a skipped test binds nothing (vacuity). Every expected-RED row fails with a message naming the row ID and the missing/mismatched obligation.
4. **Anti-vacuity is law.** A gate row GREEN at first contact is a FINDING (the test binds nothing, or the ledger row is wrong): STOP on that row, file it in the WP1-close SITREP for routing up — never silently re-write the test to force RED, and never count it a pass. Symmetrically: any of the 20 pin rows (G01–G20) RED at base is a finding (regression pin broken or test misbound).
5. **Reachability preconditions named.** Each test reaches its gate through the enclosing path the contract names (the gate-claims-need-reachability law); a test that asserts a gate it never reaches is vacuous.
6. **Binding visible for the fidelity round.** Each test function carries a doc comment: row ID · the CT cell reference (r9 §2 row, or A-1 for G20) · governing selector(s) · which §4 flag(s) apply. The PM fidelity round verifies BINDING; make it checkable from the test text.
7. **One test per row.** Multiple assertions inside a row's test are fine; a 65th test function for coverage that fits NO row is not — any no-row coverage discovered during the build is routed up (the G20 precedent shows the path works), never written.
8. **Existing batteries stay green — exact command.** At every commit, from `frank/`: `go test -p=1 -count=1 $(go list ./... | grep -v '^github.com/jackli/frank/test/seam$')` stays green (all pre-existing packages; the ONLY exclusion is the seam package itself). The seam battery runs separately: `go test -count=1 ./test/seam/ -run 'TestCT_'` (expected 20 GREEN / 44 RED at base; the census tool consumes its `-json` form). The seam package is the gate instrument, exempt from green-at-every-commit until WP5, where the full unexcluded battery `go test -p=1 -count=1 ./...` must be green.
